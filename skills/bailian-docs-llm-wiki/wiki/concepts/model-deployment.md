# 模型部署与推理优化

模型部署与推理优化是指将训练或微调完成的模型，通过规格适配、量化压缩、缓存加速、参数调优等手段，在百炼平台高效、稳定、低成本地提供在线服务（如 API 调用）的全过程。其核心目标是在满足业务对延迟（如首 Token 延时）、吞吐（RPM/TPS）、精度和成本（MU 规格）要求的前提下，实现推理性能与资源效率的最佳平衡。

## 在百炼平台的不同场景中，这个概念如何使用

- **模型压缩环节**：作为部署前的关键预处理步骤，通过后训练量化（PTQ）将微调模型转换为低精度版本（如 W4A4），显著降低部署所需的 MU 规格（如从 MU16 降至 MU5/MU8），从而直接减少推理成本；该操作不可逆，且仅支持华北2（北京）地域的百炼内微调模型。

- **模型调用与 API 集成**：在 `GET STARTED WITH MODELS` 和 `APPLICATION CALL` 场景中，推理优化体现为对关键参数的主动控制——例如显式设置 `max_tokens` 防止冗余生成、启用 `stream=true` 降低端到端感知延迟、合理配置 `temperature` 与 `top_p` 减少无效采样开销；同时需严格匹配地域与 Base URL（如北京地域必须使用 `dashscope.aliyuncs.com`），避免跨域调度引入额外网络延迟。

- **监控与持续调优**：在 `MODEL MONITORING` 场景中，推理优化是闭环反馈的基础——通过分钟级指标（如「首 Token 延时」「调用时长」「失败率」）实时定位性能瓶颈，结合告警（如“首 Token 延时 >10 秒”）触发人工干预或自动扩缩容决策；用量统计（如 TotalToken 消耗）则用于验证优化效果与成本收益。

> ✅ 提示：所有优化动作均以「已发布模型」为作用对象；未发布的微调模型、基础模型或 OSS 上传模型无法直接部署，须先完成发布流程。

## 关键参数和配置

| 参数/配置项 | 所属环节 | 说明 | 推荐实践 |
|-------------|----------|------|-----------|
| **量化模板（MU 编号）** | 模型压缩 | 决定压缩后模型的部署规格（如 MU5/MU8/MU9），编号越大，成本越低但精度风险越高 | 免费期内对比多个模板在业务测试集上的首 Token 延时与准确率，优先选 MU8 平衡点 |
| `max_tokens` | 模型调用 | 限制响应最大长度，直接影响推理时长与 Token 成本 | 生产环境必设，值应略高于历史 P95 输出长度，避免截断或过度生成 |
| `stream` / `incremental_output` | 模型调用 & 应用调用 | 启用[流式输出](streaming.md)，降低客户端首包等待时间 | 对话类应用默认开启；注意流式响应需客户端兼容 SSE 或分块解析 |
| `workspace`（Header） | 应用调用 & 模型调用 | 显式指定工作空间 ID，确保请求路由至正确地域与资源池 | 跨地域调用（如法兰克福）时**必须传入**，否则可能失败或延迟激增 |
| **告警阈值（首 Token 延时、失败率等）** | 模型监控 | 定义性能退化的判定边界，驱动快速响应 | 将「首 Token 延时 >10 秒」与「失败率 >1%」设为必配基础告警 |

## 面向开发者，简洁实用

- ✅ **先压测，再上线**：新模型部署前，务必用真实业务请求压测 5~10 分钟，观察监控页的「首 Token 延时」P95 和「调用时长」分布，而非仅依赖单次调用结果。  
- ✅ **压缩不是万能药**：量化可降成本，但不解决架构瓶颈（如 RAG 检索慢、插件调用阻塞）；若首 Token 延时高，优先检查是否启用了高开销功能（如 `enable_thinking=true`）。  
- ✅ **日志即证据**：开启「推理日志」后，可精准比对 Prompt 输入与实际 Token 分词、Attention 计算耗时，快速定位是模型本身慢，还是输入预处理/后处理拖累。  
- ❌ **勿跳过地域校验**：北京地域支持全部优化能力（压缩、监控、流式、推理日志），其他地域功能不全；生产环境请统一使用北京地域工作空间，避免兼容性问题。  
- ⚡ **一句话口诀**：**“北京压、量化选、流式开、延时盯、日志留”** —— 覆盖部署与推理优化全链路关键动作。
