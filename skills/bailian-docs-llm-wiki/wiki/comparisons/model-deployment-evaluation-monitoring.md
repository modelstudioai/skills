# 模型部署、评估与监控方案对比

为帮助开发者在百炼平台高效构建、验证与运维大模型服务，本文系统对比三大核心能力模块——**模型部署**、**模型评估**与**模型监控**——在技术实现、使用约束、成本结构及适用阶段上的关键差异。对比聚焦于生产落地全生命周期：从服务上线（部署）、效果验证（评估）到稳定运行（监控），旨在提供清晰、可操作的技术选型依据，避免因能力错配导致的资源浪费、验证偏差或运维盲区。

---

## 关键维度对比

| 维度 | 模型部署 | 模型评估 | 模型监控 |
|------|----------|----------|----------|
| **核心目标** | 提供稳定、可扩展、可计费的推理服务能力 | 量化模型输出质量，支撑效果决策与迭代归因 | 保障线上服务健康度，实现分钟级可观测与异常响应 |
| **输入格式** | 模型标识（`model_code`）、部署参数（如 `input_tpm`, `deploy_spec`）、OSS 模型文件（LoRA） | 评测数据集（含 `prompt`/`completion` 列）、自定义评分 Prompt、规则表达式、人工标签定义 | 无显式“输入”；自动采集所有已部署模型的调用请求（含 API-Key、时间戳、用量元数据） |
| **输出格式** | 可调用的 API 端点（`https://dashscope.aliyuncs.com/api/v1/services/...` 或 OpenAI 兼容 `https://maas.aliyuncs.com/v1/chat/completions`） | 结构化评测报告（综合得分、通过率、维度分布图）、逐样本明细表（含裁判模型打分/规则匹配结果/人工标注） | 实时监控图表（TPS、延迟、失败率等）、告警通知（短信/邮件/钉钉）、审计日志（Request ID + 状态码 + [Token](../concepts/token.md) 数）、推理日志（完整 [prompt](../guides/prompt.md)/response，需投递） |
| **支持模型类型** | • PTU/DTU/MU：预置模型、LoRA 微调模型、全参微调模型<br>• [Token](../concepts/token.md) 按量：**仅 LoRA 微调模型**<br>• 智能路由：限定预置模型子集（如 `qwen3.8-max`, `deepseek-v4-flash-0731`） | **仅文本生成类模型（Text Generation）**：<br>• 预置模型（千问系列等）<br>• 用户 LoRA/全参微调模型<br>• **不支持多模态、语音、向量模型** | 所有已在百炼模型列表中可调用的模型（含调优模型）<br>• **但语音/图片/视频生成、三方直连模型不支持告警功能** |
| **API 端点** | • 部署管理：`POST /api/v1/deployments`（创建）<br>• 推理调用：`POST /api/v1/services/{service_id}/chat/completions`（DashScope 协议）或 `POST /v1/chat/completions`（OpenAI 兼容） | • 创建维度：`POST /api/v1/evaluation/metrics`<br>• 创建任务：`POST /api/v1/evaluation/tasks`<br>• 查询结果：`GET /api/v1/evaluation/tasks/{task_id}/results` | • 监控数据：`GET /api/v1/telemetry/metrics`（需权限）<br>• 告警配置：`POST /api/v1/alert/rules`<br>• 日志查询：通过 SLS 控制台或 OpenSearch API（投递后） |
| **计费方式** | • PTU/DTU：按预购 TPM（每分钟 [Token](../concepts/token.md) 数）**预付费/后付费**，保底计费<br>• MU：按模型单元（MU）数量**按小时计费**<br>• Token 按量：按实际输入/输出 Token 数**按量计费**（无保底） | • **大模型评估维度**：产生**被测模型推理费 + 裁判模型评分费**<br>• **规则评估/人工评估维度**：**仅被测模型推理费**（若使用推理结果集则免二次推理费）<br>• 评测维度模板创建本身**不收费** | • 监控指标展示、告警配置、审计日志查看**免费**<br>• 推理日志投递至 SLS：按 SLS 标准计费（存储 + 写入 + 查询）<br>• **监控数据本身不参与计费对账**（对账以费用中心账单为准） |
| **典型场景** | • 高并发客服机器人（PTU）<br>• 金融风控强隔离推理（DTU/MU）<br>• A/B 测试快速验证 LoRA 效果（Token 按量）<br>• 成本敏感型灰度发布（智能路由） | • 新模型上线前效果验收（自定义评测）<br>• LoRA 调优前后效果归因分析<br>• 通用能力基线 benchmark（MMLU-Pro/GSM8K，北京地域）<br>• 客服回答准确性自动化抽检（规则+LLM评估组合） | • 生产环境 SLA 监控（首 Token 延迟 <800ms）<br>• 突发流量导致限流告警（`rate_limit_exceeded_count > 5/min`）<br>• 异常错误率排查（失败率突增至 5%）<br>• 合规审计（审计日志留存） |

## 适用场景建议

### ✅ 模型部署 —— 选型决策树
- **需要极致低延迟 & 长上下文（1M token）？** → 优先选 **PTU**（如知识库问答、长文档摘要）。  
- **要求资源独占、强 SLA 保障、支持 PD 分离/高级推理模式？** → 选 **DTU 或 MU**（如金融交易决策、医疗报告生成）。  
- **仅验证 LoRA 效果、无稳定流量预期、预算极敏感？** → 用 **Token 按量**（注意：不支持全参微调模型）。  
- **多模型并行测试、追求效果与成本自动平衡？** → 启用 **智能路由**（仅限 OpenAI 接口 + 北京/新加坡地域）。  
- ⚠️ **避坑提示**：Token 按量部署不可扩缩容（需人工审核），且一个月无调用自动释放；切换计费模式必须重建服务。

### ✅ 模型评估 —— 效果验证策略
- **快速初筛模型能力？** → 使用 **基线评测**（MMLU-Pro/GSM8K），5 分钟出报告（限北京地域）。  
- **业务场景定制化评估（如“法律条款解释准确性”）？** → 构建 **自定义评测任务**，组合：  
  - `大模型评估-分类型`（裁判模型判断是否合规） +  
  - `规则评估-字符串匹配`（检查是否包含强制关键词“不得”“应当”）  
- **成本敏感型高频验证？** → 优先用 **规则评估**（BLEU/ROUGE/Cosine）或 **人工评估**（无裁判模型费）；避免高频调用大模型评估。  
- ⚠️ **避坑提示**：评测维度类型创建后不可更改；使用“推理结果集”作为数据源可规避重复推理费用；1–3% 分差属正常评测噪声，勿过度解读。

### ✅ 模型监控 —— 运维保障要点
- **生产环境必须开启？** → **审计日志（默认开启） + 关键指标告警（失败率、TotalToken 突增）**。  
- **深度故障排查（如“为何某次回答错误”）？** → **开启推理日志投递至 SLS**（注意：需提前授权，关闭后日志不可补录）。  
- **成本治理重点？** → 在 **用量统计页**（非监控页）分析 Token 消耗 Top 模型/API-Key，结合“免费额度用完即停”开关控制预算。  
- ⚠️ **避坑提示**：用量数据延迟约 1 小时（用于对账），监控指标延迟为分钟级（用于故障响应）；二者不可混用；内容安全错误次数等指标**不支持告警**。

## 技术选型参考（面向开发者）

| 阶段 | 推荐组合 | 理由 |
|------|----------|------|
| **开发验证期** | Token 按量部署 + 自定义评测（规则评估为主） + 基础监控（审计日志） | 低成本启动，快速验证 LoRA 效果；避免裁判模型费用；审计日志满足基础追溯需求。 |
| **灰度上线期** | PTU 或 MU 部署 + 基线评测（MMLU-Pro） + 失败率/延迟告警 | 平衡性能与成本；用权威 benchmark 建立效果基线；分钟级告警保障灰度稳定性。 |
| **生产稳态期** | DTU/MU 部署 + 组合评测（LLM评估 + 规则评估） + 全维度监控（推理日志 + 多指标告警） | 强隔离保障 SLA；多维度交叉验证效果（如“事实性”用 LLM 评，“格式合规”用规则评）；推理日志支撑根因分析与合规审计。 |
| **成本优化期** | 智能路由（OpenAI 接口） + 用量统计分析 + TotalToken 突增告警 | 自动选择性价比最优模型；用量页精准定位高消耗点；告警驱动主动缩容或模型降级。 |

> **最后建议**：始终遵循「先评估、再部署、后监控」闭环。避免未经评测直接部署上线；监控配置应在服务上线前完成；所有部署与评测操作均需在**同一业务空间**下进行，跨空间数据不互通。
