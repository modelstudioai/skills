# 开发指南类对比：Agent Development、Model Compression、Model Monitoring

## 对比目的与背景

在百炼平台的模型应用全生命周期中，开发者需在不同阶段选用适配的技术能力：从构建具备自主行为的智能体系统，到优化模型部署成本与性能，再到保障线上服务的稳定性与可观测性。本对比旨在为开发者提供清晰、结构化的技术选型参考，聚焦三类核心开发指南——**Agent Development（智能体开发）**、**Model Compression（模型压缩）** 和 **Model Monitoring（模型监控）**，厘清其定位差异、能力边界与集成路径，避免因场景错配导致开发返工、资源浪费或运维盲区。

三者并非互斥功能，而是分属不同抽象层级的支撑能力：
- **Agent Development** 是面向**应用逻辑层**的高阶编排框架，解决“如何让模型自主完成复杂任务”；
- **Model Compression** 是面向**模型交付层**的工程优化工具，解决“如何以更低资源成本部署已训练模型”；
- **Model Monitoring** 是面向**运行时基础设施层**的可观测性体系，解决“如何持续验证模型服务是否健康、合规、高效”。

以下从关键维度展开横向对比，并给出针对性的适用场景建议。

## 关键维度对比表

| 维度 | Agent Development | Model Compression | Model Monitoring |
|------|-------------------|-------------------|------------------|
| **核心目标** | 构建有状态、可中断续接、支持多步工具调用与沙箱执行的智能体应用 | 将微调模型进行后训练量化，降低推理部署所需的 MU 规格与成本 | 提供分钟级延迟的调用统计、性能指标、告警与日志能力，保障模型服务可观测性 |
| **输入格式** | - `message` 事件（含用户输入文本/图片等）<br>- 挂载资源（文件、记忆库、MCP 配置）<br>- Session 初始化参数（`agent.id`, `environment_id`, `resources`） | - 微调模型 ID（仅限百炼平台内训练成功的 custom fine-tuned model）<br>- 量化模板（如 `MU5`/`MU8`）<br>- 可选校准数据集（最多 5 个已发布数据集） | - 模型 Code（所有百炼可见模型均支持用量统计；仅部分模型支持完整监控告警）<br>- 告警配置（指标、阈值、周期、通知方式）<br>- 日志投递配置（SLS Project/Logstore、角色授权） |
| **输出格式** | - SSE 事件流（`message`, `tool_call`, `tool_approval_request`, `session_status` 等）<br>- 沙箱执行结果（stdout/stderr、文件变更、工具返回值）<br>- 持久化会话历史与记忆库快照 | - 新的压缩后模型 ID（格式：`原模型名-后缀`，如 `my-qwen-ft-001-w4a4`）<br>- 量化报告（含精度评估摘要，控制台可查） | - 实时监控图表（调用次数、失败率、首 Token 延时等 15+ 指标）<br>- 告警通知（短信/邮件/钉钉/Webhook）<br>- 审计日志（Request ID、状态码、Token 数、延时）<br>- 推理日志（含完整 Prompt/Response，需手动开启） |
| **支持模型** | - 主力支持 Qwen 系列：`qwen3.8-max`（多模态）、`qwen3.7-max`、`qwen3.7-plus`<br>- 要求模型具备工具调用与长上下文理解能力<br>- 不支持纯基础模型或无状态轻量模型 | - **仅支持百炼平台内完成的微调模型（custom fine-tuned models）**<br>- 当前明确支持：`qwen3.5-flash-2026-02-23`、`qwen3.6-plus-2026-04-02` 等（以控制台为准）<br>- **不支持基础模型、第三方模型、OSS 上传模型** | - **用量统计**：所有百炼模型列表中可见模型（含微调部署模型）<br>- **监控告警**：文本生成类模型普遍支持；语音/图片/视频生成及三方直连模型**部分不支持**（控制台实时展示为准） |
| **API 端点（典型）** | - `POST /v1/managed-agents/sessions`（创建会话）<br>- `POST /v1/managed-agents/sessions/{session_id}/events`（发送事件）<br>- `GET /v1/managed-agents/sessions/{session_id}/events`（SSE 流式订阅） | - `POST /v1/model-compression/tasks`（创建压缩任务）<br>- `GET /v1/model-compression/tasks/{task_id}`（查询状态）<br>- `GET /v1/model-compression/models/{model_id}`（获取压缩后模型详情） | - `GET /v1/model/telemetry/metrics`（查询监控指标）<br>- `POST /v1/model/alerts/rules`（创建告警规则）<br>- `GET /v1/model/usage/statistics`（查询用量）<br>- 日志通过 SLS OpenAPI 或控制台投递 |
| **计费方式** | - 按 **Session 运行时长 + 所用 MU 规格** 计费（沙箱环境按实际占用资源计费）<br>- 工具调用（如 `web_search`）、MCP 服务调用可能产生额外费用<br>- CLI 工具链免费 | - **压缩任务本身限时免费**（截止时间以控制台公告为准）<br>- **压缩后模型部署仍按 MU 规格正常计费**<br>- 不产生额外 SLS/Prometheus 费用 | - **监控与告警规则本身免费**<br>- 依赖的底层服务按量计费：<br> ✓ 云监控（基础指标免费，自定义指标/高级告警可能收费）<br> ✓ SLS（日志写入/存储/检索）<br> ✓ Prometheus（实例规格与存储） |
| **典型场景** | - 自动化数据分析（读取 CSV → 清洗 → 建模 → 生成报告）<br>- 多步骤内容创作（调研→大纲→初稿→润色→配图）<br>- 企业级 RAG 编排（跨知识库检索+引用验证+摘要生成）<br>- 浏览器自动化测试/竞品监控 | - 微调后的 `qwen3.5-flash` 模型需部署至边缘设备（如车载终端）<br>- 在线客服大模型需降本增效，将 `MU16` 部署降至 `MU5`<br>- A/B 测试多个量化档位对业务指标（如回复准确率）的影响 | - 监控生产环境大模型 API 的 P95 延迟突增（排查性能退化）<br>- 设置“失败率 >3% 持续 5 分钟”告警，快速响应服务异常<br>- 分析某天 Token 消耗环比上涨 200%，定位异常调用方（爬虫 or Bug）<br>- 审计敏感 Prompt 是否被高频触发（合规审计） |

## 各方案适用场景建议

| 方案 | 推荐采用场景 | 不建议采用场景 | 关键决策提示 |
|------|--------------|----------------|--------------|
| **Agent Development** | ✅ 需要模型**主动规划、调用外部工具、处理文件、执行代码、维持会话状态**的复杂业务流程<br>✅ 任务具有**长时性、可中断性、沙箱隔离刚需**（如金融合规分析、科研计算）<br>✅ 团队希望复用技能（Skill）、编排多智能体协作、或对接 MCP 生态 | ❌ 简单问答、单次 prompt-to-response 场景（应直接调用 `/v1/chat/completions`）<br>❌ 对延迟极度敏感（如实时语音交互），且无法接受沙箱启动开销<br>❌ 无状态、无工具需求的轻量级 API 封装 | ▶️ 优先验证所选模型是否支持所需工具（如 `web_fetch`）及多模态输入<br>▶️ 生产环境务必配置 `tool_approval_policy` 并启用 Memory Store 防止状态丢失<br>▶️ 使用 CLI (`bl managed-agent apply`) 实现 IaC，提升环境一致性 |
| **Model Compression** | ✅ 已完成高质量微调，**需降低推理成本但无法接受显著精度下降**<br>✅ 部署目标为**资源受限环境**（如边缘节点、低成本容器集群）<br>✅ 正处于压测/灰度阶段，需快速对比不同量化档位效果 | ❌ 模型尚未微调完成，或使用的是基础模型/第三方模型<br>❌ 业务对精度极其敏感（如医疗诊断、法律文书生成），且未在自有测试集上充分验证量化效果<br>❌ 需要后续继续微调该模型（压缩后模型不可逆，不支持二次微调） | ▶️ **必须在华北2（北京）地域操作**，其他地域暂不支持<br>▶️ 免费期内务必运行多组压缩任务（不同模板 + 校准数据），用业务指标（非仅 loss）评估效果<br>▶️ 压缩后模型名后缀需体现量化策略（如 `w4a4`），便于追踪与回滚 |
| **Model Monitoring** | ✅ **所有线上模型服务均应启用**（基础用量统计 + 关键指标监控）<br>✅ 需要建立 SLO（如“P95 延迟 < 3s”，“失败率 < 0.5%”）并驱动运维闭环<br>✅ 合规强监管场景（需审计日志留存、Prompt 内容安全拦截分析）<br>✅ 成本中心需精细化管控 Token 消耗（设置 `TotalToken` 环比告警） | ❌ 本地开发调试阶段（可暂不开启，避免日志噪音）<br>❌ 仅用于离线批量推理且无 SLA 要求的实验性任务<br>❌ 期望用监控数据替代账单进行计费核对（监控数据不作为计费依据） | ▶️ **必开审计日志**（默认开启，零成本）；推理日志按需开启（注意 SLS 成本）<br>▶️ 优先配置 `失败率`、`首 Token 延时`、`TotalToken 数` 三大核心告警<br>▶️ 北京/新加坡以外地域暂不支持推理日志，需提前规划日志架构 |

## 面向开发者的选型参考总结

- **如果你在构建一个“能自己做事”的系统**（比如自动写周报、分析财报、订机票），请首选 **Agent Development** —— 它提供状态管理、工具生态和沙箱安全，是复杂智能体应用的基石。  
- **如果你已有一个训练好的模型，但发现部署太贵或太慢**，请立即评估 **Model Compression** —— 它是成本优化的“杠杆支点”，但务必在免费期内完成效果验证，且仅适用于百炼微调模型。  
- **如果你的模型已上线，却不知道它是否稳定、是否被滥用、是否在悄悄烧钱**，请立刻启用 **Model Monitoring** —— 它不是锦上添花，而是生产环境的“仪表盘”与“哨兵”，所有模型服务都应默认开启基础监控。

> ⚠️ **重要协同提醒**：三者可组合使用。例如：  
> - 用 **Model Compression** 优化 Agent 所用的 `qwen3.7-plus` 模型，降低其沙箱运行成本；  
> - 为 Agent 创建的每个 Session 所调用的底层模型，统一配置 **Model Monitoring** 告警，实现端到端可观测；  
> - 通过监控发现某 Agent 任务失败率飙升，结合推理日志快速定位是工具调用超时还是模型幻觉，再反向优化 Agent 提示词或工具配置。  

选择不是非此即彼，而是分层筑基：**Monitoring 是底线，Compression 是优化，Agent 是跃迁**。
