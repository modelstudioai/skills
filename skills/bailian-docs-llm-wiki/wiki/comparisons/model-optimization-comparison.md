# 模型微调 vs 模型压缩 vs [模型部署](../concepts/model-deployment.md)

在百炼平台上，将大模型从"通用能力"推进到"生产可用"通常涉及三个关键环节：**模型微调**（Fine-tuning）、**模型压缩**（Compression / Quantization）和**[模型部署](../concepts/model-deployment.md)**（Deployment）。三者并非互斥的替代方案，而是模型生命周期中各司其职的不同阶段。理解它们的定位、输入输出和计费差异，有助于开发者制定最优的技术选型路径。

## 核心定位对比

| 维度 | 模型微调 | 模型压缩 | [模型部署](../concepts/model-deployment.md) |
|------|---------|---------|---------|
| **核心目标** | 提升模型在特定领域/任务上的表现 | 降低模型显存占用，缩减部署成本 | 将模型上线为可调用的推理服务 |
| **输入** | 基础模型 + 标注数据（JSONL/ZIP） | 微调产出的全精度自定义模型 | 预置模型或微调/压缩产出的模型 |
| **输出** | 自定义微调模型 | 低精度量化模型 | 在线推理服务（API 端点） |
| **是否必需** | 可选——仅在 [Prompt 工程](../concepts/prompt-engineering.md)无法满足需求时使用 | 可选——仅在需要降低部署规格/成本时使用 | 必需——模型必须部署后才能对外提供服务 |

## 关键维度详细对比

| 维度 | 模型微调 | 模型压缩 | [模型部署](../concepts/model-deployment.md) |
|------|---------|---------|---------|
| **调优/处理方式** | CPT（持续预训练）、SFT（监督微调）、DPO（偏好优化）；各分全参和 LoRA 两种模式 | 量化（选择量化模板，可选校准数据） | 无处理，直接上线服务 |
| **支持的模型类型** | Qwen 文本生成、千问 VL、万相视频/图像、CosyVoice 语音 | 仅通过微调产出的全精度自定义模型（基础模型须在支持列表内） | 预置模型（Qwen、DeepSeek、GLM 等）、微调模型、压缩模型、OSS 导入的 LoRA 模型 |
| **数据要求** | SFT: 1000+ 条问答对；CPT: 1000 万+ Token 无标签文本；DPO: 100+ 组正负样本对 | 可选校准数据集（需为"已发布"状态的内部上传数据集） | 无数据要求 |
| **API 端点** | `POST /api/v1/fine-tunes`（创建任务）；`POST /api/v1/files`（上传数据） | 控制台操作 + OpenAPI 调用 | `POST /api/v1/deployments`（创建）；`GET /api/v1/deployments/<id>`（查询）；`DELETE /api/v1/deployments/<id>`（删除） |
| **计费方式** | 按训练数据 Token 总数 x 循环次数 x 训练单价（如 qwen3-8b: 0.006 元/千 Token） | 当前限时免费 | PTU（预置吞吐）：按天/小时预付费；MU（模型单元）：按时长 x 单元数；按 Token 用量：仅限 LoRA 模型 |
| **地域限制** | 仅华北2（北京） | 仅华北2（北京） | 仅华北2（北京） |
| **操作方式** | 控制台可视化 + API/命令行 | 控制台 + OpenAPI | 控制台 + API |
| **产出可逆性** | 可重新训练迭代 | 不可逆——产出模型不支持继续训练或二次压缩 | 可随时下线/删除，重新部署 |
| **耗时量级** | 分钟到小时级（视数据量和模型规模） | 分钟到小时级 | 分钟级（部署状态变为 RUNNING 即可用） |

## 典型工作流与依赖关系

三者在模型生命周期中存在明确的上下游关系：

1. **微调** 在最上游，将通用基础模型适配到特定业务场景
2. **压缩** 在中游，对微调产出的全精度模型做量化以降低部署成本
3. **部署** 在最下游，将模型上线为可被业务系统调用的推理服务

```
基础模型 ──[微调]──> 自定义模型 ──[压缩(可选)]──> 量化模型 ──[部署]──> 在线服务
                         │                                        ▲
                         └────────────[直接部署]───────────────────┘
```

## 适用场景建议

### 选择模型微调

- 通用模型在你的业务领域表现不佳，需要注入领域知识或学习特定输出格式
- 需要降低幻觉率或对齐特定偏好
- 拥有足量的高质量标注数据
- 需要对视觉理解、视频生成、图像生成或语音合成模型做场景定制

### 选择模型压缩

- 微调后的全精度[模型部署](../concepts/model-deployment.md)成本过高，需要降低显存占用
- 希望缩小部署单元规格（如从 MU1x2 降到 MU8x1）以节省推理费用
- 对模型精度的轻微损失可接受
- 基础模型在压缩支持列表内

### 选择[模型部署](../concepts/model-deployment.md)（直接部署预置模型）

- 预置模型已满足业务需求，无需微调
- 需要高并发、低延迟的资源专享推理服务
- 需要对吞吐量（TPM）、延迟等性能指标做精确控制
- 希望通过 PD 分离等高级特性优化首 Token 延迟

## 技术选型决策参考

1. **先评估预置模型 + [Prompt 工程](../concepts/prompt-engineering.md)**能否满足需求，若可以则直接部署预置模型，成本最低。
2. **若 [Prompt 工程](../concepts/prompt-engineering.md)不够**，进入微调流程。推荐先用 LoRA 高效训练快速验证效果，再考虑全参训练。
3. **微调完成后评估部署成本**：若全精度模型的部署规格过高，可通过压缩降低到更小的 MU 规格。
4. **选择部署计费模式**：流量稳定选 PTU（性价比高、有保障），流量波动大选 MU（灵活可控），仅做效果验证选按 Token 用量（不用不计费）。
