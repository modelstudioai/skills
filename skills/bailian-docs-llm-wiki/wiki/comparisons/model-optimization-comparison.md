# 模型微调 vs 模型压缩 vs 模型部署对比

百炼平台提供从模型定制到上线服务的完整链路，其中模型微调、模型压缩和模型部署是三个关键环节。开发者在实际项目中经常需要理解它们各自的定位、输入输出和适用条件，以便做出合理的技术选型。本文从多个维度系统对比这三项能力，帮助开发者快速定位所需功能。

## 核心定位对比

| 维度 | 模型微调（Fine-tuning） | 模型压缩（Model Compression） | 模型部署（Model Deployment） |
|------|------------------------|-------------------------------|------------------------------|
| **核心目标** | 提升模型在特定场景下的效果 | 降低模型推理资源占用 | 将模型上线为可调用的推理服务 |
| **输入** | 基础模型 + 训练数据集（JSONL/ZIP） | 自定义微调模型 | 预置模型或微调/压缩后模型 |
| **输出** | 定制化微调模型 | 低精度量化模型 | 在线推理服务（API 端点） |
| **是否需要数据** | 是（SFT 需 1000+ 条，CPT 需 1000万+ [Token](../concepts/token.md)） | 条件需要（校准数据，视量化模板而定） | 否 |
| **是否涉及 LLM 训练** | 是 | 否（仅量化转换） | 否（仅资源分配与服务化） |
| **耗时量级** | 数小时至数天（视数据量和模型规模） | 数十分钟至数小时 | 数分钟（资源就绪后即可调用） |

## 操作方式对比

| 维度 | 模型微调 | 模型压缩 | 模型部署 |
|------|---------|---------|---------|
| **控制台入口** | 模型训练 > 模型调优 | 模型训练 > 模型压缩 | 模型部署 |
| **API 端点** | POST /api/v1/fine-tunes | OpenAPI（控制台创建为主） | POST /api/v1/deployments |
| **支持模型范围** | Qwen3.6/3.5/3/2.5 系列、千问VL、Wan 图像/视频、CosyVoice | 仅部分基础模型的自定义微调产出（如 qwen3.5-flash） | 预置模型 + 微调模型 + 压缩模型 + 导入模型 |
| **关键配置项** | 训练方式、learning_rate、n_epochs、batch_size、lora_rank | 源模型、量化模板、校准数据 | [计费](../concepts/billing.md)方式（PTU/模型单元/[Token](../concepts/token.md)用量）、副本数、推理模式 |

## [计费](../concepts/billing.md)方式对比

| 维度 | 模型微调 | 模型压缩 | 模型部署 |
|------|---------|---------|---------|
| **[计费](../concepts/billing.md)模式** | 按训练 [Token](../concepts/token.md) 用量计费 | 当前限时免费 | PTU（保障吞吐）/ 模型单元（按时长）/ Token 用量（按调用） |
| **费用公式** | Token 总数 x 循环次数 x 单价 | 免费（压缩本身） | 视计费方式而定，部署即计费 |
| **费用量级参考** | 0.003~0.15 元/千Token（因模型而异） | 免费 | PTU 按 TPM 额度计费；模型单元 47~108 元/小时 |

## 流程关系与依赖

三者在百炼平台的模型生命周期中呈前后串联关系：

```
基础模型 → [微调] → 微调模型 → [压缩(可选)] → 量化模型 → [部署] → 在线服务
                                    ↓                              ↑
                              也可跳过压缩直接部署 ─────────────────┘
```

- 模型压缩的输入必须是微调产出的自定义模型，不支持直接压缩预置模型
- 压缩后的模型不可继续微调或二次压缩
- 部署是最终环节，接受微调模型、压缩模型或预置模型

## 适用场景建议

### 选择模型微调

- 模型在目标场景下效果不达标，需要注入领域知识或对齐特定风格
- 有高质量标注数据（至少 1000 条问答对）
- 希望模型学会特定工具调用、输出格式或安全策略

### 选择模型压缩

- 微调模型效果已满足需求，但部署成本过高
- 希望用更小规格的部署单元承载大模型（如从 MU1x2 降至 MU8x1）
- 对推理速度有更高要求，愿意接受轻微精度损失

### 选择模型部署

- 需要将模型上线为生产级 API 服务
- 有高并发、低延迟的业务需求，需要独享资源
- 需要灵活选择吞吐保障（PTU）、资源隔离（模型单元）或按量付费（Token 用量）

## 技术选型决策参考

| 决策问题 | 推荐方案 |
|---------|---------|
| 模型效果不够好，需要提升准确率 | 模型微调 |
| 模型效果已满足，部署成本太高 | 模型压缩 → 模型部署 |
| 快速验证微调效果 | 模型部署（Token 用量模式，不使用不计费） |
| 生产环境需要稳定吞吐保障 | 模型部署（PTU 模式） |
| 需要资源隔离和 PD 分离降低延迟 | 模型部署（模型单元模式） |
| 从零开始构建垂直领域模型 | CPT 微调 → SFT 微调 → 压缩(可选) → 部署 |
