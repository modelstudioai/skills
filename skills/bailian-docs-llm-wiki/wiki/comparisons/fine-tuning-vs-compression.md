# 微调与模型压缩对比

微调（Fine-tuning）和模型压缩（Model Compression）是百炼平台上两条面向定制化模型的能力路径：前者通过自有数据训练改变模型行为与能力，后者通过量化算法把已经微调好的全精度模型转换为低精度版本以降低部署成本。两者并非互斥——压缩是微调产出的下游环节，但在「目标、输入要求、产出物、计费方式、可逆性」等维度上差异显著，开发者做技术选型时常需要在「能力定制 vs 部署优化」之间权衡。本文从核心目标、输入输出、支持模型、操作方式、计费、典型场景等维度对比两者，帮助开发者快速判断该走哪条路径。

## 关键维度对比

| 维度 | 微调（Fine-tuning） | 模型压缩（Model Compression） |
| --- | --- | --- |
| 核心目标 | 基于自有数据定制模型能力，提升特定场景表现、抑制幻觉、对齐人类偏好 | 将全精度微调模型量化为低精度版本，降低显存占用与部署成本 |
| 输入要求 | 训练数据集（JSONL/ZIP，含问答对、偏好对、音视频等） | 已有的自定义微调模型 + 可选校准数据集 |
| 输出物 | 全精度或 LoRA 适配器形式的微调模型 | 低精度量化模型（带自定义后缀） |
| 支持模型 | Qwen3.6/3.5/3/2.5 文本、Qwen-VL 视觉、wan 图像/视频、CosyVoice 语音 | 当前主要为 qwen3.5-flash-2026-02-23 等支持压缩的基础模型对应的微调模型，列表以控制台为准 |
| 训练方法 | CPT / SFT / DPO，每种再分全参训练与高效训练（LoRA） | 量化算法，通过量化模板（含目标规格如 MU5/MU8）决定产出规格 |
| 操作入口 | 控制台「[模型调优](../concepts/fine-tuning.md)」页面，或 DashScope API（files / fine-tunes / deployments） | 控制台「模型训练 > 模型压缩」页面，或 OpenAPI |
| 关键超参 | learning_rate、n_epochs、batch_size、max_length、lora_rank | 任务名称、源模型、量化产出后缀、量化模板、校准数据（条件必填） |
| 任务状态 | 训练中 / 成功 / 失败等，可查询轮询 | 待开始 / 排队中 / 运行中 / 停止中 / 压缩成功 / 压缩失败 / 已取消；排队中/运行中可取消 |
| 可逆性 | 可迭代——可在已有产出上继续训练或更换数据重训 | 不可逆——产出模型不支持继续训练，也不支持二次压缩，迭代需回到上游全精度模型 |
| 计费方式 | 按 Token 用量计费：费用 = 训练数据 Token 总数 × 循环次数 × 训练单价 | 当前限时免费；产出模型部署后按部署单元规格计费 |
| 部署规格 | 取决于微调模式（全参 / LoRA）与模型本身，部署为在线服务后按规格计费 | 由所选量化模板决定（MU5、MU8 等），可部署到更小规格单元 |
| 数据格式 | SFT 用 ChatML-JSONL；DPO 增加 chosen/rejected；视觉/图像/视频/语音用 ZIP 打包 | 校准数据需为「数据管理」中「内部上传」且「已发布」的数据集；OpenAPI 可用 custom_calibration_file_ids |

## 各方案适用场景

### 推荐使用微调的场景

- 需要注入领域知识、改变模型回答风格或对齐人类偏好（CPT / SFT / DPO）。
- 客服、代码助手、Agent 工具调用等需要模型学会遵循特定指令格式的业务。
- 多模态定制：视觉理解、图像/视频生成风格定制、语音合成专属音色。
- 有足量高质量训练数据（SFT 1000+ 条问答对、DPO 100+ 组偏好对、CPT 1000万+ Token）。
- 期望可迭代——后续可基于新数据继续训练或换方法重训。

### 推荐使用模型压缩的场景

- 已有可用的全精度微调模型，希望降低推理显存与部署成本。
- 希望部署到更小规格单元（如从 MU1×2 降到 MU8×1）以提升吞吐。
- 对模型效果变化可接受——量化以牺牲少量精度换取部署效率。
- 不需要在产出模型上继续训练；如需迭代，愿意回到上游全精度模型重新微调后再压缩。

### 二者结合的典型链路

生产环境中常见的链路是 `微调（产出全精度模型）→ 模型压缩（产出低精度模型）→ 部署`：先用微调定制能力，再用压缩优化部署成本。需要注意压缩不可逆，迭代时必须回到全精度微调模型重新走压缩流程；同时压缩前后的部署规格由量化模板决定，需要在压缩阶段就规划好目标部署单元。

## 技术选型建议

- 若核心诉求是「让模型在特定业务上表现更好」 → 走微调。
- 若核心诉求是「已有模型太贵/太慢，想降本提速」 → 走模型压缩。
- 若两者都需要 → 先微调再压缩，但压缩只做一次，把迭代放在微调环节。
- 若模型不在压缩支持列表中 → 只能走微调，部署优化需通过规格选择或其它手段。
- 若数据量不足以微调（如 SFT 数据不足 1000 条） → 优先考虑压缩已有模型或使用 Prompt 工程，而非强行微调。
