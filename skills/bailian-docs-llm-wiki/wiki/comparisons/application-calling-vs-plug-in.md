# 应用调用与插件机制对比

为帮助开发者在百炼平台中合理选择能力集成方式，本文对三种核心扩展机制——**应用调用（Application Calling）**、**插件（Plug-in）** 和 **Skill** 进行系统性对比分析。三者虽均用于增强 AI 系统能力，但在设计定位、运行时角色、集成粒度及适用边界上存在本质差异。本对比聚焦实际工程落地中的关键决策维度，旨在为技术选型提供清晰、可操作的参考依据。

| 维度 | 应用调用（Application Calling） | 插件（Plug-in） | Skill |
|------|----------------------------------|------------------|--------|
| **本质定位** | **面向业务系统的端到端能力封装与交付接口**：将已发布的智能体/工作流应用作为黑盒服务供外部系统调用 | **面向模型推理过程的能力增强机制**：在单次 LLM 推理链路中，由模型自主触发外部工具调用，实现“思考-决策-执行”闭环 | **面向开发者的可复用逻辑单元封装机制**：将模型调用、工具链、分支逻辑等抽象为标准化、可编排、可版本化的组件 |
| **输入格式** | JSON 对象，结构由应用定义：<br>• 智能体应用：通常为 `{"query": "..."}`<br>• 工作流应用：严格匹配发布时配置的 `input_schema` | JSON 对象，必须显式包含 `tools`（数组，含 OpenAI-style function schema）和 `model`（指定支持插件的模型版本，如 `"qwen-max-v20240910"`） | JSON 对象，严格遵循 Skill 定义的 `input_schema`（JSON Schema 校验），支持类型约束、必填项、默认值等语义 |
| **输出格式** | JSON 对象，结构由应用定义，含 `output` 字段（业务结果）和 `usage`（token 统计）；支持流式 SSE 响应（`stream: true`） | 分阶段响应：<br>1. 首次响应含 `tool_calls`（模型生成的调用指令）；<br>2. 开发者执行后需二次提交 `tool_result`；<br>3. 最终返回完整 `content` 或 `function_call` 结果。<br>**不支持流式响应**（`tool_calls` 仅在 final chunk 出现） | JSON 对象，结构由 Skill 的 `output_schema` 声明；支持流式响应（若内部节点启用）；调用失败时返回标准错误码（如 `MODEL_NOT_FOUND`） |
| **支持模型** | **不限定具体模型**：应用底层可自由选用任意百炼托管模型（Qwen、Baichuan、GLM 等）或自定义模型；模型选择在应用构建阶段完成，调用方无感知 | **严格限定模型版本**：<br>• 仅 `qwen-plus`、`qwen-max`（v20240910+）、`qwen-turbo`（v20240910+）原生支持<br>• 旧版模型（如 `qwen-max-v20240610`）静默忽略插件参数 | **模型无关，但依赖节点能力**：<br>• Skill 内部节点（如 `llm_call`）可灵活配置模型；<br>• 工具调用（`tool_call`）节点要求所选模型支持 OpenAI-style tool spec；<br>• 兼容 Qwen1.5/2/2.5、Baichuan、GLM 等主流模型（需满足 [prompt](../guides/prompt.md) 工程兼容性） |
| **API 端点** | 统一端点：<br>`POST /v1/applications/{app_id}/call` | 复用标准聊天端点：<br>`POST /v1/chat/completions`（需携带 `tools`、`model` 等插件专用参数） | 两种调用路径：<br>• 直接调用：`POST /v1/skills/{skill_id}/invoke`<br>• 编排调用：在 Workflow 中通过 `skill_call` 节点引用 |
| **计费方式** | 按**调用次数 + 实际消耗 [Token](../concepts/token.md)** 计费：<br>• 每次 `/call` 请求计 1 次调用；<br>• `usage` 字段精确返回 input/output token 数，计入账户总配额 | 按**LLM 推理 [Token](../concepts/token.md) + 插件调用次数** 计费：<br>• 模型生成 `tool_calls` 的 token 计费；<br>• 每次成功执行的插件调用额外计费（按插件类型定价）；<br>• `tool_result` 提交不产生新 token 费用 | 按**Skill 执行耗时 + 内部资源消耗** 计费：<br>• 基础费用按 `timeout_ms` 占用时长阶梯计价；<br>• 内部 LLM 调用、工具调用等子操作单独计费并汇总至 Skill 总账单；<br>• 支持细粒度用量分摊（见控制台「用量管理」） |
| **典型场景** | • 客服对话系统对接 CRM<br>• 工单审批流嵌入 OA 系统<br>• 数据分析报告自动生成并推送邮件<br>• 多轮导购助手集成至电商 App | • 用户提问中隐含多步操作（如“查北京天气并推荐穿搭”）<br>• 需模型动态判断是否调用搜索/计算/数据库查询<br>• 构建具备实时信息获取能力的通用助手 | • 将“用户意图识别+实体抽取+知识库检索”打包为标准 NLU Skill<br>• 复用“合同条款比对逻辑”于多个风控工作流<br>• 封装“多源数据清洗→特征工程→模型预测”流水线供 BI 团队调用 |

## 各方案的适用场景建议

### ✅ 优先选择 **应用调用（Application Calling）** 当：
- 你已构建完成一个**功能完备、业务闭环的应用**（如客服机器人、报销审批流），需要将其作为稳定服务暴露给外部系统（如企业微信、ERP、小程序后端）；
- 调用方是**非 AI 系统**，不具备解析 `tool_calls` 或维护多轮对话状态的能力；
- 需要**强会话管理**（如 `session_id` 维护多轮上下文）或**复杂流程控制**（如工作流中的条件分支、人工审核、子流程嵌套）；
- 对**响应确定性、SLA 和可观测性**有明确要求（如 P99 延迟 < 2s，完整 usage 统计）。

### ✅ 优先选择 **插件（Plug-in）** 当：
- 你希望**赋予单次 LLM 推理以动态扩展能力**，且该能力需由模型根据用户输入**自主、即时决策是否调用**（如自动触发搜索、计算器、API）；
- 场景强调**低延迟、高灵活性**，无需预定义完整流程，而是让模型在“思考过程中”按需调用工具；
- 你正在构建**通用型助手产品**（如 Copilot 类应用），需支持用户自然语言中隐含的多样化操作意图；
- **不接受中间状态透出**，调用方只需最终答案，不参与工具执行环节。

### ✅ 优先选择 **Skill** 当：
- 你有一段**高频复用、逻辑稳定、需跨项目共享的 AI 子能力**（如“身份证OCR+信息校验”、“舆情情感分析+摘要生成”），希望统一维护、灰度发布、版本回滚；
- 你需要在**工作流（Workflow）中模块化编排**，将 Skill 作为原子节点与其他节点（LLM、条件判断、HTTP 调用）组合使用；
- 要求**强契约保障**：输入/输出结构通过 JSON Schema 严格定义，便于前端对接、类型安全检查与自动化测试；
- 团队协作中需**解耦能力开发与流程编排**，让算法工程师专注 Skill 实现，流程工程师专注 Workflow 设计。

## 技术选型参考指南（面向开发者）

| 你的需求 | 推荐方案 | 关键理由 |
|----------|-----------|-----------|
| “我有一个现成的 Python 函数（查库存），想让大模型在回答时自动调用它” | **插件（Plug-in）** | 插件机制专为此类“模型驱动的动态工具调用”设计，无需改造函数，只需提供 OpenAPI Schema 并注册即可被 `qwen-max-v20240910` 等模型识别。 |
| “我开发了一个客户投诉分类+工单创建的工作流，要嵌入到公司客服系统里” | **应用调用（Application Calling）** | 工作流应用天然支持多节点、异步等待、人工介入等企业级流程特性，且 `/call` 接口提供标准 HTTP 集成方式与完整 session 管理，适合系统间对接。 |
| “我们团队写了 5 个相似的‘用户画像生成’逻辑，分散在不同项目里，维护困难” | **Skill** | Skill 提供版本化、Schema 化、跨 Workflow 复用的能力封装，一次开发、多处引用，显著降低重复开发与不一致风险。 |
| “我要做一个能查股票、算数学、搜网页的 AI 助手，用户提问很自由” | **插件（Plug-in）** + **应用调用** | 基础助手能力用插件实现（模型自主调用）；若需结合企业知识库或定制化流程，则将插件能力封装进智能体应用，再通过应用调用对外暴露。 |
| “我的前端需要调用一个返回结构化 JSON 的接口（如 `{"status":"success","data":{...}}`），且必须类型安全” | **Skill** | Skill 的 `output_schema` 可强制约束输出结构，配合 API 调用方式（`/v1/skills/{id}/invoke`），确保前端获得可预测、可校验的响应体。 |

> **重要提醒**：三者并非互斥，而是构成百炼平台的**能力分层体系**：  
> - **插件** 是 *模型层* 的能力增强（What the model can do）；  
> - **Skill** 是 *能力层* 的复用封装（How to package a capability）；  
> - **应用调用** 是 *服务层* 的交付出口（How to expose it to users/systems）。  
> 实践中，常将插件能力注入 Skill 内部节点，再将 Skill 发布为工作流应用，最终通过应用调用供业务系统集成——形成端到端的 AI 能力交付链路。
