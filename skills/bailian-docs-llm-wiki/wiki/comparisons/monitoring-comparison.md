# 监控体系对比（应用监控 vs 模型监控）

阿里云百炼平台围绕"调用链路观测"提供两套互补能力：**应用监控（应用观测）**面向应用维度，追踪智能体/工作流/高代码应用内部的端到端调用链路；**模型监控**面向模型维度，围绕模型调用量与运行状态做稳定性保障与成本核算。两者观测对象、数据来源、指标口径均不同，但都基于业务空间维度组织数据，并在 Token、延时等关键指标上口径一致。本文面向开发者在稳定性、成本、调优等场景下做技术选型参考。

## 关键维度对比

| 维度 | 应用监控（应用观测） | 模型监控 |
| --- | --- | --- |
| 观测对象 | 应用：智能体应用、工作流应用、高代码应用 | 模型：按"模型 + 业务空间"维度生成列表 |
| 观测层级 | 应用内部端到端调用链路（CHAIN/Span 树） | 模型调用入口指标，不含应用内部编排 |
| 调用来源 | 通过控制台添加"被观测的应用"后自动追踪 Prompt 及数据 | 系统自动采集主账号下所有业务空间内的模型调用数据 |
| 数据更新频率 | 分钟级 | 普通监控为小时级；高级监控为分钟级 |
| 数据保留 | 调用记录最长可查 30 天 | 调用统计可查最近 30 天；更早数据需到费用与成本页查询 |
| 触发方式 | 主动添加应用后追踪；"关闭观测"即停止 | 自动采集，无需手动添加模型 |
| 支持应用/模型范围 | 不支持 Assistant API 创建的智能体应用；高代码应用仅能观测到入口 CHAIN 节点，不支持追踪其内部链路 | 普通监控支持所有地域所有模型（含调优后自定义模型）；高级监控支持北京/新加坡/弗吉尼亚；告警仅北京/新加坡 |
| 关键指标 | 调用次数（含失败次数/失败率）、Token 总量（全部/输入/输出）、平均单次请求 Token、平均首 Token 耗时、平均调用时长 | 模型总量、总调用次数、总失败次数、平均调用时长、平均首包时长；详情页含安全/成本/性能/错误四类指标（RPM、TPM、429 限流、内容安全错误等） |
| 调用记录字段 | Prompt 内容、输出、延时、调用时间、Token 量；支持按 Request ID / Trace ID / Span ID 检索 | 实时推理调用记录含"请求和响应"（输入/输出）、"用量"（Token 消耗）；需开通推理日志 |
| 日志/历史对话 | 无独立日志页签，调用记录在 Trace 列表查看 | 仅适用于华北2（北京）地域部分模型；需开通审计日志与推理日志 |
| 数据导出 | 支持 JSONL / EXCEL 导出 | 未提供独立导出入口，可通过 Grafana / Prometheus HTTP API 取数 |
| 数据标注 | 支持 Span 标签（布尔/分类/数字/文本），与应用评测标签统一管理 | 不提供数据标注能力 |
| 接入评测集 | 支持 Span 数据直接加入评测集（含字段映射，单评测集最多 50 字段） | 不直接接入评测集 |
| API 能力 | 无 API，仅控制台操作 | 高级监控指标存储于私有 Prometheus 实例，支持标准 Prometheus HTTP API，可接入 Grafana 或自建应用 |
| 主动告警 | 无告警能力 | 支持创建告警规则（北京/新加坡），通知方式含短信/邮件/电话/钉钉/企业微信/Webhook；告警等级紧急/错误/警告/普通 |
| [计费](../concepts/billing.md)方式 | 应用观测功能本身不收费；数据存储在可观测链路 OpenTelemetry 服务，存储费由 OpenTelemetry 收取 | 模型用量按业务空间汇总[计费](../concepts/billing.md)用量（Token/张/秒）；监控功能本身不另收费 |
| 前提条件 | 需开通应用观测配置：授权 OpenTelemetry 服务角色 → 开通 OpenTelemetry 服务 → 初始化 LogStore | 普通监控默认可用；高级监控/告警/日志需在"模型监控配置"中手动开通 |
| 权限要求 | 子账号需 `AliyunBailianFullAccess` + 应用观测操作/管理员页面权限 + `ram:CreateServiceLinkedRole` | 默认业务空间成员可查看所有业务空间；子业务空间成员仅能查看当前空间 |
| [计费](../concepts/billing.md)统计口径 | Token = LLM 节点输入+输出；Embedding 节点为向量化 Token 数 | 大语言/全模态/向量模型按 Token；图像生成按张；视频生成按秒；语音模型按秒/字符/Token |

## 适用场景建议

### 选应用监控（应用观测）

- 需要追踪**应用内部编排链路**：智能体应用的检索、改写、向量、重排、LLM、插件、绿网等节点调用关系与嵌套。
- 需要**排查应用级故障**：通过 Trace ID / Span ID 定位某次应用调用中具体哪个节点出错、延时分布、Token 消耗。
- 需要把**真实线上调用回流为评测样本**：将 Span 数据加入评测集做回归。
- 需要**对调用数据打标签**做人工审计或分类筛选。
- 适用对象为智能体应用、工作流应用（含完整节点链路）或仅需入口观测的高代码应用。

### 选模型监控

- 关心**模型维度的稳定性与成本**：失败率、429 限流、内容安全错误、首包/调用时长趋势、RPM/TPM。
- 需要**主动告警**：Token 消耗突增、超时、失败率升高等静默失败（北京/新加坡地域）。
- 需要**跨应用、跨业务空间**查看某个模型的统一调用量与费用。
- 需要**接入 Grafana 或自建运维系统**：通过 Prometheus HTTP API 取高级监控指标。
- 需要**内容审计**：查看请求与响应原文（北京地域部分模型，需开通推理日志）。

### 两者结合

应用负责"编排"，模型负责"原子能力"。在生产环境建议同时启用：应用监控定位"哪次调用、哪个节点"出了问题，模型监控定位"哪个模型、哪类错误"在上升，并依靠告警实现分钟级发现。Token 口径在两者中一致（输入+输出），可交叉对账。
