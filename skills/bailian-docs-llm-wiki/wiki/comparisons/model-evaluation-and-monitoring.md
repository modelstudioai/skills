# 模型评估与监控能力对比

为帮助开发者清晰区分百炼平台中面向不同目标的评测与观测能力，本文对四类核心能力进行系统性对比：**模型评测（Model Evaluation）**、**模型监控（Model Monitoring）**、**应用评测（Application Evaluation）** 和 **应用监控（Application Monitoring）**。这些能力虽均服务于模型生命周期的质量保障，但在设计目标、技术边界、数据来源及适用阶段上存在本质差异。本对比旨在消除概念混淆，支撑精准技术选型——例如：在模型上线前验证“它答得对不对”，应选评测类能力；在服务运行中判断“它是否稳、快、可用”，则需监控类能力。

---

## 关键维度对比

| 维度 | 模型评测<br>`/v1/evaluations` | 模型监控<br>`/api/v1/monitor/metrics` | 应用评测<br>`/v1/evaluation-jobs` | 应用监控<br>`/v1/monitoring/metrics` |
|------|-------------------------------|----------------------------------------|-------------------------------------|----------------------------------------|
| **核心目标** | 量化模型**静态能力**：在标准任务下“答得准不准、好不好” | 追踪模型服务**运行时状态**：在真实流量下“调得稳不稳、快不快、错不错” | 评估**端到端应用效果**：含提示工程、RAG、工具调用等组合逻辑的输出质量与稳定性 | 观测**生产级应用链路**：覆盖 API 网关、路由、后处理等全链路性能与异常 |
| **输入格式** | JSONL 数据集（每行含 `input` + `reference` 字段），需提前上传校验 | 仅需 `model_id`（如 `"qwen-max-20240601"`）+ 时间范围参数（如 `last_24h`） | CSV/JSONL 评测集（支持 `input` + `expected_output` + `metadata`）；或直接传入 `app_id` 调用在线服务 | ISO8601 时间范围（`start_time`/`end_time`）+ 可选多维分组（`model_id`, `app_id`, `status_code`） |
| **输出格式** | 结构化评测报告（JSON）：含各指标聚合值（如 `rouge-l: 0.72`）、样本级明细、失败原因分析、可视化图表链接 | 时序指标数据（JSON）：按粒度（`1m`/`5m`）返回 `qps`, `latency_p99`, `error_rate_5xx` 等原始数值序列 | 自动评测：JSON 报告（含 `accuracy`, `safety_score`, `latency_ms` 等多维得分）；人工评测：标注结果导出 CSV/Excel | 多维聚合指标（JSON）：支持按 `model_id`/`app_id` 下钻的 `qps`, `latency_p95`, `error_rate_4xx` 等，含时间序列与统计摘要 |
| **支持模型** | 所有已部署并启用推理服务的 LLM（Qwen 系列、第三方模型），需兼容 OpenAI 或百炼 Native 接口 | 仅限通过百炼控制台部署的 **API 模型服务** 及 **显式开启可观测性的工作流节点** | 已发布为可调用服务的应用（HTTP endpoint 或 SDK 封装），包括 RAG、Agent、微调模型等复杂应用 | 所有通过百炼 API 网关发布的模型服务（含 `qwen-max`, 自定义微调模型, RAG 应用），**默认启用，无需配置** |
| **API 端点** | `POST /v1/evaluations` | `GET /api/v1/monitor/metrics` | `POST /v1/evaluation-jobs` | `GET /v1/monitoring/metrics` |
| **计费方式** | 按**评测样本数 × 模型数 × 指标计算复杂度**计费（自定义指标额外加权）；免费额度限每月 1000 样本 | **不单独计费**，计入模型服务基础用量包；无额外调用成本 | 按**评测样本数 × 并发数 × 应用调用次数**计费（自动评测）；人工评测按标注人天计费 | **不单独计费**，作为 API 网关标配能力，包含在模型服务订阅费用中 |
| **典型场景** | • 模型选型：对比 `qwen-max` vs `qwen-plus` 在金融问答数据集上的 ROUGE-L 分数<br>• 提示优化：同一模型下 A/B 测试不同 system [prompt](../guides/prompt.md) 的 factuality 得分<br>• 效果归因：定位某次迭代后 EM 下降是否源于 reference 格式变更 | • 实时巡检：发现 `qwen-plus` P99 延迟突增至 8s，触发告警<br>• 容量规划：分析过去 7 天 QPS 峰值与增长趋势<br>• 版本对比：比较 `qwen-max-v1` 与 `v2` 的 5xx 错误率差异 | • RAG 应用验收：用 500 条客户咨询样本评测召回准确率与答案简洁性<br>• Agent 安全审计：批量检测工具调用结果中的 PII 泄露风险<br>• 提示词 AB 测试：对比两个 workflow 版本的用户满意度（人工标注） | • 全链路排障：发现 `app-rag-customer` 的高延迟源于向向量库发起的子请求超时<br>• 多租户分析：按 `app_id` 分组查看各业务线的错误率分布<br>• SLA 追踪：导出近 30 天 `latency_p95 < 3s` 达标率报表 |

## 各方案适用场景建议

| 场景描述 | 推荐能力 | 理由说明 |
|----------|-----------|-----------|
| **模型研发阶段**：需在上线前验证新微调模型在专业领域测试集上的事实一致性、指令遵循能力 | ✅ 模型评测 | 直接对接模型原生接口，支持深度指标（如 Self-Check GPT、FactScore），提供归因分析，是模型能力基线确认的黄金标准 |
| **模型灰度发布期**：需实时观察新版本在小流量下的错误率、延迟波动，快速回滚异常版本 | ✅ 应用监控 | 覆盖 API 网关层，能捕获路由失败、鉴权拒绝等非模型内部错误；支持秒级指标下钻，定位 `app-id` 粒度问题 |
| **工作流节点调试**：需诊断某个 RAG 工作流中“检索节点”响应慢，但不确定是模型还是向量库导致 | ✅ 模型监控 + 应用监控 联合使用 | 模型监控聚焦节点自身（如 `node_id=rag-retriever` 的 P99 延迟）；应用监控可关联其上游调用（如 `app_id=workflow-x` 的子请求耗时），实现跨层级根因分析 |
| **客户交付验收**：需向客户证明某智能客服应用在 1000 条真实对话样本上达到 92% 准确率，并附人工复核报告 | ✅ 应用评测（自动+人工混合） | 支持混合评测模式：先用自动指标快速筛选，再对低分样本启动专家人工标注，生成符合交付要求的结构化报告 |
| **日常运维巡检**：SRE 团队需每日检查所有生产模型服务的健康水位，对延迟 >5s 或错误率 >1% 的服务自动告警 | ✅ 应用监控（主） + 模型监控（辅） | 应用监控提供统一入口、多维分组和标准化告警策略；模型监控可作为补充，用于验证工作流节点级指标是否与网关层一致（如排查埋点偏差） |

## 技术选型参考（面向开发者）

- **优先选择「模型评测」当且仅当**：  
  ✅ 你拥有标准测试集（含高质量 `reference`）且关注**绝对性能上限**；  
  ✅ 你需要横向对比多个模型在相同任务下的能力排序；  
  ❌ 不适用于监控线上服务稳定性，也不支持对未部署模型的离线评估。

- **优先选择「应用评测」当且仅当**：  
  ✅ 你的服务是封装后的应用（含 RAG/Agent/多步逻辑），且 `reference` 难以定义（如开放域摘要）；  
  ✅ 你需要评估端到端体验（如响应时长、安全性、用户满意度），而非纯模型能力；  
  ❌ 不适用于纯 API 性能压测，也不提供模型内部 token 级别分析。

- **优先选择「应用监控」当且仅当**：  
  ✅ 服务已通过百炼 API 网关发布，你关注**生产环境真实流量下的 SLA**；  
  ✅ 你需要多维下钻（如按 `app_id` + `status_code` 分析错误分布）或导出原始数据做 BI 分析；  
  ✅ 你依赖钉钉/邮件等通道接收实时告警；  
  ❌ 不适用于本地调试环境或未接入网关的服务。

- **优先选择「模型监控」当且仅当**：  
  ✅ 你管理的是**原子化模型服务**（非组合应用），且需精确追踪工作流中每个节点的独立表现；  
  ✅ 你需要与百炼工作流深度集成（如基于节点延迟自动扩缩容）；  
  ❌ 不支持跨地域指标聚合，且无法观测 API 网关层的网络错误（如 499 Client Closed）。

> **关键决策树**：  
> ① 问题是否发生在**上线前**？→ 是 → 选 **模型评测** 或 **应用评测**（取决于是否封装为应用）；  
> ② 问题是否发生在**上线后真实流量中**？→ 是 → 选 **应用监控**（首选）；若需深入工作流节点 → 补充 **模型监控**；  
> ③ 是否需人工介入判断主观质量？→ 是 → 必选 **应用评测** 的人工模式；  
> ④ 是否需对比多个模型的理论能力？→ 是 → 必选 **模型评测**。  

通过明确区分“评测”（*What should it do?*）与“监控”（*What is it doing?*），以及“模型”（*Atomic capability*）与“应用”（*Composed service*），开发者可避免能力误用，构建高效、可信的大模型质量保障体系。
