# 模型部署方式对比：高并发推理、模型压缩与模型监控

本页旨在帮助开发者在百炼平台进行模型生产化部署时，清晰区分**高并发推理（性能加速）**、**模型压缩（轻量化部署）** 与**模型监控（可观测运维）** 三类核心能力的定位、能力边界与适用条件。三者并非互斥方案，而是面向模型生命周期不同阶段（部署前优化 → 运行时保障 → 运行后治理）的正交技术栈。正确理解其差异，可避免选型错配（如用模型压缩解决容量瓶颈，或依赖监控替代性能加固），提升系统稳定性、成本效率与迭代速度。

---

## 关键维度对比表

| 维度 | 高并发推理（Prime / 吞吐预留） | 模型压缩（INT4 量化） | 模型监控（可观测性） |
|------|-------------------------------|------------------------|------------------------|
| **核心目标** | 提升服务吞吐量（TPS）、降低延迟、保障 SLA 确定性 | 减小模型体积、降低显存占用、加速单次推理、适配边缘/低成本实例 | 实现调用链路可观测、异常快速定位、用量精细化分析与风险预警 |
| **作用阶段** | 模型**运行时（Inference Serving）** 的资源调度与执行优化 | 模型**部署前（Model Deployment）** 的静态结构优化（量化/剪枝） | 模型**运行中及运行后（Runtime & Post-Run）** 的数据采集与分析 |
| **输入格式** | 标准 OpenAI 兼容 API 请求（`model`, `messages`, `stream` 等）；需指定特定 model ID 或专属 model code | 已发布的模型版本（`model_id` + `version_id`），通过 `/v1/models/{id}/versions/{v}/deploy` 接口提交 `compression` 配置对象 | 无主动输入；自动采集所有经百炼网关的合法 API 调用（含 Prompt/Response，若开启推理日志） |
| **输出格式** | 与标准 API 完全一致（JSON 响应或 SSE 流式响应）；Prime 模式额外返回 `delta.reasoning_content` 字段 | 部署成功后生成新 `deployment_id`；返回 `compression_status: "completed"` 及量化误差指标（如 `max_activation_error`） | 多维可视化图表（控制台）、结构化日志（SLS/Prometheus）、告警通知（短信/邮件/钉钉）、用量报表（CSV/Excel 导出） |
| **支持模型** | • Prime：`glm-5.3-prime`, `glm-5.2-fast-preview`, `wan3.0-video-prime` 等专用 ID<br>• 吞吐预留：Qwen/GLM/DeepSeek/Kimi 等主流系列（不含 `-fast-preview` 等 Prime 专用后缀） | 仅 Qwen 系列（Qwen1.5/Qwen2/Qwen2.5/Qwen-VL）的 FP16 发布版本；不支持 LoRA 未合并模型 | 所有在控制台「模型列表」可见的已发布模型（含调优模型）；语音/图片/视频/三方直连类模型部分功能受限 |
| **API 端点** | 与标准兼容模式一致：<br>`https://{workspace_id}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/chat/completions`<br>（仅需替换 `model` 参数） | 非独立端点，集成于部署接口：<br>`POST /v1/models/{model_id}/versions/{version_id}/deploy` | 非调用型能力；数据通过控制台页面、OpenAPI（`/v1/monitoring/*`, `/v1/usage/*`）或日志服务（SLS）获取 |
| **计费方式** | • Prime：按实际输入/输出 token 计费（同标准 API）<br>• 吞吐预留：预付费（kTPM 容量包）+ 溢出按量计费（token） | **不产生额外计费**；压缩本身免费；但部署后运行仍按标准 token 计费；所选实例类型（如 a10/a100）影响资源成本 | **基础监控免费**；审计日志投递、推理日志投递、Prometheus 数据投递等高级能力需消耗对应云产品资源（SLS 写入/存储、云监控配额等） |
| **典型场景** | • AI 编程助手实时补全<br>• Agent 多步串行推理链路<br>• 大促期间对话服务刚性容量保障<br>• 对首 [Token](../concepts/token.md) 延迟敏感的交互应用 | • 边缘设备（Jetson/ARM 服务器）部署<br>• 高并发低延迟场景下降低 GPU 显存压力（如千卡集群推理）<br>• 快速验证模型轻量化效果（A/B 测试） | • 生产环境 SLA 异常归因（失败率突增/延迟毛刺）<br>• 成本治理（识别低效 API-Key / 高 [Token](../concepts/token.md) 消耗模型）<br>• 模型性能退化追踪（周级延迟趋势分析）<br>• 合规审计（完整请求/响应留存） |

## 各方案适用场景建议

### ✅ 推荐选择「高并发推理」当：
- 业务流量**可预测且峰谷比高**（如工作日 9–18 点集中访问），需保障高峰期确定性响应；
- 对**首 [Token](../concepts/token.md) 延迟（TTFT）或端到端延迟（E2E Latency）有明确 SLA 要求**（如 <800ms）；
- 当前使用标准 API 出现**频繁限流（HTTP 429）或排队延迟**，且扩容公共池资源不可控；
- 需要**分钟级容量弹性**（吞吐预留支持叠加扩容），而非长期固定资源。

> ⚠️ 注意：Prime 模式适用于“微调提速”，吞吐预留适用于“刚性保底”；二者不可叠加，且模型 ID 严格隔离。

### ✅ 推荐选择「模型压缩」当：
- 目标部署环境**GPU 显存受限**（如 A10 卡部署 7B 模型需 >20GB，INT4 可降至 ~6GB）；
- 业务对**单次推理延迟极度敏感**（如实时语音转写后处理），且能接受轻微质量折损（需 A/B 测试验证）；
- 需在**边缘侧或客户私有云**部署轻量模型，降低带宽与硬件成本；
- 正在进行模型选型验证，需快速对比同一模型不同精度下的性能/质量权衡。

> ⚠️ 注意：压缩为一次性操作，不支持热更新；INT4 激活压缩可能影响长文本/数学推理质量，务必在业务场景下实测。

### ✅ 推荐选择「模型监控」当：
- 模型已上线生产，但缺乏**故障快速定位能力**（如无法区分是模型崩了、网络抖动还是上游超时）；
- 需要**精细化成本分摊**（按 API-Key / 模型 / 时间维度统计 Token 消耗）；
- 存在**合规或审计要求**，需留存完整请求/响应日志（需手动开启推理日志并配置 SLS 投递）；
- 计划实施**模型迭代治理**（如识别低调用量模型、监控新版模型质量衰减）。

> ⚠️ 注意：监控数据延迟存在（图表分钟级，用量报表约 1 小时）；告警仅支持预置指标，非所有监控项均可配置。

## 开发者技术选型参考指南

| 你的问题 | 推荐方案 | 关键判断依据 | 行动建议 |
|----------|-----------|----------------|------------|
| “我们的对话服务在晚高峰大量超时，用户投诉增多” | ✅ 高并发推理（吞吐预留） | 问题本质是**容量不足导致排队/限流**，属资源层瓶颈 | 在控制台开通吞吐预留，按历史峰值 120% 预留 kTPM；启用「自动溢出」防服务中断；监控「超额降级率」 |
| “想在 24GB 显存的 A10 服务器上跑 Qwen2-7B，但 OOM 了” | ✅ 模型压缩（`int4_weight_only`） | 问题本质是**显存超限**，属模型结构层约束 | 使用 `model.deploy` 接口对已发布 Qwen2-7B 版本发起 INT4 权重压缩；部署后验证 TTFT 与生成质量是否达标 |
| “上线新模型一周后，发现平均延迟上升了 30%，但不知道原因” | ✅ 模型监控（分钟级延迟趋势 + 告警） | 问题本质是**性能退化需归因**，属可观测性缺失 | 在监控详情页查看「调用时长」分钟级曲线；关联「失败率」「限流次数」排查干扰因素；配置「连续5分钟平均延迟 > 1200ms」告警 |
| “需要把模型部署到客户现场的 ARM 服务器上” | ✅ 模型压缩 + 高并发推理（可选） | 边缘部署需**体积小 + 延迟稳**，双重要求 | 先压缩为 INT4；再根据现场流量特征决定是否启用 Prime（若客户环境可控且流量平稳） |
| “每天被业务方追问‘今天用了多少 Token？哪个团队最耗？’” | ✅ 模型监控（用量统计 + API-Key 筛选） | 问题本质是**成本透明化需求**，属运营分析范畴 | 在「模型用量」页按 API-Key 和时间范围导出报表；设置「单日 TotalToken > 1000 万」用量告警 |

> 💡 **终极原则**：  
> - **性能瓶颈 → 查资源（高并发推理）**  
> - **资源瓶颈 → 查模型（模型压缩）**  
> - **认知瓶颈 → 查数据（模型监控）**  
> 三者协同使用效果最佳：用监控发现瓶颈 → 用高并发/压缩针对性解决 → 用监控验证改进效果。
