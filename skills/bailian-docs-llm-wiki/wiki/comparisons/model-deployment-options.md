# 模型部署方式对比：高并发推理、模型压缩与模型监控

为帮助开发者在百炼平台构建稳定、高效、可观测的 AI 生产服务，本文对三种关键部署支撑能力——**高并发推理（含 Prime 模式与吞吐预留）**、**模型压缩（后训练量化）** 和 **模型监控（生产级可观测性）** 进行系统性对比分析。三者定位不同：高并发推理聚焦**性能交付保障**，模型压缩侧重**资源与成本优化**，模型监控则提供**运行态健康治理能力**。本对比不替代各功能独立文档，而是从技术选型视角提炼核心差异，辅助开发者在架构设计阶段做出合理决策。

---

## 关键维度对比表

| 维度 | 高并发推理（Prime 模式） | 高并发推理（吞吐预留） | 模型压缩 | 模型监控 |
|------|--------------------------|--------------------------|-----------|------------|
| **核心目标** | 提升单请求响应速度与共享资源池下的整体 TPS | 保障业务高峰期确定性容量与 SLA（TPM 刚性兑付） | 降低模型部署规格（MU）与推理成本，平衡精度与效率 | 实现生产环境模型调用的实时可观测、可诊断、可告警 |
| **输入格式** | 标准 OpenAI 兼容 API 请求体（含 `model`、`messages`、`stream` 等），`model` 值为预置 Prime ID（如 `glm-5.2-fast-preview`） | 同左，但 `model` 必须替换为控制台生成的专属 `model code`（非原始模型名） | 微调完成且状态为 `SUCCEEDED` 的自定义模型（仅支持百炼内训模型） | 无显式“输入”；自动采集所有通过百炼 API 发起的有效调用（含标准/兼容模式） |
| **输出格式** | 与标准 API 完全一致；流式响应中新增 `delta.reasoning_content` 字段用于分离思考过程与最终输出 | 同左；高速模式下响应结构与 Prime 一致，但延迟更稳定 | 输出为新模型实例（ID 后缀自动追加，如 `my-qwen-ft-v1-int4`），可直接用于部署 | 多维数据视图：用量统计（[Token](../concepts/token.md)/图像/视频等）、实时指标（首 [Token](../concepts/token.md) 延时、失败率等）、审计日志（Request ID/状态码/耗时）、告警通知 |
| **支持模型** | 预置 Prime 专用模型 ID（如 `qwen3.8-max-prime`、`wan3.0-video-prime`），不支持任意模型切换 | 所有主流基础模型（如 `Qwen3.8-Max`、`GLM-5.2`、`DeepSeek-v4-Pro`）+ 吞吐预留实例，需控制台创建 | 仅限百炼平台内完成微调并成功发布的**自定义模型**（如 `qwen3.5-flash-2026-02-23`），不支持基础模型或第三方模型 |
| **API 端点** | `https://{workspace_id}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`（工作空间专属域名） | `https://dashscope.aliyuncs.com/compatible-mode/v1`（或同区域兼容域名），需使用专属 `model code` | 无独立 API；通过控制台发起任务，产出模型后仍走标准部署/调用链路 | 无调用端点；全部能力通过控制台页面（用量、监控、告警）及 SLS/Prometheus 投递接口访问 |
| **计费方式** | 按实际消耗 token 计费（输入/输出/缓存命中均计费），无额外加速费用 | **预付费**：按 kTPM·天（输入/输出分开计价）；**溢出部分**：按 token 计费（若启用自动溢出） | 压缩任务本身限时免费；压缩后模型部署按 MU 规格单独计费（通常比原模型低 30%~60%） | 监控数据采集与展示**免费**；开启 SLS 日志投递或 Prometheus 监控投递将产生对应云产品费用 |
| **典型场景** | AI 编程助手实时补全、轻量级对话机器人、Agent 单步快速决策等对首 [Token](../concepts/token.md) 延迟敏感、流量波动平缓的场景 | 电商大促客服机器人、金融风控实时审批、企业级知识库高负载问答等需 SLA 保障、流量可预测的稳态高并发场景 | 微调后模型上线前的轻量化改造，尤其适用于预算受限、对推理延迟容忍度较高、需长期稳定运行的中长尾业务场景 | 所有已上线模型的日常运维：成本异常排查、P99 延迟突增归因、429 限流根因分析、安全合规审计、服务健康度日报生成 |

## 适用场景建议（面向开发者的技术选型参考）

| 场景特征 | 推荐方案 | 关键理由 | 注意事项 |
|----------|----------|----------|----------|
| **需要毫秒级首 Token 响应，但流量峰谷明显、无法预估峰值** | ✅ Prime 模式 | 共享资源池弹性好，无需预购、开箱即用，TPS 提升 1.5~2 倍且不改变模型能力 | 不保障容量刚性；超限后行为由平台动态调度，不适合对 SLA 有合同级要求的场景 |
| **业务有明确 QPS/TPM 上限，且高峰期必须零抖动、零降级** | ✅ 吞吐预留（高速模式） | 独占 TPM 容量，刚性兑付；高速模式叠加后 TPS 提升 1.5~2 倍，彻底规避公共限流影响 | 需提前购买、按自然日计费（非 24 小时）；务必开启自动续费防中断；首次使用需关注预热期延迟波动 |
| **微调模型部署成本过高（如需 MU16），希望降低规格而不显著牺牲效果** | ✅ 模型压缩 | 通过 INT4/INT8 量化显著降低 MU 需求（如 MU16 → MU4），推理成本下降明显；精度损失可控且可验证 | 仅支持百炼内训模型；不可逆（无法再微调）；需用业务测试集充分验证效果；仅华北2可用 |
| **模型已上线，但缺乏对调用量、失败率、延迟分布的感知，常被动响应故障** | ✅ 模型监控 | 分钟级延迟的全链路指标（首 Token 延时、失败率、429 次数等），支持一键配置告警，审计日志可追溯 Request ID | 推理日志需手动开启并投递至 SLS；用量数据延迟约 1 小时，不作为计费依据；需结合费用中心账单做成本闭环分析 |
| **同时存在高并发 + 成本敏感 + 运维复杂问题** | ⚙️ **组合使用**：<br>• 吞吐预留保障容量<br>• 模型压缩降低 MU 规格<br>• 模型监控驱动持续优化 | 三者正交：吞吐预留解决“能不能扛住”，模型压缩解决“扛得省不省”，模型监控解决“扛得稳不稳” | 需分阶段实施：先压缩验证效果 → 再预留容量 → 最后配置监控告警；注意吞吐预留的 `model code` 与压缩后模型 ID 是两个独立概念，可叠加使用 |

> 💡 **选型口诀**：  
> - 要“快”？→ 优先看 **Prime 模式**（轻量、免配置）；要“稳”？→ 必选 **吞吐预留**（刚性、可承诺）。  
> - 要“省”？→ 检查是否已完成微调 → 是，则启动 **模型压缩**；否，则暂不适用。  
> - 要“管”？→ **模型监控** 是所有上线模型的必备基础设施，无例外场景。
