# 模型部署方式对比：高并发推理、模型压缩与模型生产部署

本页旨在帮助开发者清晰区分百炼平台中三类关键模型部署能力：**高并发推理（含 Prime 模式与吞吐预留）**、**模型压缩** 和 **模型生产部署（Model Production）**。三者定位不同——高并发推理聚焦 *已有模型的运行时性能保障*，模型压缩专注 *自定义模型的轻量化降本*，而模型生产部署则覆盖 *从模型资产构建到服务上线的全生命周期管理*。理解其边界、能力交集与技术约束，是实现高效、稳定、经济的 AI 服务落地的前提。

---

## 关键维度对比表

| 维度 | 高并发推理（Prime 模式 & 吞吐预留） | 模型压缩 | 模型生产部署（Model Production） |
|------|-------------------------------------|-----------|----------------------------------|
| **核心目标** | 提升推理吞吐量、降低延迟，保障服务稳定性 | 减少模型显存占用与计算开销，降低部署成本 | 将训练/导入/压缩后的模型转化为可管理、可扩展、可计费的在线服务 |
| **输入格式** | 标准 OpenAI 兼容请求体（`messages`, `model`, `stream` 等）；`model` 参数需为特定 ID（Prime 模型名 或 吞吐预留专属 code） | 百炼平台内已成功微调的自定义模型（状态为 `SUCCEEDED`）；校准数据需为已“发布”的数据集 | 模型标识符（`model_name`），来源包括：微调产出、OSS 导入、压缩生成、或官方基础模型名 |
| **输出格式** | 与标准 API 完全一致（JSON 响应或 SSE 流式响应）；Prime 模式额外支持 `delta.reasoning_content` 字段 | 生成新模型 ID（如 `my-qwen-ft-001-w4a4`），不改变推理接口格式；输出为模型元数据与部署就绪状态 | 返回部署实例 ID（`deployment_id`）、服务端点（`endpoint`）、状态（`RUNNING`/`FAILED`）等；最终调用仍通过标准 `/chat/completions` 等接口 |
| **支持模型** | • Prime：限定 Prime 专属模型（如 `glm-5.2-fast-preview`, `qwen3.8-max-prime`）<br>• 吞吐预留：主流基础模型（Qwen/GLM/DeepSeek/Kimi 等）的官方版本（如 `Qwen3.8-Max`, `GLM-5.2`） | 仅限百炼平台内完成且状态为 `SUCCEEDED` 的**自定义微调模型**（如 `qwen3.5-flash-2026-02-23`）；不支持基础模型或第三方模型 | • 微调模型：全部支持<br>• 导入模型：支持 OSS 导入的 `full`/`lora` 模型<br>• 压缩模型：支持自身压缩产出<br>• 基础模型：支持官方模型（但 `ptu` 方案仅限基础模型） |
| **API 端点** | 与标准兼容模式一致：<br>`https://{workspace_id}.{region}.maas.aliyuncs.com/compatible-mode/v1/chat/completions` | 控制台为主；API 路径为 `/api/v1/fine-tunes/compress/jobs`（创建任务）及 `/api/v1/fine-tunes/compress/templates`（获取模板） | 主要为 `/api/v1/deployments`（部署）、`/api/v1/fine-tunes`（微调）、`/api/v1/custom_models/import`（导入）等生产类 API；均限定华北2（北京）地域 |
| **计费方式** | • Prime：**纯按 token 计费**，无预付费，与标准 API 同价<br>• 吞吐预留：**预付费模式（按天结算）**，预留容量内免费，超额按策略处理（降级或拒绝） | • 压缩任务：限时免费（以控制台公告为准）<br>• 部署后：按所选 MU 规格单独计费（与是否压缩无关） | • `mu`/`lora` 部署：按 MU 单位或 [Token](../concepts/token.md) 实时计费<br>• `ptu`（吞吐预留）：按预留 kTPM 容量预付费<br>• 微调/导入：按训练时长或模型大小计费 |
| **资源隔离性** | • Prime：**无隔离**，共享公共资源池，依赖平台剩余算力<br>• 吞吐预留：**强隔离**，锁定专属 TPM 容量，规避公共限流 | 不涉及运行时资源分配；压缩后模型部署时才绑定 MU 规格 | • `mu`：专属 MU 资源，完全隔离<br>• `lora`：共享底层资源，按 [Token](../concepts/token.md) 分摊计费<br>• `ptu`：专属吞吐配额，逻辑隔离 |
| **典型场景** | • Prime：AI 编程助手实时补全、Agent 多步推理链、低延迟对话交互<br>• 吞吐预留：大促期间客服机器人、高 SLA 要求的金融问答、流量可预测的 SaaS 接口 | 自定义微调模型上线前的轻量化优化，例如：将 7B 全参模型压缩至 W4A4，使单卡部署成本下降 40%+，适用于中小客户私有化部署或边缘场景 | • 企业定制知识库问答模型上线<br>• 第三方 LoRA 模型快速接入并对外提供 API<br>• 视频生成服务从训练到生产环境一键发布 |

## 各方案适用场景建议

| 方案 | 推荐使用场景 | 不推荐场景 | 关键决策提示 |
|------|--------------|-------------|----------------|
| **Prime 模式** | ✅ 流量波动大、对首字延迟敏感、预算有限、无需刚性容量保障的通用增强场景（如内部工具、实验性产品）<br>✅ 快速验证某模型在高速推理下的表现（无需申请资源） | ❌ 对可用性 SLA 有严格要求（如 99.95%）<br>❌ 需要长期稳定高吞吐（如每分钟稳定 50k tokens） | ▶️ 优先尝试 Prime，成本零增加；若实测延迟抖动超预期，再升级至吞吐预留。 |
| **吞吐预留** | ✅ 流量可预测、有明确峰值需求、需规避公共限流风险的核心业务（如电商搜索问答、银行智能投顾）<br>✅ 需要确定性响应时间（P99 < 800ms）的 B2B 接口 | ❌ 小流量长尾应用（预留成本远高于实际消耗）<br>❌ 模型尚未完成 A/B 测试，稳定性待验证 | ▶️ 必须使用专属 model code；务必预估 `input_tpm`/`output_tpm` 并设置合理 `overflow_strategy`；建议搭配客户端重试与排队机制。 |
| **模型压缩** | ✅ 已完成微调且确认效果达标，需降低部署规格（如从 MU5 → MU2）以节省成本<br>✅ 边缘/本地化部署场景，对显存和启动时间敏感 | ❌ 模型仍在迭代调优阶段（压缩不可逆，无法继续微调）<br>❌ 未进行充分精度验证即上线（必须用业务测试集验证 W4A4/W8A8 效果） | ▶️ 仅限华北2；务必在免费期内多模板对比 + 校准数据验证；压缩后模型名需带后缀，避免与原模型混淆。 |
| **模型生产部署（`mu`/`lora`/`ptu`）** | ✅ 全流程自主可控：从微调→压缩→部署→扩缩容闭环管理<br>✅ [多模态](../concepts/multi-modal.md)模型统一纳管（文本/图像/视频/语音）<br>✅ 需要灰度发布、版本回滚、资源弹性伸缩的企业级运维 | ❌ 仅需调用现成基础模型（直接用标准 API 或吞吐预留更简单）<br>❌ 无自定义模型需求，仅做简单 Prompt 工程 | ▶️ `ptu` 仅支持基础模型；`mu` 是唯一支持 CosyVoice 语音模型的方案；图像/视频生成强制 `lora`；所有生产 API 仅在北京地域可用。 |

## 技术选型参考（面向开发者）

请按以下路径进行技术决策：

1. **先问“我有没有自己的模型？”**  
   - **否** → 直接使用 **高并发推理（Prime 或吞吐预留）**，跳过压缩与生产部署。  
     - 流量小/实验期 → 选 **Prime**；  
     - 流量大/高 SLA → 选 **吞吐预留**。  
   - **是**（自定义微调/导入模型） → 进入下一步。

2. **再问“是否需要降低成本或适配硬件限制？”**  
   - **是** → 在部署前执行 **模型压缩**（仅限微调模型，华北2），验证精度后生成新模型 ID。  
   - **否** → 直接进入部署环节。

3. **最后问“如何上线这个模型？”**  
   - 需要专属资源、最高隔离性、支持语音 → 选 **`mu` 部署**；  
   - 图像/视频生成、或希望按 [Token](../concepts/token.md) 灵活计费 → 选 **`lora` 部署**；  
   - 模型是官方基础模型（非自定义），且需固定吞吐保障 → 用 **`ptu`（即吞吐预留）**，但注意：**此 `ptu` 与高并发推理中的“吞吐预留”本质相同，只是调用入口不同（生产 API vs 兼容 API）**。

> 💡 **关键提醒**：  
> - **功能正交性**：Prime 模式与吞吐预留互斥（模型 ID 不同）；模型压缩与吞吐预留无依赖关系（压缩后模型仍可走 `mu`/`lora` 部署，但不可用于 `ptu`）；  
> - **地域一致性**：所有操作（微调、压缩、部署、吞吐预留）若通过 API 执行，**必须统一使用华北2（北京）地域**；控制台操作会自动匹配工作空间地域；  
> - **命名即契约**：`model` 参数值决定行为——`glm-5.2-fast-preview` 触发 Prime，`tpm-reserved-xxx` 触发吞吐预留，`my-model-w4a4` 是压缩产物，`my-model-mu-001` 是 `mu` 部署实例——请严格按文档命名规范使用。  

如需进一步实践指导，请查阅对应模块的 [快速入门](raw/model-user-guide/getting-started.md) 或调试常见问题（如：[吞吐预留 429 错误排查](raw/model-user-guide/model-high-speed-inference/tpm-reservation.md#troubleshooting)、[压缩精度下降分析](raw/model-user-guide/model-compression/model-compression-introduction.md#accuracy-fall)）。
