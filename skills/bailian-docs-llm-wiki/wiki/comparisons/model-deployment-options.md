# 模型部署方案对比：高并发推理、模型压缩、模型监控

## 背景与目的  
在百炼平台构建生产级 AI 应用时，开发者需在**性能、成本、稳定性与可观测性**之间进行系统性权衡。高并发推理方案聚焦于服务吞吐与延迟优化；模型压缩方案面向资源效率与部署成本控制；模型监控方案则保障服务健康度与问题可追溯性。三者并非互斥，而是模型上线全生命周期中不同阶段的关键能力模块。本页旨在为开发者提供清晰、结构化的横向对比，辅助技术选型决策——明确“什么场景该用什么能力”“哪些能力可组合使用”“哪些限制必须提前规避”。

## 关键维度对比表

| 维度 | 高并发推理（Model High-Speed Inference） | 模型压缩（Model Compression） | 模型监控（Model Monitoring） |
|------|------------------------------------------|------------------------------|------------------------------|
| **核心目标** | 提升请求处理能力（TPS/QPS）、降低端到端延迟（P95/P99）、保障服务确定性 | 降低推理资源占用（MU 规格）、减少显存/内存开销、降低单位 Token 推理成本 | 实现调用链路可观测：用量统计、性能诊断、失败归因、异常告警 |
| **输入格式** | 标准 OpenAI 兼容请求体（JSON），含 `model`、`messages`、`stream` 等字段；部分模式需特定 `model` ID 或 code | 控制台表单输入：任务名称、量化后缀、源微调模型、量化模板、可选校准数据集 | 无主动输入；自动采集所有 API 调用的请求头、响应头、Token 用量、耗时、状态码等元数据 |
| **输出格式** | 标准 OpenAI 兼容响应（流式/非流式），部分模式扩展字段（如 `delta.reasoning_content`） | 新生成的压缩模型（唯一 model code），不可逆，不支持继续微调或二次压缩 | 多维图表（监控概览）、结构化表格（用量统计）、告警通知（短信/邮件/钉钉）、原始日志（SLS 投递） |
| **支持模型** | • Prime 模式：`glm-5.2-fast-preview`、`glm-5.3-prime`、`wan3.0-video-prime` 等专用模型<br>• 吞吐预留/PTU/DTU：Qwen3.x、GLM-5.x、DeepSeek-v4.x、Kimi-K2.6 等主流文本/视频模型<br>• 智能路由：`qwen3.8-max`、`qwen3.7-flash`、`deepseek-v4-pro-0813` 等预设模型池<br>• 批量推理：`qwen3.8-max`、`qwen3.7-plus`、`qwen3-vl-plus` 等 | **仅限百炼平台内完成的微调模型（Custom Fine-tuned Models）**，当前明确支持 `qwen3.5-flash-2026-02-23`、`qwen3.6-plus-2026-04-02` 等 Qwen 系列；不支持基础模型、第三方模型、OSS 导入模型 | **全量支持**：所有百炼控制台「模型列表」中可选模型（LLM、视觉、语音、视频、向量模型）<br>⚠️ 高级监控（首 Token 延时、缓存命中率、告警）对语音/图片/视频/三方直连类模型存在功能限制 |
| **API 端点** | • Prime / 吞吐预留 / 智能路由：`https://{workspace_id}.{region}.maas.aliyuncs.com/compatible-mode/v1`<br>• PTU/DTU 专属部署：`https://dashscope.aliyuncs.com/api/v1`<br>• 批量推理：异步提交接口（`/v1/batches`）+ 结果轮询 | **无 API 端点**：纯控制台操作（模型中心 → 模型压缩 → 创建任务）；压缩结果作为新模型自动注册至模型中心 | **无调用型 API**：数据通过控制台访问（用量统计、监控概览、告警配置、日志查看）；支持 SLS/Prometheus 数据投递（需额外授权） |
| **计费方式** | • Prime 模式：按标准模型单价计费（无额外费用）<br>• 吞吐预留：按预留 TPM 容量月度包年/包月付费<br>• PTU/DTU：按预置吞吐（PTU）或独占吞吐（DTU）规格计费；Token 按量仅限 LoRA 微调模型<br>• 批量推理：约实时推理成本的 50% | **压缩任务本身限时免费**（以控制台公告为准）；**部署压缩模型仍按 MU 规格正常计费**（但相同效果下 MU 规格更低 → 实际成本下降） | **监控与告警功能完全免费**；但开启日志投递（至 SLS）或监控数据投递（至 Prometheus）将产生对应云产品费用 |
| **典型场景** | • 秒级响应要求的 C 端应用（如客服机器人、实时翻译）<br>• 大促期间流量洪峰保障（如电商推荐、营销文案生成）<br>• 多模型动态选优（如 A/B 测试、效果兜底）<br>• 非实时批量任务降本（如日报生成、内容审核） | • 微调模型已验证效果，需规模化部署但受限于 GPU 显存/预算<br>• 边缘侧或轻量容器环境部署（如低配云服务器、本地私有化）<br>• 在保持业务指标前提下压降推理成本（如千次调用成本降低 30%+） | • 快速定位线上故障（如某模型 P99 延时突增、失败率飙升）<br>• 成本精细化运营（按模型/API-Key/时间维度分析 Token 消耗）<br>• 合规审计与调用溯源（完整 Request/Response 日志留存）<br>• 自动化运维（失败率 >1% 自动触发告警与工单） |

## 适用场景建议（面向开发者的技术选型参考）

| 场景描述 | 推荐方案 | 关键理由与组合提示 |
|----------|----------|---------------------|
| **需要毫秒级首 Token 响应，且流量稳定可预测**（如金融风控问答、车载语音助手） | ✅ **Prime 模式 + 吞吐预留** | Prime 提供底层调度加速（TPS↑1.5~2×），吞吐预留锁定资源避免排队；二者叠加可兼顾速度与确定性。注意：需选用 `*-prime` 模型 ID，并申请对应地域的 TPM 预留。 |
| **业务模型效果已达标，但单次推理成本过高，GPU 显存成为瓶颈**（如企业知识库问答服务，日均百万次调用） | ✅ **模型压缩 → PTU/DTU 专属部署** | 先对微调模型做 W8A8 量化，显著降低 MU 规格需求；再以 PTU/DTU 方式部署，获得资源隔离与成本锁定优势。⚠️ 压缩不可逆，务必在免费期内多模板对比精度损失。 |
| **多模型并行服务，需根据请求内容智能分发，同时保障 SLA**（如内容平台：短文本走轻量模型，长文档走大模型） | ✅ **智能路由 + 吞吐预留（为关键备选模型）** | 智能路由实现语义感知的模型自动匹配；为路由池中核心模型（如 `qwen3.8-max`）配置吞吐预留，避免因某模型过载拖累整体路由成功率。注意：仅北京/新加坡可用，且必须使用 OpenAI 兼容协议。 |
| **非实时批量任务，追求极致成本效益**（如每日 10 万条用户评论情感分析） | ✅ **批量推理（Batch）** | 成本约为实时推理 50%，支持 256K 上下文；适合离线 ETL、报告生成等场景。注意：需构造 JSONL 文件提交，不支持流式响应。 |
| **刚上线新模型，需快速建立基线监控并防范风险**（如灰度发布期间） | ✅ **模型监控（全量开启） + 告警配置** | 立即启用审计日志 + 首 Token 延时/失败率告警；结合用量统计分析 Token 分布，及时发现 Prompt 泄露或恶意刷量。无需代码改造，控制台 5 分钟完成配置。 |
| **混合架构：既有高并发实时接口，又有后台批量任务，还需长期成本审计** | ✅ **组合方案：**<br>• 实时层：`Prime 模式`（主） + `吞吐预留`（兜底）<br>• 批量层：`Batch 推理`<br>• 成本层：`模型监控用量统计` + `自定义告警`（如 TotalToken 突增）<br>• 优化层：对高频调用的微调模型执行 `模型压缩` → `DTU 部署` | 百炼平台能力天然支持分层治理：高并发方案保体验，监控方案保稳定，压缩方案保成本。所有能力共享同一模型中心与计费体系，运维界面统一。 |

## 重要限制与避坑指南（开发者必读）

- **地域强约束**：  
  - 吞吐预留、PTU/DTU、智能路由、批量推理、模型监控（推理日志）**仅支持华北2（北京）与新加坡**；  
  - 模型压缩**仅支持华北2（北京）**；跨地域部署需同步规划资源。

- **协议与接口兼容性**：  
  - 智能路由**仅支持 OpenAI 兼容 `/v1/chat/completions` 接口**，不支持 DashScope 原生协议、`/v1/embeddings`、Anthropic 协议等；  
  - 模型压缩产出模型**不支持继续微调或二次压缩**，请确保微调效果已充分验证后再启动压缩任务。

- **参数与行为冲突预警**：  
  - `thinking_budget` 参数在 PTU/DTU 部署中**不生效**，仅在标准 API 或 Prime 模式下配合 `enable_thinking=true` 使用；  
  - 智能路由中 `response_format` 和 `max_tokens` 会参与路由决策，若备选模型不支持将导致请求被拒绝；  
  - 开启推理日志**必须先开启审计日志投递**，且关闭审计日志投递将自动停用推理日志。

- **数据时效性认知**：  
  - 用量统计延迟约 **1 小时**（用于财务对账）；  
  - 监控指标延迟为**分钟级**（用于实时运维）；  
  - 告警历史在 2026 年 9 月 3 日后需通过云监控控制台查询。

- **成本优化黄金实践**：  
  - 高并发场景优先用 `Prime`（零成本加速）→ 再评估是否需 `吞吐预留`（确定性保障）；  
  - 批量任务默认选 `Batch`，勿用实时接口模拟；  
  - 监控本身免费，但**是成本优化的前提**：通过用量统计识别高消耗模型，再针对性压缩或替换。

> 💡 **一句话选型口诀**：  
> **要快？选 Prime 或吞吐预留；要省？先压缩再 PTU/DTU；要稳？监控告警必须开；要全？Batch + 智能路由组合用。**
