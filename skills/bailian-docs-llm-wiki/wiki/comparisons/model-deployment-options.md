# [模型部署](../concepts/model-deployment.md)方式对比：高并发推理、微调与压缩

本文旨在帮助开发者清晰理解百炼平台上三种核心[模型部署](../concepts/model-deployment.md)能力——**高并发推理（含吞吐预留与Prime模式）**、**微调（Fine-tuning）** 和 **模型压缩（Compression）** 的技术定位、能力边界与适用阶段。三者并非互斥选项，而是构成「模型生产—优化—交付」全链路的关键环节：  
- **微调** 是模型能力定制的起点，解决「模型是否懂业务」的问题；  
- **模型压缩** 是微调后的可选提效步骤，解决「定制模型能否低成本、低延迟上线」的问题；  
- **高并发推理** 是面向线上服务的部署形态，解决「定制/基础模型能否稳定支撑业务流量」的问题。  

正确区分三者的输入输出、生命周期、计费逻辑与技术约束，是避免资源浪费、缩短上线周期、保障服务 SLA 的前提。

---

## 关键维度对比表

| 维度 | 高并发推理（吞吐预留 + Prime 模式） | 微调（Fine-tuning） | 模型压缩（Compression） |
|------|-----------------------------------|---------------------|--------------------------|
| **本质目标** | 保障推理服务的**稳定性、低延迟与高吞吐** | 提升模型在**特定任务/领域下的效果与对齐度** | 降低已训练模型的**部署资源消耗与推理成本** |
| **输入格式** | 标准 API 请求（`messages` 或 `prompt` 等）；吞吐预留需专属 `model code`，Prime 需指定 `model ID` + 专用域名 | 训练数据集（JSONL/XLSX/纯文本等，格式强约束）+ 超参数配置 | 已成功完成微调的**全精度自定义模型**（状态为 `SUCCEEDED`）+ 可选校准数据集 |
| **输出格式** | 标准推理响应（含 `choices`, `usage`, `cached_tokens` 等字段）；Prime 模式额外支持 `reasoning_content` 流式解析 | 一个**全新部署的模型实例**（拥有独立 model ID，如 `ft-qwen3-8b-20240510-abc123`） | 一个**量化后的新模型**（ID 为源模型名 + 后缀，如 `my-ft-model-awq`），不可逆 |
| **支持模型** | • 吞吐预留：Qwen3.x、GLM-5.x、DeepSeek-v4、Kimi-K2.6 等主流基础/微调模型（地域绑定）<br>• Prime：仅 `glm-5.2-fast-preview`, `glm-5.3-prime`, `wan3.0-video-prime` 等有限型号 | • 文本生成：Qwen、GLM、DeepSeek 全系列（支持 CPT/SFT/DPO/RL）<br>• 多模态：Qwen-VL（SFT）、万相图像/视频（SFT-LoRA）、CosyVoice（SFT）<br>• **不支持基础模型直接微调**（必须基于百炼平台训练） | • **仅支持百炼平台产出的微调模型**（状态 `SUCCEEDED`）<br>• 不支持基础模型、第三方模型、未完成训练的 checkpoint |
| **API 端点** | • 吞吐预留：通用 dashscope 域名（`dashscope.aliyuncs.com`），`model` 字段填专属 code<br>• Prime：**专属接入域名**（如 `{workspace_id}.cn-beijing.maas.aliyuncs.com`），`model` 填固定 ID | • 控制台 GUI 入口（`/cn-beijing/model/tuning`）<br>• API：`POST /api/v1/fine-tunes`（需先上传数据获取 `file_id`）<br>• RL/OPD：必须使用 DashScope SDK Python 接口 | • 控制台入口：左侧导航栏 → **模型压缩** → 创建任务<br>• **暂无开放 API**，全部通过控制台操作完成 |
| **计费方式** | • 吞吐预留：**预付费**（按 kTPM 输入/输出容量包购买，预留内调用免费）<br>• Prime：**纯按 token 计费**（与预留无关，费用不互通） | • 控制台：支持按 [Token](../concepts/token.md)、训练单元（MTU）预付费/后付费<br>• API 方式：**仅支持按 [Token](../concepts/token.md) 计费** | • 压缩任务本身：**限时免费**（以控制台公告为准）<br>• 压缩后[模型部署](../concepts/model-deployment.md)：按实际使用的 **MU 规格单独计费**（与压缩过程无关） |
| **典型场景** | • 秒级响应要求的客服对话、实时搜索摘要<br>• 大促期间流量洪峰保障（如电商商品推荐）<br>• 对 P99 延迟和抖动敏感的 SaaS 服务 | • 客服知识库问答准确率不足（需 SFT 对齐业务语料）<br>• 生成内容存在幻觉或指令遵循差（需 DPO/RL 对齐偏好）<br>• 需要模型理解专有视觉文档（Qwen-VL SFT） | • 微调模型部署成本过高（如 MU1×2 → MU8×1 可降本 56%）<br>• 需要在边缘设备或轻量容器中运行定制模型<br>• 推理延迟受显存带宽限制，需加速访存 |
| **生命周期管理** | • 吞吐预留：到期后 2 小时内仍可用，14 小时后释放，`model code` 失效<br>• Prime：无有效期，账号有效即可持续调用 | • 训练任务：`RUNNING`/`PENDING` 可取消；终态（`SUCCEEDED`/`FAILED`）可删除记录<br>• 产出模型：长期存在，可随时用于推理或压缩 | • 压缩任务：`PENDING`/`RUNNING` 可停止（不可恢复）；终态可删除（不影响已产出模型）<br>• 产出模型：**不可继续微调、不可二次压缩、不可修改**（必须回退上游重训） |
| **地域限制** | 严格按地域隔离（华北2、新加坡等），model code / model ID 不跨地域通用 | 绝大多数功能仅支持 **华北2（北京）**；部分文本 SFT 支持多地域 | 仅 **华北2（北京）** 可用 |
| **技术路径关键区别** | • 吞吐预留「高速模式」= PTU 专属实例（硬件隔离）<br>• Prime = 共享资源池内性能增强通道（软件调度优化） | • CPT：更新底层语言建模能力<br>• SFT：对齐指令与领域知识<br>• DPO/RL：对齐人类偏好与价值观 | • 当前仅支持 **后训练量化（PTQ）**（如 AWQ、GPTQ）<br>• 不支持剪枝、蒸馏、稀疏化等其他压缩范式 |

## 适用场景建议（面向开发者的技术选型参考）

### ✅ 选择「高并发推理」当且仅当：
- 你已有**可用模型**（基础模型或已微调模型），且当前推理服务出现以下问题之一：  
  ▪️ P99 延迟 > 2s，无法满足用户体验阈值；  
  ▪️ 流量波动大，按量调用频繁触发限流（429）；  
  ▪️ 业务有确定性 SLA 要求（如“99.95% 请求 < 800ms”）。  
- **决策提示**：优先评估「吞吐预留」——若预算可控、流量可预测，它提供最强确定性；若追求极致性价比且能接受共享资源调度，再评估 Prime 模式（注意：Prime 模型列表极窄，切勿强行迁移非支持模型）。

### ✅ 选择「微调」当且仅当：
- 你已尝试 Prompt 工程、RAG 等轻量方案，但模型在**关键业务指标上仍不达标**：  
  ▪️ 客服场景意图识别准确率 < 85%；  
  ▪️ 金融报告生成中事实错误率 > 12%；  
  ▪️ 代码生成任务中工具调用失败率高。  
- **决策提示**：严格遵循 `CPT → SFT → DPO → RL` 链路（RL 为可选终局）；图像/语音类任务务必确认模型类型与支持的训练方式（如万相仅支持 SFT-LoRA）；所有数据格式必须提前校验（JSONL 行格式、XLSX 评测集结构）。

### ✅ 选择「模型压缩」当且仅当：
- 你已完成微调并验证效果达标，但**部署成本或延迟成为瓶颈**：  
  ▪️ 微调模型需 MU1×2 规格，月成本超预算 40%；  
  ▪️ 在线服务平均延迟达 1.5s，其中 60% 由显存带宽占用导致；  
  ▪️ 需将模型部署至资源受限环境（如 Kubernetes 边缘节点）。  
- **决策提示**：压缩是**单向、不可逆操作**，务必在免费期内对同一微调模型尝试 ≥2 种量化模板，并用**真实业务测试集**验证精度损失（建议监控关键字段准确率、BLEU-4、人工评分等）；切勿压缩后直接上线。

### ⚠️ 常见误用警示（避坑指南）
| 错误行为 | 风险 | 正确做法 |
|----------|------|-----------|
| 用 Prime 模式的 `glm-5.2-fast-preview` model ID 去调用吞吐预留专属 endpoint | 请求失败（404 或 400） | Prime 必须使用专属域名；吞吐预留必须用控制台生成的 `tpm-reserved-xxx` code |
| 对未完成微调的基础模型（如 `qwen3-8b`）直接发起压缩任务 | 控制台无源模型可选，任务创建失败 | 压缩**仅接受状态为 `SUCCEEDED` 的微调产出模型** |
| 在吞吐预留中启用「高速模式」后，仍使用通用 dashscope 域名调用 | 性能不提升，仍走标准路由 | 高速模式无需改域名，但必须使用专属 `model code` |
| 微调任务使用 API 方式提交，却选择「训练单元预付费」计费方式 | 请求被拒绝（API 仅支持按 [Token](../concepts/token.md) 计费） | API 创建任务时，`billing_type` 必须设为 `"token"` |
| 压缩后模型尝试再次微调或叠加压缩 | 控制台禁止操作，API 返回 400 错误 | 如需调整，必须回到上游全精度微调模型重新训练 |

## 总结：构建稳健模型服务的推荐路径

1. **效果优先**：从 Prompt 工程/RAG 开始验证；效果不足 → 进入微调；  
2. **定制落地**：完成微调并验证业务指标达标 → 获得专属模型 ID；  
3. **成本优化（可选）**：若部署规格/成本过高 → 在华北2发起模型压缩 → 获得量化模型；  
4. **服务交付**：将最终模型（原始微调版或压缩版）接入高并发推理体系：  
   - 流量平稳、SLA 要求严苛 → 选用**吞吐预留**（推荐组合：预留 + 高速模式）；  
   - 流量弹性大、预算敏感、模型在 Prime 支持列表内 → 选用**Prime 模式**；  
   - 初期验证或低负载场景 → 直接使用**按量推理**（无需额外配置）。  

> 技术选型没有银弹。请始终以**业务指标（准确率、延迟、成本）为唯一标尺**，结合各方案的硬性约束（地域、模型支持、格式要求、不可逆性）做决策。百炼平台的设计哲学是：让效果优化与工程交付解耦，使团队可并行推进算法迭代与服务治理。
