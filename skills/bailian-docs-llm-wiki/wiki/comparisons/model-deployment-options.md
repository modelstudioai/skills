# 模型部署方式对比：高并发推理、模型压缩与模型监控

本页旨在帮助开发者在百炼平台进行模型生产化部署时，清晰区分**高并发推理（Model High Speed Inference）**、**模型压缩（Model Compression）** 和 **模型监控（Model Monitoring）** 三类核心能力的定位、技术边界与协同关系。三者并非互斥方案，而是模型生命周期中不同阶段的关键支撑能力：  
- **高并发推理**聚焦 *运行时性能保障*，解决“如何稳定承载高负载、低延迟请求”；  
- **模型压缩**聚焦 *部署前模型优化*，解决“如何以更小资源开销实现可接受精度的推理”；  
- **模型监控**聚焦 *运行后可观测性*，解决“如何持续感知服务健康度、发现性能退化与异常”。  

正确理解三者的差异与组合逻辑，是构建高可用、低成本、可运维大模型服务的基础。

## 关键维度对比表

| 维度 | 高并发推理（High Speed Inference） | 模型压缩（Model Compression） | 模型监控（Model Monitoring） |
|------|-----------------------------------|------------------------------|-----------------------------|
| **核心目标** | 保障低延迟（P99 < 150ms）、高吞吐（TPM 可控）的稳定推理体验 | 降低模型推理资源占用（MU 规格）与部署成本，容忍可控精度损失 | 实时采集并分析模型调用行为与性能指标，支撑诊断、容量规划与告警 |
| **作用阶段** | 模型部署阶段（创建/更新服务时启用） | 模型部署前阶段（微调完成后、部署前执行） | 模型运行阶段（服务上线后自动生效，全程覆盖） |
| **输入格式** | 推理服务配置参数（JSON），含 `high_speed_inference`, `mode`, `tpm` 或 `instance_type` | 微调完成的模型 ID、量化模板、可选校准数据集（已发布数据集） | 查询参数（`model_id`, `start_time`, `end_time`, `granularity`）或控制台交互操作 |
| **输出格式** | 部署成功的高速推理服务（具备独立 endpoint），返回标准推理响应（非流式） | 一个全新的、已量化的模型 ID（如 `my-qwen-ft-quant`），可直接用于后续部署 | 时间序列指标数据（JSON API 响应）或控制台可视化图表（延迟分布、错误率、用量趋势等） |
| **支持模型** | 仅限 Qwen 系列（Qwen2/Qwen2.5/Qwen3）及部分 Llama3 定制版；仅 `chat` 类型模型 | 仅限百炼平台内完成且状态为 `SUCCEEDED` 的微调模型（`fine-tuned`）；当前仅华北2（北京）地域支持 Qwen3.5/Qwen3.6 等指定版本 | 全量支持：百炼托管模型（`qwen-max`, `qwen-plus` 等） + 用户自部署模型（需接入 Telemetry Agent v2.3+） |
| **API 端点** | 无独立端点；复用标准推理 endpoint（如 `/v1/services/{service_id}/call`），请求自动路由至高速通道 | 无实时推理端点；通过 `POST /v1/model-compression/tasks` 创建任务，异步生成新模型 | `GET /v1/monitoring/metrics`（指标查询）；告警配置通过控制台或 `POST /v1/alert-rules` |
| **计费方式** | 按实际使用的 GPU 实例规格（Prime）或预留 TPM 配额（TPM Reservation）计费；费用高于标准推理 | **压缩任务本身限时免费**；但压缩后模型部署时，按其所需 MU 规格单独计费（通常低于原模型） | 监控数据采集与存储免费；告警通知（钉钉/邮件）免费；无额外用量费用 |
| **典型场景** | 实时对话机器人（客服/游戏NPC）、搜索关键词实时补全、金融交易风控决策、A/B 测试流量隔离通道 | 微调后的业务专属模型需降本上线（如移动端/边缘侧轻量部署）、灰度发布前多版本精度-成本权衡验证 | 服务上线后日常巡检、突发流量导致延迟飙升的根因定位、月度用量分析与预算预测、模型性能漂移预警 |

## 各方案适用场景建议

### ✅ 推荐使用「高并发推理」当：
- 业务 SLA 明确要求 P95 延迟 ≤ 300ms 或 P99 ≤ 150ms（如实时语音转写、高频交互式助手）；
- 流量存在明显波峰（如电商大促期间搜索补全请求激增），需保障吞吐下限；
- 已有成熟模型，但标准推理通道无法满足时延稳定性需求，且愿意为独占资源支付溢价；
- **注意规避**：需要流式响应（`stream=true`）、使用 `embedding`/`rerank` 模型、或需弹性扩缩容的场景。

### ✅ 推荐使用「模型压缩」当：
- 微调模型体积过大，导致部署成本过高（如 7B 模型需 2×A10，压缩后可单卡 A10 运行）；
- 业务对推理精度容忍一定下降（如客服问答 Top-1 准确率从 92% → 89%，但响应速度提升 40%）；
- 在华北2（北京）地域运营，且模型符合平台当前支持列表；
- **注意规避**：模型尚未完成微调（`SUCCEEDED` 状态）、需在新加坡等地域部署、或未来计划对该模型继续微调/二次压缩。

### ✅ 推荐使用「模型监控」当：
- 任何已上线模型（无论是否启用高速推理或是否经过压缩）都需要基础可观测性；
- 需要建立 SLO（如 “99% 请求延迟 < 1s”）并定期审计达标情况；
- 出现线上问题（如错误率突增）时，需快速下钻到模型、API Key、时间粒度定位根因；
- **注意规避**：无需任何运行态数据反馈的纯离线测试场景（此时可关闭告警，但用量统计仍默认开启）。

## 技术选型参考（面向开发者）

| 选型问题 | 推荐决策路径 | 关键检查点 |
|----------|--------------|------------|
| **我的模型延迟不达标，该选哪个？** | 优先排查是否已启用「高并发推理」→ 若已启用仍不达标，再评估是否可通过「模型压缩」降低计算复杂度 → 最后用「模型监控」确认瓶颈是否在模型本身（如某次请求 Token 超长导致延迟尖刺） | - Prime 模式是否已正确配置 `instance_type`？<br>- TPM 预留值是否远超实际峰值流量？<br>- 监控中 `p95_latency_ms` 是否持续超过 SLO？ |
| **如何平衡成本与性能？** | **组合使用**：先用「模型压缩」生成多个量化版本（如 `quant-4bit`/`quant-8bit`），分别部署并启用「高并发推理」→ 用「模型监控」持续对比各版本的 `avg_latency_ms`、`error_rate`、`mu_cost_per_1k_tokens` → 选择性价比最优方案 | - 压缩后模型在监控中的精度相关指标（如人工抽检回答质量）是否可接受？<br>- 不同量化版本的 `mu_cost_per_1k_tokens` 差异是否显著？ |
| **上线后发现错误率升高，怎么查？** | 立即打开「模型监控」→ 切换至「性能监控」页，按 `5m` 粒度查看 `http_status_code_5xx_rate` 和 `timeout_rate` 曲线 → 下钻至异常时间段，关联查看 `p95_latency_ms` 是否同步飙升 → 若延迟也升高，检查是否触发了「高并发推理」配额上限或 GPU 资源争抢 | - 是否有未配置告警的静默失败（如 429 频繁出现）？<br>- 自部署模型是否已升级 Telemetry Agent 至 v2.3+？ |
| **能否只用监控，不用其他两项？** | ✅ 可以，且**强烈推荐所有生产服务默认启用**。监控是零成本、零侵入的基础能力，是其他优化决策的数据基石。但仅靠监控无法主动改善性能或降低成本。 | - 确认控制台「监控」页数据正常刷新（延迟约 30 秒）；<br>- 至少配置一条基础告警（如 `error_rate > 1% for 5m`）。 |

> 💡 **最佳实践提示**：  
> - **部署前**：对微调模型执行压缩 → 生成轻量版本；  
> - **部署时**：为压缩后模型启用 `high_speed_inference: { "mode": "prime" }`，锁定低延迟；  
> - **部署后**：通过 `GET /v1/monitoring/metrics` 定期拉取关键指标，构建内部 Dashboard；  
> - **持续迭代**：基于监控数据，每季度重新评估压缩模板有效性，必要时重跑压缩任务。  

本对比基于百炼平台当前（2024年Q2）功能状态，具体能力与限制请以控制台实时提示及最新 API 文档为准。
