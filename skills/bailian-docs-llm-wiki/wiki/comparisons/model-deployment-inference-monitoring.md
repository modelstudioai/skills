# 模型部署、高速推理与监控能力对比

本文档面向百炼平台开发者，旨在清晰对比**模型部署（[model deployment 1](../guides/model-deployment-1.md)）**、**高速推理（[model high speed inference](../guides/model-high-speed-inference.md)）** 和**模型监控（[model monitoring](../guides/model-monitoring.md)）** 三大核心能力在技术定位、适用边界与协同关系上的差异。三者并非并列替代方案，而是构成「服务化 → 加速 → 可观测」闭环的关键环节：  
- **模型部署** 是服务落地的前提，决定资源归属、计费模型与长期稳定性；  
- **高速推理** 是性能优化的手段，可在已部署服务基础上叠加加速能力（如 PTU 部署 + 吞吐预留），或通过轻量方式（Prime）快速提效；  
- **模型监控** 是运维保障的基础，对所有调用行为（无论部署模式、是否启用加速）提供统一可观测视图，支撑成本治理、SLA 保障与故障归因。  

本对比聚焦开发者最常决策的维度，帮助您在真实业务场景中做出高效、可扩展、可运维的技术选型。

## 关键能力维度对比

| 维度 | 模型部署（[model deployment 1](../guides/model-deployment-1.md)） | 高速推理（[model high speed inference](../guides/model-high-speed-inference.md)） | 模型监控（[model monitoring](../guides/model-monitoring.md)） |
|------|-------------------------------|----------------------------------------|------------------------------|
| **核心目标** | 将模型固化为生产级 API 服务，实现资源隔离、成本可控与长期稳定运行 | 在已有服务基础上提升吞吐能力与响应确定性，应对高并发/低延迟敏感场景 | 全面采集、可视化与告警模型调用行为，支撑运维分析、成本审计与稳定性治理 |
| **输入格式** | 控制台表单或 API 请求体（含 `plan`, `model_name`, `ptu_capacity`/`deploy_spec` 等结构化参数） | 标准 OpenAI 兼容请求（仅需修改 `model` 字段为 Prime ID 或吞吐预留专属 code） | 无主动输入；数据自动采集自所有符合权限的 API 调用（兼容 DashScope / OpenAI 协议） |
| **输出格式** | 部署成功后返回唯一 `model_code`（如 `qwen3-8b-ft-xxx` 或 `tpm-abc123`），用于后续调用 | 与原模型完全一致的响应格式（含 `choices`, `usage`, `reasoning_content` 等字段），无协议变更 | 图表化监控面板、结构化用量报表（CSV 导出）、告警通知（邮件/钉钉/短信）、SLS 日志流（JSON 格式） |
| **支持模型** | ✅ 平台预置模型（Qwen、GLM、DeepSeek 等）<br>✅ 百炼调优模型<br>✅ OSS 导入 LoRA 模型（全参微调需白名单）<br>❌ [Token](../concepts/token.md) 按量不支持全参模型 | ✅ Prime：限定型号（如 `glm-5.2-fast-preview`, `qwen3.8-max-prime`）<br>✅ 吞吐预留：覆盖主流大模型（Qwen/GLM/DeepSeek/Kimi），支持标准/高速双模式 | ✅ 所有在百炼模型列表中可见的模型（LLM、多模态、Embedding、Rerank、语音、图像等）<br>⚠️ 告警与部分指标对语音/视频/三方直连模型支持有限（控制台动态隐藏） |
| **API 端点** | 部署后使用标准兼容 endpoint：<br>`https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`<br>（智能路由必须用 `maas.aliyuncs.com`） | 与部署端点**完全一致**，无需更换域名或路径，仅替换 `model` 字段 | 无独立调用端点；数据通过控制台访问或 SLS/OpenSearch 查询 |
| **计费方式** | 🔹 PTU：按预置 TPM 额度月结<br>🔹 MU/DTU：按独占算力规格（MU1/MU4 等）月结<br>🔹 [Token](../concepts/token.md) 按量：按实际 token 消耗实时计费<br>❗ 计费模式创建后不可变更 | 🔹 Prime：按 token 计费（含缓存折扣）<br>🔹 吞吐预留：预付费购买 kTPM（按自然日结算），预留内调用免费；溢出部分按 token 计费 | ❌ **不计费**：监控数据纯运维用途，**不作为计费依据**；精确账单请以费用中心为准 |
| **典型场景** | • 需长期稳定服务的 SaaS 应用后端<br>• 对数据隔离/合规有强要求的企业私有部署<br>• 多模型 A/B 测试与灰度发布<br>• 自定义 LoRA 微调模型上线 | • AI 编程助手、Agent 多步推理等首 token 敏感场景<br>• 大促/活动期间流量洪峰保障<br>• 快速验证性能瓶颈，无需重构部署架构 | • 追踪某模型在各业务线的用量分布<br>• 设置失败率 >1% 的 SLA 告警<br>• 分析首 token 延迟突增根因<br>• 审计 Prompt/Response 内容（开启推理日志后） |
| **资源隔离级别** | ⭐⭐⭐⭐⭐ 物理/逻辑强隔离（DTU/MU）或弹性共享池保障（PTU） | ⭐⭐ Prime：共享池调度优化，无容量承诺<br>⭐⭐⭐⭐ 吞吐预留：专属 kTPM 刚性兑付 | ⚠️ 无资源占用：纯数据采集层，不影响模型推理性能 |

## 适用场景建议（面向开发者）

| 业务需求 | 推荐能力组合 | 关键理由 | 注意事项 |
|----------|--------------|----------|----------|
| **构建企业级 AI 中台，要求高可用、强隔离、长期稳定** | ✅ **模型部署（DTU/MU）** + ✅ 模型监控 | DTU/MU 提供物理级资源隔离与 SLA 保障；监控提供用量基线与告警闭环，满足合规审计要求 | 避免选用 [Token](../concepts/token.md) 按量模式——其扩缩容需人工审核，不满足生产稳定性要求 |
| **快速上线 PoC，验证微调效果，预算敏感** | ✅ **模型部署（Token 按量）** + ✅ 模型监控 | 按量模式“用多少付多少”，零闲置成本；监控可清晰追踪验证过程中的 token 消耗与失败率 | Token 按量仅支持 LoRA 模型，且无法升级为 PTU/MU，验证成功后需重建服务 |
| **现有服务遭遇性能瓶颈，需提升 TPS 与首字延迟** | ✅ **高速推理（吞吐预留·高速模式）** + ✅ 模型监控 | 吞吐预留提供刚性容量保障，性能对标 Prime 但更稳定；监控可量化加速效果（对比加速前后首 token P95） | 吞吐预留需配合已部署的模型（如 `qwen3-8b-ft-xxx`），不能单独启用；务必配置溢出策略（如自动降级） |
| **轻量级性能优化，无复杂运维诉求，追求快速见效** | ✅ **高速推理（Prime 模式）** | 无需部署新服务，仅替换 model ID 即可获得 1.5~2× TPS 提升，接入成本最低 | Prime 模型 ID（如 `glm-5.2-fast-preview`）与原模型 ID（如 `GLM-5.2`）不互通，不可混用；无容量保障，高峰时段性能可能波动 |
| **多模型混合调用，需统一成本分析与异常溯源** | ✅ **模型监控（全量）** + ✅ 模型部署/高速推理（任意组合） | 监控按业务空间聚合所有调用（无论部署模式、是否启用加速），支持跨模型用量对比与告警统一管理 | 审计日志默认开启，但推理日志需手动配置 SLS 投递；日志单条上限 128KB，超长内容将被截断 |

## 技术选型决策指南

开发者在选型时，请遵循以下分层判断逻辑：

1. **先定“服务形态”（部署层）**  
   - 若需**长期运行、资源隔离、自主扩缩容** → 选 **PTU / DTU / MU**；  
   - 若仅**短期验证、低成本试错** → 选 **Token 按量**；  
   - 若需**动态路由、自动选模** → 选 **智能路由（属于 [model deployment 1](../guides/model-deployment-1.md) 生态）**。

2. **再选“性能增强”（推理层）**  
   - 已完成部署？→ 优先评估 **吞吐预留**（尤其对稳定性要求高）；  
   - 仅需快速提效且能接受共享资源波动？→ 选用 **Prime 模式**；  
   - ⚠️ 注意：**PTU 部署本身已具备高吞吐能力，通常无需额外叠加吞吐预留**；二者叠加属过度配置。

3. **最后配“可观测性”（监控层）**  
   - **所有场景均应启用模型监控**：它是唯一能回答“谁在用？用了多少？为什么失败？”的问题的能力；  
   - 生产环境必开：**用量统计 + 实时监控 + 失败率告警**；  
   - 安全/审计场景必开：**推理日志（SLS 投递）**；  
   - ⚠️ 关键提醒：监控数据延迟约 1 小时（用量）至分钟级（实时指标），**不可用于实时限流或秒级熔断**。

> 💡 **最佳实践提示**：  
> - **避免“裸奔”部署**：任何模型部署上线前，务必在监控中配置基础告警（失败率、429 限流）；  
> - **善用组合能力**：例如，用 `MU` 部署核心模型 → 为其配置 `吞吐预留·高速模式` 应对大促 → 通过监控看板实时比对加速前后 P95 延迟；  
> - **警惕文档陷阱**：DTU 与 MU 是互补而非替代关系；`glm-5.2-fast-preview`（Prime）与 `GLM-5.2`（吞吐预留）是不同路径，切勿混淆 model ID。

通过本对比，开发者可清晰识别各能力的职责边界与协同价值，避免重复建设或能力误用，最终构建出高性能、高可靠、高可观测的 AI 服务架构。
