# 模型微调、压缩与部署对比

百炼平台为开发者提供了从模型定制到上线服务的完整链路：**模型微调（Fine-tuning）** 让基础模型适配垂直业务，**模型压缩** 通过量化降低部署成本，**[模型部署](../concepts/model-deployment.md)** 将模型转化为可调用的推理服务。三者在模型生产流水线中各司其职、前后衔接，理解它们的定位与差异是做好技术选型的前提。

## 核心维度对比

| 维度 | 模型微调 | 模型压缩 | [模型部署](../concepts/model-deployment.md) |
|------|---------|---------|---------|
| **定位** | 用领域数据改造模型能力 | 用量化算法缩小模型体积 | 将模型上线为推理服务 |
| **输入** | 训练数据集（JSONL / 纯文本 / ZIP） | 自定义微调后的全精度模型 + 可选校准数据 | 预置模型或微调/压缩后的模型 |
| **输出** | 微调后的自定义模型 | 低精度量化模型 | 可调用的在线推理端点 |
| **操作方式** | 控制台可视化 / DashScope API | 控制台 / OpenAPI | 控制台 / HTTP API |
| **支持的模型类型** | 文本生成、视觉理解、视频生成、图像生成、语音合成 | 仅限支持列表内的自定义微调模型（当前仅 qwen3.5-flash 系列） | 预置模型（千问、DeepSeek、GLM 等）及自定义调优模型 |
| **训练/处理方式** | SFT、CPT、DPO；全参训练或 LoRA 高效训练 | 量化（由量化模板决定精度与目标规格） | 不涉及训练 |
| **耗时** | 数小时到数十小时 | 视模型大小而定 | 部署启动后数分钟到数十分钟 |
| **计费方式** | 按训练消耗的 Token 数计费 | 当前限时免费 | PTU（预留吞吐）/ MU（模型单元按时长）/ 按 Token 用量 |
| **产物可逆性** | 可基于产出模型继续训练或压缩 | 不可逆，不支持二次压缩或继续训练 | 可随时上线/下线/删除 |
| **地域限制** | 华北 2（北京） | 以控制台为准 | 华北 2（北京） |

## 流水线中的位置关系

三者在模型生产流程中通常按以下顺序衔接：

```
基础模型 → [模型微调] → 微调模型 → [模型压缩(可选)] → 量化模型 → [模型部署] → 推理服务
```

- **模型微调**是起点：当 [Prompt 工程](../concepts/prompt-engineering.md)和插件调用无法满足业务需求时，通过 SFT/CPT/DPO 等方式让模型习得领域知识或遵循特定指令。
- **模型压缩**是可选的中间环节：仅对微调产出的全精度模型生效，通过量化降低显存占用，使模型可以用更小的部署单元（如从 MU1x2 降至 MU8x1）运行，从而降低部署成本。
- **[模型部署](../concepts/model-deployment.md)**是终点：无论是预置模型、微调模型还是压缩模型，都必须经过部署才能对外提供推理服务。

## 适用场景建议

### 优先考虑模型微调

- 基础模型在目标任务上表现不佳，需要注入领域知识（CPT）或对齐任务指令（SFT）。
- 有明确的 bad case 需要通过偏好对齐（DPO）修正。
- 业务涉及特定风格的图像/视频生成或专属音色合成。

### 优先考虑模型压缩

- 微调后的模型部署成本过高，希望在可接受的精度损失范围内降低资源消耗。
- 需要提升推理吞吐量以应对更高并发。
- 所用基础模型在压缩支持列表内。

### 优先考虑模型部署

- 模型已就绪（预置或微调/压缩后），需要上线为可调用的推理服务。
- 需要根据业务负载选择不同计费策略：流量稳定选 PTU，需要自定义性能指标选 MU，效果验证阶段选按 Token 用量。
- 有本地训练的 LoRA 模型需要导入平台并上线。

## 技术选型参考

| 决策场景 | 推荐方案 |
|---------|---------|
| 模型能力不满足业务需求 | 先尝试 [Prompt 工程](../concepts/prompt-engineering.md)，不行再做微调 |
| 微调后部署成本过高 | 检查模型是否支持压缩，支持则先压缩再部署 |
| 快速验证微调效果 | 使用按 Token 用量计费的部署方式（仅限 LoRA 模型） |
| 生产环境高并发稳定服务 | 微调 → 可选压缩 → PTU 或 MU 模式部署 |
| 仅需使用预置模型 | 直接部署，无需微调和压缩 |
