# [长期记忆](../concepts/memory.md)、知识库与RAG方案对比

为帮助开发者在百炼平台中科学选型，本文系统对比**[长期记忆](../concepts/memory.md)（Long Term Memory, LTM）New**、**知识库（Knowledge Base）** 和 **RAG API** 三类核心知识增强能力。三者虽均涉及“记忆”与“检索”，但设计目标、数据范式、调用粒度与适用边界存在本质差异：  
- **[长期记忆](../concepts/memory.md)**聚焦**用户/智能体自身的结构化经验沉淀**（如行为模式、技能流程、画像属性），强调跨会话的个性化上下文延续；  
- **知识库**是**面向应用的托管式向量检索基础设施**，专为私有文档、多模态资料构建可复用、可共享的“外部知识源”；  
- **RAG API**则是**开箱即用的端到端问答服务封装**，将知识库检索与大模型生成深度耦合，追求快速交付业务价值。  

本对比旨在厘清技术定位，避免功能错配（例如用知识库强行建用户画像，或用LTM管理企业手册），并为架构设计、成本预估与迭代路径提供依据。

## 关键维度对比

| 维度 | 长期记忆（LTM）New | 知识库（Knowledge Base） | RAG API |
|------|-------------------|--------------------------|---------|
| **核心定位** | 用户/智能体的**个性化、结构化记忆中枢**（事实记忆 + 用户画像） | 应用级**多模态私有知识托管与检索服务** | **端到端检索增强问答服务**（知识库 + 模型生成一体化封装） |
| **输入格式** | • `messages`（对话历史）<br>• `custom_content`（自定义文本/JSON）<br>• `profile_schema`（画像模板ID） | • 多源文件（PDF/DOCX/TXT/Excel/音视频等）<br>• URL（飞书、钉钉、语雀等）<br>• 数据库表（MySQL等） | • `query`（自然语言问题，≤2048字符）<br>• `knowledge_base_id`（必填，指向已创建的知识库） |
| **输出格式** | • 同步：`memory_nodes`（结构化节点列表，含`observation`/`skill`/`profile`类型）<br>• 异步：`event_id` → 轮询获取抽取结果<br>• 画像：`GET /profile_schemas/{id}/user_profile` 返回 JSON 属性对象 | • 检索服务：`chunks`（原始切片文本 + 元数据 + score）<br>• 问答服务：`answer`（生成回答） + `retrieved_chunks`（引用片段） + `citations`（标注） | • `answer`（纯文本回答）<br>• `retrieved_chunks`（召回切片数组）<br>• `trace_id`（调试标识）<br>• 支持 SSE 流式响应（`stream=true`） |
| **支持模型** | • **不暴露模型选择权**：<br> - 记忆抽取由后端固定模型完成（`plan_version=pro`/`lite` 控制策略）<br> - 无 Embedding/Rerank/Generation 模型显式配置 | • **Embedding**：`text-embedding-v4`（默认），创建时可选<br>• **Rerank**：`qwen3-rerank`（文本）、`qwen3-vl-rerank`（多模态）<br>• **Generation**：绑定 Qwen/DeepSeek 等大模型（问答服务中配置） | • **固定专用模型**：`qwen-max-rag` / `qwen-plus-rag`<br>• `model` 参数已废弃，模型由知识库类型隐式决定 |
| **API 端点（典型）** | • 写入：`POST /add`（同步） / `POST /add-async`（异步）<br>• 检索：`POST /memory_nodes/search`<br>• 画像：`GET /profile_schemas/{id}/user_profile` | • 检索：`POST /api/v1/indices/knowledge/search`（联合检索）<br>• 问答：`POST /api/v2/apps/knowledge/chat`（流式）<br>• 底层：`POST /api/v1/indices/rag/index/retrieve`（单库直连） | • `POST /v1/knowledge_bases/{kb_id}/query`（核心问答接口） |
| **计费方式** | • **商业化起始时间**：2026年8月20日 10:00（北京时间）<br>• `Add` / `Search` 调用区分 `Pro` 与 `Lite` 版本计费<br>• 具体单价未公开，以控制台为准 | • **规格费**：<br> - 标准版：0.03 元/小时（含基础计算资源）<br> - 旗舰版：0.2 元/RCU/小时（1 RCU ≈ 50 QPS）<br>• **模型费**：Embedding/Rerank/Generation 单独计费<br>• 免费额度：720 小时（仅抵扣标准版规格费） | • **按调用计费**：<br> - `query` 请求次数（含成功/失败）<br> - Embedding/Rerank/Generation 模型调用单独计费<br>• 具体单价未公开，以控制台为准 |
| **典型场景** | • 智能客服持续学习用户偏好（如“张三总订素食餐”）<br>• Agent 自动沉淀操作技能（如“重置路由器步骤”）<br>• 个性化推荐系统构建用户画像（年龄/职业/兴趣标签） | • 企业内部文档助手（制度/手册/财报）<br>• 客服知识库（FAQ/工单记录/产品文档）<br>• 多模态内容检索（PPT图表+会议录音+Excel数据） | • 快速上线轻量级问答应用（无需自研RAG链路）<br>• 需要开箱即用引用标注与拒答控制的场景<br>• 对首字延迟敏感、要求低集成复杂度的MVP验证 |

## 各方案适用场景建议

### ✅ 推荐使用 **长期记忆（LTM）New** 当：
- 你需要**持久化用户个体或智能体自身的状态**，而非通用知识；
- 记忆需具备**强结构化语义**（如明确区分“观察事实”`observation`、“可复用技能”`skill`、“用户属性”`profile`）；
- 业务逻辑依赖**跨会话上下文连续性**（例如：用户上月投诉过物流，本月咨询时自动关联）；
- 你希望**免模型运维**，由平台统一管理抽取策略与精度（通过 `plan_version` 切换）；
- ⚠️ 注意：**不适合存储静态文档、手册、法规等通用知识**；不支持多模态文件解析。

### ✅ 推荐使用 **知识库（Knowledge Base）** 当：
- 你的知识源是**静态或半静态的私有资料**（PDF/Word/Excel/数据库等）；
- 需要**多模态支持**（图片中的表格、音视频转录文本、PPT图文混合）；
- 要求**灵活的检索控制**（如按元数据过滤、多库联合路由、自定义切片规则）；
- 你已有成熟的 RAG 工程链路，需要**高性能、可扩展的底层向量检索能力**；
- ⚠️ 注意：**不直接提供生成能力**，需自行集成大模型；地域限制严格（仅北京/新加坡）。

### ✅ 推荐使用 **RAG API** 当：
- 你追求**最快上线速度**，希望跳过知识库创建、切片配置、模型绑定等环节；
- 场景对**答案可靠性与可追溯性要求高**（需原生支持引用标注、拒答策略、防泄漏）；
- 团队缺乏 RAG 工程经验，需要**平台兜底全链路稳定性与可观测性**（`trace_id`）；
- 业务规模适中，无需极致定制化（如自定义重排逻辑、混合检索策略）；
- ⚠️ 注意：**灵活性最低**——无法更换底层模型、不可修改切片逻辑、不支持多模态（仅文本知识库）。

## 技术选型参考（面向开发者）

| 选型考量 | LTM New | 知识库 | RAG API |
|----------|---------|--------|---------|
| **开发复杂度** | 中（需理解 `user_id`/`project_id` 隔离、异步轮询机制） | 高（需配置切片、嵌入模型、重排模型、问答服务绑定） | **极低**（1个API + `kb_id` 即可发起问答） |
| **定制化能力** | **高**（自定义画像 schema、抽取模式 `extract_mode`、`plan_version` 精细控制） | **极高**（全链路参数可调：切片长度、嵌入模型、重排模型、检索策略） | **低**（模型、切片、重排均不可配，仅 `top_k`/`stream` 可调） |
| **数据所有权与隔离** | 强隔离：`user_id` + `memory_library_id` + `project_id` 三级隔离 | 强隔离：业务空间 + 知识库实例 + 权限策略（`AliyunBailianDataFullAccess`） | 中隔离：依赖知识库本身的权限体系，`kb_id` 是访问凭证 |
| **实时性要求** | • 同步写入：毫秒级（适合简短消息）<br>• 异步抽取：秒级延迟（推荐） | • 检索：毫秒级（向量索引）<br>• 文档解析：分钟级（异步任务） | • 问答：首字延迟约 300–800ms（含检索+生成） |
| **运维负担** | 低（平台托管抽取/检索/画像生成） | 中（需监控切片质量、重排效果、日志投递） | **最低**（平台全托管，仅需关注 `trace_id` 排查） |
| **演进路径建议** | • MVP：用 `AddMemoryAsync` 快速沉淀用户反馈<br>• 进阶：结合 `SearchMemory` 实现个性化回复 | • MVP：用 Playground 快速验证文档召回<br>• 进阶：接入 CLI/MCP 构建自动化同步流水线 | • MVP：直接调用 `/query` 上线问答<br>• 进阶：当性能/定制需求上升，迁移到知识库 + 自研 RAG 链路 |

> **终极建议**：  
> - **做“人”的记忆，选 LTM；做“事”的知识，选知识库；做“快”的交付，选 RAG API**。  
> - 在复杂智能体中，三者常**协同使用**：LTM 管理用户画像 → 知识库提供领域知识 → RAG API 或自研链路融合二者生成回答。  
> - 始终以 **`user_id` 隔离性**（LTM）和 **`kb_id` 权限管控**（知识库/RAG）为安全设计前提，避免数据越界。
