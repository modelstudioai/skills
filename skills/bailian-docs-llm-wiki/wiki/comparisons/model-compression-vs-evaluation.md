# 模型压缩与模型评估对比

在百炼平台的模型生产全生命周期中，**模型压缩**与**模型评估**是两个关键但目标迥异的技术环节：前者聚焦于**部署效率优化**（降本、提速、轻量化），后者服务于**质量可信验证**（可衡量、可对比、可归因）。二者常在微调之后协同使用——先通过评估确认模型效果达标，再执行压缩以降低上线成本；若压缩后精度下降明显，亦需回退评估定位损失来源。本文旨在为开发者提供清晰、可操作的对比视图，辅助技术选型与流程编排决策。

## 关键维度对比

| 维度 | 模型压缩 | 模型评估 |
|------|----------|----------|
| **核心目标** | 降低模型推理资源消耗（MU 规格），提升吞吐、降低成本，**不改变模型功能语义** | 量化模型生成质量，验证能力表现，支撑选型、调优验证与持续监控，**不修改模型本身** |
| **输入格式** | • 源模型：仅限百炼平台内状态为 `SUCCEEDED` 的微调模型（`fine-tuned`）<br>• （可选）校准数据集：已在「数据管理」中发布、类型为 `EvaluationSet` 的结构化数据（含 `Prompt`/`Completion`），最多 5 个 | • 被测模型：百炼预置文本生成模型或用户微调模型<br>• 数据来源：<br> – 自定义评测：`EvaluationSet` 数据集 或 已有推理结果集（CSV，含 `Prompt`/`Output`/`Completion`）<br> – 基线评测：内置 Benchmark（如 MMLU-Pro、GSM8K），无需上传数据 |
| **输出格式** | • 新模型 ID（源模型名 + 用户指定后缀，如 `ft-qwen35-20260223-w4a4`）<br>• 压缩任务日志（含 PTQ 过程信息、校准统计、失败原因）<br>• **无中间评分或质量报告** | • 综合得分（各维度平均值）<br>• 维度级指标（通过率、均值、分布直方图）<br>• 逐条明细（Prompt、Output、Completion、各维度评分、裁判依据）<br>• 可视化图表（雷达图、多任务对比、Bad Case 分析） |
| **支持模型** | • **仅支持百炼平台内完成且状态为 `SUCCEEDED` 的微调模型**<br>• 不支持基础模型、导入模型、API 上传模型、未发布模型<br>• 当前仅适配 Qwen 等主流文本生成模型系列（依赖量化模板覆盖） | • 支持百炼预置文本生成模型（如 Qwen-Max、Qwen-Plus）<br>• 支持用户微调后的文本生成模型（`fine-tuned` 状态）<br>• **明确不支持**：[多模态](../concepts/multi-modal.md)、语音、向量嵌入、图像生成等非文本生成类模型 |
| **API 端点（控制台路径）** | 模型中心 → 模型压缩 → 创建压缩任务<br>（地域限制：仅华北2（北京）控制台可见并可用） | 模型中心 → [模型评测](../concepts/model-evaluation.md) → 创建评测任务<br>（地域限制：基线评测仅华北2（北京）可用；自定义评测全地域支持） |
| **计费方式** | • **压缩任务本身当前限时免费**（截止时间以控制台公告为准）<br>• **部署阶段按压缩后模型实际 MU 规格计费**（如 MU5/MU8），与未压缩版本不同<br>• 校准数据不产生额外费用 | • **被测模型推理费**：使用「评测数据集」触发推理时产生（按 tokens 计费）<br>• **裁判模型评分费**：仅当评测维度为「大模型评估」时产生（按裁判模型 tokens 计费）<br>• 「规则评估」「人工评估」无裁判模型费用<br>• 使用「推理结果集」作为数据源时，**不产生被测模型推理费** |
| **典型场景** | • 微调模型效果达标后，需降低线上服务成本<br>• 高并发低延迟场景下需提升单节点吞吐<br>• 边缘/端侧轻量化部署需求<br>• A/B 测试中对比不同量化模板的性价比 | • 微调前后效果对比，验证调优有效性<br>• 多个候选模型（如不同微调超参、不同基础模型）横向选型<br>• 上线前质量准入检查（设定通过阈值）<br>• 持续监控线上模型退化（定期重跑评测）<br>• 客户交付时提供可验证的质量报告 |
| **可逆性与后续操作** | • **不可逆**：压缩后模型无法继续微调，也不支持二次压缩<br>• 输出为独立新模型，可正常部署、调用、删除 | • **完全可逆**：评测仅为只读分析，不修改任何模型或数据<br>• 同一模型可反复创建不同维度/数据的任务<br>• 评测维度可删除重建，任务可重复执行 |

## 各方案适用场景建议

| 场景描述 | 推荐方案 | 关键理由 |
|----------|----------|----------|
| **刚完成微调，不确定效果是否达标** | ✅ 优先执行**模型评估**（自定义评测） | 必须先确认模型质量基线；若评估未达预期（如综合分 < 3.5 或关键维度通过率低），压缩无意义，应回退调优。 |
| **微调模型已通过业务验收，准备上线但预算紧张** | ✅ 执行**模型压缩**（选 MU5/MU8 模板）+ **压缩后补做评估** | 压缩是部署前必经降本步骤；但必须对压缩后模型重新评测，验证精度损失在容忍范围内（如综合分下降 ≤ 0.3）。 |
| **需对比多个微调版本（如不同 learning rate）的最终效果** | ✅ 使用**模型评估**（统一数据集 + 统一维度）进行横向打分 | 评估提供标准化、可复现的量化标尺；压缩无法用于横向对比（每个模型压缩后规格/精度不同，不可比）。 |
| **客户要求提供“模型性能白皮书”，包含权威 benchmark 结果** | ✅ 使用**模型评估**（基线评测模式，勾选 MMLU-Pro、GSM8K 等） | 基线评测自动运行行业标准数据集，输出可直接交付的权威报告；压缩不产生任何 benchmark 分数。 |
| **需将模型部署至资源受限的边缘设备（如 4GB GPU）** | ✅ 重点使用**模型压缩**（选择最低 MU 规格模板，如 MU2/MU3）+ 强化校准 | MU 编号直接对应部署规格；必须配合贴近边缘场景的校准数据，否则精度损失可能不可控。 |
| **发现线上模型响应变慢、错误率上升，需定位原因** | ✅ 使用**模型评估**（固定数据集 + 回归评测任务）进行周期性监控 | 通过历史任务对比分数趋势，快速识别是模型退化、数据漂移还是系统问题；压缩与此类诊断无关。 |

## 面向开发者的选型参考

- **不要混淆目的**：压缩解决“能不能便宜地跑”，评估解决“跑得好不好”。二者不是替代关系，而是**流水线上下游协作关系**。典型工作流应为：微调 → 评估（确认效果）→ 压缩 → 评估（验证压缩保真度）→ 部署。
  
- **地域是硬约束**：若您不在华北2（北京）地域：
  - 模型压缩功能**不可用**，请规划模型开发与部署地域；
  - 模型评估的**自定义评测**仍可用，但**基线评测**将不可见，请提前下载所需 Benchmark 数据自行构建评测集。

- **成本敏感型决策要点**：
  - 压缩任务本身免费，但部署成本取决于 MU 规格——务必在免费期内多试几个模板（如 w4a4/w3a3），用评估结果选出“精度损失最小、MU 最低”的最优解；
  - 评估成本可控：小规模验证用 100 条数据集 + 规则评估（零裁判费）；大规模基线评测建议用「推理结果集」避免重复推理开销。

- **风险规避提示**：
  - 压缩前务必保存原始微调模型快照（平台自动保留）；
  - 评估维度一旦创建不可修改，建议先用小数据集测试 Prompt 和阈值，再应用于正式任务；
  - 所有失败任务均不可重试，压缩失败需新建任务；评估失败可直接修改参数重试。

- **进阶建议**：
  - 将评估任务配置为 CI/CD 流水线一环（如 GitHub Action 调用百炼 API），实现每次微调自动回归测试；
  - 对关键业务模型，建立“压缩-评估”自动化脚本：自动遍历模板 → 并行压缩 → 并行评测 → 生成对比报告 → 推荐最优组合。

> 💡 **一句话总结**：**用评估定质量底线，用压缩守成本红线——二者缺一不可，但顺序不能颠倒。**
