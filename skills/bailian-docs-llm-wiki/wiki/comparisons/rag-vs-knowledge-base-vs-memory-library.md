# RAG、知识库与记忆库方案对比

本文旨在帮助开发者清晰区分百炼平台中三种核心语义增强能力：**RAG API**（程序化 RAG 工作流）、**知识库**（面向业务的知识服务载体）与**记忆库**（面向用户的[长期记忆](../concepts/long-term-memory.md)服务）。三者虽均基于检索增强技术，但在设计目标、数据生命周期、调用范式及适用场景上存在本质差异。本对比聚焦实际工程落地维度，为技术选型提供可操作的决策依据。

## 关键维度对比

| 维度 | RAG API | 知识库（Knowledge Base） | 记忆库（Memory Library） |
|--------|---------|---------------------------|-----------------------------|
| **定位与目标** | 面向开发者的**底层能力封装**，提供全链路 RAG 控制权（从数据导入、索引构建到服务发布） | 面向业务人员与开发者的**开箱即用知识服务**，以“知识库”为单位统一管理数据、检索与问答策略 | 面向智能体（Agent）的**跨会话用户级[长期记忆](../concepts/long-term-memory.md)服务**，解决上下文窗口限制与个性化连续交互问题 |
| **输入格式** | 原始文件（PDF/DOCX/CSV/音视频等）、结构化元数据（`category`, `meta_data`）、纯文本片段；支持 OSS/飞书/语雀等外部源注册 | 同 RAG API，但通过控制台/CLI/API 一键导入更友好；支持“数据集”抽象，允许多源混合接入 | **对话消息流**（`user_message` + `assistant_message`），或显式传入事实字符串（如 `"用户喜欢咖啡"`）；不接受原始文件 |
| **输出格式** | • 检索：JSON 数组（含切片内容、来源文档、相似度）<br>• 问答：标准 LLM 流式响应（SSE）或 JSON（含引用溯源） | • 检索：结构化 JSON（含 `chunks`, `documents`, `retrieval_score`）<br>• 问答：带引用标记的自然语言回答（支持 Markdown 格式化） | • 检索：JSON 数组（含 `memory_id`, `content`, `type`（fact/profile）, `score`, `meta_data`）<br>• 用户画像：结构化 Schema 对象（如 `{"age": 28, "occupation": "engineer"}`） |
| **支持模型** | • Embedding：`text-embedding-v4`, `qwen3-vl-embedding`（多模态）<br>• Rerank：`qwen3-rerank`, `qwen3-vl-rerank`<br>• LLM：由 Agent 配置（如 `qwen3.7-plus`）<br>• Parser：`DOCMIND_LLM_VERSION` 等 | • Embedding：默认 `text-embedding-v4`（创建后不可改）<br>• Rerank：`qwen3-rerank`, `qwen3-vl-rerank`（按需启用）<br>• LLM：`qwen3.6-plus` 等（问答服务配置）<br>• 多模态解析：`Qwen-VL`（图片）、ASR 模型（音视频） | • Embedding：内置专用记忆向量模型（不暴露名称）<br>• Rerank：`Pro` 版本启用重排，`Lite` 版本跳过<br>• 无生成模型：仅检索注入，生成由调用方 LLM 完成 |
| **API 端点（典型）** | • 管理类：`/api/v1/indices/knowledge/base`（知识库 CRUD）<br>• 数据类：`/api/v1/indices/knowledge/file`（文档管理）<br>• 运行时：`/api/v1/indices/knowledge/search`（联合检索）, `/api/v2/apps/knowledge/chat`（问答） | • 单库检索：`/api/v1/indices/rag/index/retrieve`（需 `index_id`）<br>• 应用级检索：`/api/v1/indices/knowledge/search`（需 `agent_id`）<br>• 问答：`/api/v2/apps/knowledge/chat`（SSE 流式） | • 写入：`POST /api/v2/apps/memory/add`<br>• 检索：`POST /api/v2/apps/memory/search`<br>• 用户画像：`GET /api/v2/apps/memory/profile/{user_id}`<br>• 全量查询：`GET /api/v2/apps/memory/list` |
| **计费方式** | • **按调用计费**：知识库管理、文档同步、检索、问答等接口独立计费<br>• **模型费用叠加**：Embedding/Rerank/LLM 调用单独计费<br>• 无固定规格费 | • **规格费 + 模型费**：<br>  - 规格费：按小时计费（标准版/旗舰版 RCU）<br>  - 模型费：Embedding/Rerank/LLM 调用按 token 或次数计费<br>• 免费额度仅抵扣规格费 | • **操作费 + 存储费**：<br>  - `AddMemory` / `SearchMemory` 按次计费（分 `Pro`/`Lite` 版本）<br>  - 记忆存储按小时计费<br>• 免费额度覆盖 Add/Search 操作与基础存储 |
| **数据生命周期** | • **完全可控**：开发者自主决定何时导入、更新、删除文档/切片/知识库<br>• 删除操作永久生效，无回收站 | • **半托管**：数据导入后自动完成解析、切片、向量化；更新需重新导入或调用更新接口<br>• 删除知识库 = 永久清除所有数据与索引 | • **自动演进**：<br>  - 事实记忆：按规则自动提取、自动过期（可配置）<br>  - 用户画像：结构化持久化，长期有效<br>• 支持手动增删改查，但核心价值在于自动化提取 |
| **典型场景** | • 构建私有化部署的 RAG 平台<br>• 需深度定制切片逻辑、嵌入策略或检索流程<br>• 多知识库动态编排与灰度发布<br>• 与自研工作流引擎（如 Airflow/LangChain）深度集成 | • 快速上线客服知识问答机器人<br>• 企业内部文档中心（政策/产品/手册）智能搜索<br>• 多源知识聚合（OSS+飞书+语雀）的一站式管理<br>• 低代码/无代码场景下的知识服务能力复用 | • 智能客服中的用户偏好记忆（如“上次说过敏源是花生”）<br>• 个人助理中的待办提醒、健康习惯追踪<br>• 教育应用中学生学习进度与薄弱点画像<br>• 多轮对话中保持上下文连贯性（如“继续刚才的合同条款讨论”） |

## 各方案适用场景建议

### ✅ 选择 **RAG API** 当：
- 你需要**完全掌控 RAG 全流程**，例如自定义文档解析规则（如法律合同特殊段落识别）、实现多阶段混合检索（关键词+向量+图谱）、或对接内部权限系统进行细粒度访问控制；
- 你正在构建一个**多租户 SaaS 平台**，需为每个客户动态创建/销毁知识库，并隔离其数据与模型配置；
- 你已有成熟的数据管道（如 Kafka + Flink），希望将百炼作为向量化与检索后端，而非前端服务入口；
- 你对延迟、吞吐或错误处理有严苛要求，需自行实现重试、熔断、缓存等中间件逻辑。

> ⚠️ 注意：RAG API 是“能力基座”，非开箱即用服务。它要求开发者理解 RAG 各环节原理，并承担更多运维与调试成本。

### ✅ 选择 **知识库** 当：
- 你的目标是**快速交付一个稳定、可维护的知识服务**，例如将 500 份产品说明书变成可搜索的 FAQ 助手；
- 你依赖**多源异构数据**（PDF 手册 + 飞书表格 + OSS 图片），且希望统一管理、自动同步、可视化调试；
- 你需要**开箱即用的问答体验**，包括引用溯源、拒答控制、防信息泄漏等安全策略，且不愿从零实现 Prompt 工程；
- 你团队中有业务人员参与运营，需要他们通过控制台自助更新文档、调整召回数量或切换重排模型。

> ⚠️ 注意：知识库强调“知识资产”的静态性与业务一致性。它不适合高频变更的用户状态数据（如购物车、实时订单），也不适合跨用户共享的个性化记忆。

### ✅ 选择 **记忆库** 当：
- 你的应用核心是**与用户建立长期关系**，需要记住用户说过的话、做过的事、表达过的偏好，并在后续对话中自然调用；
- 你正在构建**智能体（Agent）**，且希望其具备“人格化”特征（如记住用户昵称、饮食禁忌、会议日程）；
- 你需要**解耦记忆与知识**：例如，公司产品知识放在知识库中供所有人查询，而某位客户的定制需求、历史反馈则存于其专属记忆库中；
- 你追求**零配置记忆能力**：通过预设规则（如“提取所有带‘提醒’字样的句子’”），让系统自动捕获关键事实，无需每次手动写入。

> ⚠️ 注意：记忆库不是数据库替代品。它不保证强一致性，不支持复杂 SQL 查询，也不适合存储大段原始文档或二进制文件。

## 技术选型参考（致开发者）

| 你的需求 | 推荐方案 | 关键理由 |
|----------|----------|----------|
| “我要把内部 2000 份 PDF 文档变成可搜索的知识中心，一周内上线” | **知识库** | 控制台导入 + Playground 调试 + API 集成，最快路径；免费额度可覆盖初期验证。 |
| “我需要为每个客户创建独立知识库，并通过 API 动态开关某个客户的知识源” | **RAG API** | `create_index`/`delete_index` + `submit_sync_job` 可编程控制；`index_id` 作为租户隔离标识。 |
| “我的客服机器人要记住用户上次投诉的产品型号，并在下次对话中主动询问维修进展” | **记忆库** | `AddMemory` 自动提取“投诉型号”，`SearchMemory` 在新会话中召回，天然支持 `user_id` 隔离。 |
| “我已有 LangChain 应用，想替换向量库为百炼，但保留自己的检索逻辑和 LLM 调用” | **RAG API** | 直接调用 `/api/v1/indices/rag/index/retrieve` 获取切片，再送入自有 LLM；完全绕过百炼 Agent 封装。 |
| “我想让销售助手记住客户 A 的预算范围、决策人姓名和上次会议纪要要点” | **知识库 + 记忆库组合** | 客户 A 的公开资料（官网/新闻）放入**知识库**；其私有谈判细节、预算数字、纪要摘要存入**记忆库**（`user_id=A`），二者互补。 |
| “我需要审计每条知识被检索了多少次、哪些切片最常被引用” | **RAG API** 或 **知识库（旗舰版）** | RAG API 提供 `/api/v1/indices/rag/index/monitor` 秒级监控；知识库旗舰版提供 RCU 级别用量报表。 |

> 💡 **最佳实践提示**：  
> - **不要混用同名概念**：RAG API 中的 `index_id` ≠ 知识库的 `index_id`（后者是服务 ID）≠ 记忆库的 `memory_id`；三者 ID 体系完全独立。  
> - **警惕时间戳陷阱**：RAG API 监控接口用**秒级**时间戳，其余接口普遍用毫秒级；知识库与记忆库 API 统一使用毫秒级。  
> - **限流策略差异巨大**：RAG API 检索接口最高 2000 QPS，但监控接口仅 1 QPS；记忆库 `SearchMemory` 限 300 QPM；知识库标准版仅 1 QPS —— 选型时务必评估峰值流量。  
> - **删除即永失**：三个方案的删除操作（知识库/文档/记忆）均**无回收站、不可逆**。生产环境务必添加二次确认与备份机制。
