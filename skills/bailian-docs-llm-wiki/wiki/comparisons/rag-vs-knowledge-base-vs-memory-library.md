# RAG、知识库与[记忆](../concepts/memory.md)库（Memory Library）对比

本文旨在帮助开发者清晰区分百炼平台中三个核心能力模块：**RAG API**（[检索增强生成](../concepts/rag.md)服务接口）、**知识库（Knowledge Base）**（结构化私有数据的向量化存储与检索载体）和**[记忆](../concepts/memory.md)库（Memory Library）**（面向会话的长期用户级[记忆](../concepts/memory.md)服务）。三者虽均涉及“检索”与“上下文增强”，但在设计目标、数据生命周期、适用粒度及集成方式上存在本质差异。本对比聚焦技术选型关键维度，为构建智能应用提供决策依据。

## 关键维度对比

| 维度 | RAG API | 知识库（Knowledge Base） | 记忆库（Memory Library） |
|------|---------|---------------------------|----------------------------|
| **核心定位** | RAG 能力的**统一服务接口层**，封装知识库管理、检索、问答等全链路能力 | RAG 的**数据基础设施**，即私有知识的向量化索引实体，是 RAG 的“原材料仓库” | 大模型的**跨会话长期记忆中枢**，用于持久化用户事实与画像，实现个性化上下文注入 |
| **输入格式** | - 管理类：JSON（含 `indexId`, `pipelineId`, `category`/`categoryId` 等不一致字段）<br>- 检索/问答类：`query`（文本）、`messages`（多轮对话）、`images`（Base64/URL）等 | - 文档类：PDF/Word/Markdown/HTML 等非结构化文件<br>- 表格类：CSV/Excel/数据库连接<br>- 多模态：图片、音视频（需对应解析能力） | - `AddMemory`：自然语言对话片段（如 `"用户说他过敏，不能吃花生"`）或结构化事件（需匹配规则）<br>- `AddUserProfile`：符合 `profile_schema` 的 JSON 对象（如 `{"age": 28, "job": "工程师"}`） |
| **输出格式** | - 管理类：标准 RESTful JSON 响应（含 `indexId`, `pipelineId`, `jobId` 等）<br>- 检索类：`{ "chunks": [...] }`（原始切片列表）<br>- 问答类：SSE 流式响应或 JSON（含 `answer`, `references`, `citations`） | - Playground：高亮引用、来源文档链接、切片预览<br>- API：同 RAG API 输出格式（因 RAG API 是其对外接口）<br>- 控制台：可视化切片管理、监控看板、标签体系 | - `SearchMemory`：`{ "memories": [{ "content": "...", "score": 0.82, "type": "fact" }] }`<br>- `GetUserProfile`：结构化 JSON（按 schema 返回）<br>- 控制台：按 `user_id` 分组的记忆列表、时间线视图 |
| **支持模型** | - 嵌入：`text-embedding-v4`, `qwen3-vl-embedding` 等（创建时指定）<br>- 重排：`qwen3-rerank`, `qwen3-vl-rerank`<br>- 生成：`qwen3.6-plus` 等（问答服务中配置） | 同 RAG API（知识库是模型能力的承载实体）；默认嵌入模型不可更改，重排/生成模型可在服务层灵活切换 | - 提取：内置轻量级 NLU 模型（规则驱动，不暴露模型名）<br>- 检索：`Pro` 版本启用重排（隐式调用 `qwen3-rerank` 类模型），`Lite` 版本跳过<br>- 无生成模型，仅返回记忆内容供上层模型使用 |
| **API 端点** | - 管理类：`https://{workspace_id}.cn-beijing.maas.aliyuncs.com/api/v1/indices/...`（业务空间 Endpoint）<br>- 检索/问答：`/api/v1/indices/knowledge/search`, `/api/v2/apps/knowledge/chat` | 无独立端点；所有操作通过 **RAG API** 或控制台完成。知识库本身是资源对象，非服务接口 | `https://dashscope.aliyuncs.com/api/v2/apps/memory/`（DashScope 网关），需 `DASHSCOPE_API_KEY` 鉴权，端点与 RAG API **物理隔离** |
| **计费方式** | - 按调用量计费：知识库管理（创建/删除/切片）、检索、问答均单独计费<br>- 免费额度有限，超出后按请求次数/[Token](../concepts/token.md) 数阶梯计费<br>- 存储按知识库容量（GB/月）计费 | 计费内嵌于 RAG API：知识库存储、向量化、检索、问答均计入 RAG 整体账单；无独立“知识库”计费项 | - **分版本计费**：`Pro`（含重排）与 `Lite`（无重排）单价不同<br>- **免费额度明确**：Add 免费 1500 次/3 个月，Search 免费 5000 次/3 个月，存储 10,000 条永久免费<br>- **商业化起始日**：2026 年 8 月 20 日 10:00（北京时间） |
| **典型场景** | - 构建企业级 RAG 应用的后端服务（如客服知识引擎、合同审查助手）<br>- 需精细控制数据导入、切片、索引、混排策略的中大型项目<br>- 多知识库联合路由与 A/B 测试 | - 快速验证私有知识效果（Playground 调试）<br>- 通过控制台低代码创建知识服务（检索/问答）<br>- 与 Dify/Coze/LangChain 等第三方平台集成 RAG 能力 | - 智能客服中记住用户历史投诉、偏好与禁忌<br>- 个人助理中持续学习用户作息、饮食习惯、会议偏好<br>- Agent 工作流中跨任务传递用户身份与上下文（如 OpenClaw） |
| **数据生命周期** | - 数据由用户显式上传/同步，生命周期由用户管理（可删文档、删切片、删知识库）<br>- 无自动过期机制，需人工维护 | 同 RAG API（知识库即数据实体） | - **自动过期**：事实记忆可配置 7/30/180 天或永不过期<br>- **异步提取**：用户画像首次提取可能延迟，需重试机制<br>- 默认记忆库不可删除，自定义库删除后数据不可恢复 |
| **隔离粒度** | - 以 **业务空间（Workspace）** 为单位隔离<br>- 同一空间内知识库可被多个 Agent 共享 | 同 RAG API（知识库属于业务空间） | - 以 **`user_id`** 为绝对隔离主键（强租户隔离）<br>- 同一 `user_id` 下不同记忆库数据不互通<br>- 支持多应用共享同一 `user_id` 的记忆 |

## 各方案的适用场景建议

### ✅ 选择 **RAG API** 当：
- 你需要**完全掌控 RAG 全流程**：从文件上传、智能切片、嵌入模型选择、重排策略配置，到检索服务发布与细粒度调用；
- 项目需对接**内部系统或定制化工作流**（如 ERP 数据自动同步至知识库、审批流中嵌入合同条款检索）；
- 要求**高并发、低延迟、可监控**的生产级服务，且需基于 `agent_id` 实现服务灰度与流量治理；
- 开发团队具备较强的工程能力，能处理参数不一致（如 `indexId` vs `index_id`）、时间戳精度（秒级 vs 毫秒级）等细节。

### ✅ 选择 **知识库（Knowledge Base）** 当：
- 你希望**快速验证私有知识效果**，无需写代码即可在 Playground 中调试检索与问答质量；
- 采用**低代码/无代码方式构建知识服务**：通过控制台拖拽配置多库权重、混排模型、提示词模板，一键发布；
- 需要将 RAG 能力**标准化输出给第三方平台**（如接入 Dify 的 Knowledge Source、LangChain 的 VectorStore）；
- 数据源类型丰富（文档+表格+图片），且需利用平台内置的**自动打标、定时同步（OSS/飞书/语雀）** 等自动化能力。

### ✅ 选择 **记忆库（Memory Library）** 当：
- 你的应用核心诉求是**理解并记住用户个体**，而非查询静态知识（例如：“小明上周反馈打印机卡纸，这次应优先检查进纸口”）；
- 需要**跨会话、跨应用保持上下文连续性**，且 `user_id` 是你系统中已有的稳定标识（如登录 ID、手机号哈希）；
- 希望以**零代码方式为百炼智能体（Agent）注入长期记忆**（通过 Agent Harness 配置）；
- 对成本敏感，需在检索质量（`Pro`）与延迟/成本（`Lite`）间做明确权衡，并利用其清晰的免费额度。

## 技术选型参考（面向开发者）

| 选型问题 | 推荐方案 | 理由 |
|----------|----------|------|
| **我的应用需要查公司制度文档，同时记住每个员工的请假历史？** | **组合使用**：知识库（存制度文档） + 记忆库（存员工请假记录） | 知识库适合静态、共享、结构化的“组织知识”；记忆库适合动态、私有、个体化的“用户事实”，二者互补，不可互相替代。 |
| **我用 LangChain 开发，想接入百炼的 RAG 能力，该调哪个？** | **知识库 + RAG API** | LangChain 的 `VectorStore` 接口应对接知识库的底层检索能力（如 `/api/v1/indices/rag/index/retrieve`）；而高级问答则调用 `/api/v2/apps/knowledge/chat`（需先发布 Agent）。知识库是 LangChain 可直接集成的抽象层。 |
| **我正在构建一个 ToC 的 AI 健身教练，需记住用户每日运动数据与饮食反馈** | **首选记忆库** | 这是典型的 `user_id` 粒度、时效性强、需自动提取与过期的事实记忆场景。知识库更适合存“健身原理百科”等通用知识。 |
| **我的 API 调用频繁失败，报 `429 Too Many Requests`** | **区分限流域**：<br>- RAG API 管理类接口：检查业务空间 QPS（如 `/rag/index/monitor` 仅 1 QPS）<br>- 记忆库：检查账号级 QPM（总限 3000，`SearchMemory` 单独限 300） | 三者限流策略完全独立，需分别监控与降级。RAG API 限流按接口路径细分，记忆库按账号全局统管。 |
| **我需要支持中文、英文混合文档检索，且要求高精度** | **知识库（配 `text-embedding-v4` + `qwen3-rerank`）** | `text-embedding-v4` 明确支持中英文语义兼容；`qwen3-rerank` 在中文长尾 query 上表现显著优于通用 rerank 模型。记忆库不处理多语言文档索引。 |

> **重要提醒**：  
> - **不要混淆层级**：知识库是“数据”，RAG API 是“操作数据的工具集”，记忆库是“另一套独立的数据+服务”。三者不是版本迭代关系，而是解决不同问题的平行能力。  
> - **避免重复建设**：若已用知识库存储用户手册，勿再将相同手册导入记忆库——记忆库只应存“用户专属事实”，而非“公共知识”。  
> - **关注迁移节点**：知识库旧版数据连接将于 2026 年 9 月 30 日下线；记忆库将于 2026 年 8 月 20 日起正式计费，请及时评估并规划升级路径。
