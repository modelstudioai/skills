# RAG API、知识库与记忆库（Long-term Memory）对比

为帮助开发者清晰理解百炼平台中三类核心数据增强能力的定位差异，本文对 **RAG API**（面向开发者的全生命周期服务接口）、**知识库**（RAG 能力的底层数据载体与服务单元）与 **[长期记忆](../concepts/memory.md)（Long-term Memory, LTM）**（面向多轮对话的状态化用户级记忆管理）进行系统性对比。三者虽均服务于“增强大模型能力”，但在设计目标、数据粒度、生命周期、调用方式及适用场景上存在本质区别。本对比聚焦技术选型关键维度，避免概念混淆，助力开发者在构建智能应用时做出精准决策。

| 维度 | RAG API | 知识库（Knowledge Base） | [长期记忆](../concepts/memory.md)（Long-term Memory） |
|------|---------|--------------------------|------------------------------|
| **本质定位** | **面向开发者的 RAG 全栈服务接口层**：封装知识库管理、Agent 编排、运行时检索与问答等能力的 RESTful API 集合，是集成 RAG 功能的**标准接入通道**。 | **RAG 的核心数据基础设施**：结构化存储、向量化索引与检索的**实体资源**，是知识内容的容器与服务的物理载体；支持文档/表格/图片/音视频等多模态数据。 | **面向对话状态的记忆抽象层**：在多轮会话中持久化存储和检索**用户级事实性信息与偏好画像**的轻量级结构化存储服务，与模型推理解耦。 |
| **输入格式** | JSON 请求体，含 `agent_id`（必需）、`query`/`messages`/`images`、过滤条件（如 `filter`）、元数据等；需严格遵循各端点参数命名规范（如 `page_number` vs `pageNumber`）。 | - **构建期**：原始文件（PDF/DOCX/CSV/MP4/JPG 等）、切片配置（分段长度、切片方式）、嵌入/重排模型选择<br>- **运行时**：纯文本 query 或多模态输入（图片 base64），通过 `/search` 或 `/chat` 接口传入。 | 在标准 `/v1/chat/completions` 请求中嵌入 `memory` 对象：<br>- `memory.write: true` + `memory.rules`（定义提取逻辑）<br>- `memory.query.facts` / `memory.query.profiles`（声明注入字段）<br>需携带 `x-bailian-user-id` Header。 |
| **输出格式** | - 检索接口（`/search`）：返回结构化召回结果（`nodes[]` 含 `content`, `score`, `metadata`）<br>- 问答接口（`/chat`）：SSE 流式响应，含 `delta.content`、引用 `citations[]`、`node_ids` 等<br>- 所有接口统一 `code: "Success"` + `request_id`。 | - 控制台 Playground：高亮引用、命中文档卡片、可展开切片详情<br>- API 响应同 RAG API 运行时接口（因 RAG API 的 `/search`/`/chat` 底层即调用知识库服务）<br>- CLI 输出结构化 JSON 或可读文本。 | 在 `/v1/chat/completions` 标准响应中新增字段：<br>- `memory.facts` / `memory.profiles`：本次注入的记忆片段（写入时）<br>- `memory.injected`：本次查询并注入上下文的记忆键值对<br>- 不改变 `choices[].message.content` 主体结构。 |
| **支持模型** | **不直接绑定模型**，但 Agent 配置中可指定：<br>- 嵌入模型（如 `text-embedding-v4`）<br>- 重排模型（如 `qwen3-rerank`, `qwen3-vl-rerank`）<br>- 生成模型（如 `qwen3.6-plus`）<br>—— 模型能力由知识库类型（`knowledgeType`+`knowledgeScene`）驱动。 | **深度集成多种模型**：<br>- 嵌入模型：创建时选定（不可改），如 `text-embedding-v4`<br>- 重排模型：检索阶段可配，如 `qwen3-rerank`<br>- 生成模型：问答服务绑定，如 `qwen3.6-plus`<br>- 多模态模型：图片/音视频库依赖 `Qwen-VL` 等专用模型。 | **仅限特定 Qwen 模型**：<br>- 显式支持：`qwen-max`, `qwen-plus`, `qwen-turbo`<br>- 其他模型调用时自动忽略 `memory` 字段，无报错。<br>—— **不涉及嵌入/重排等 RAG 模型链路**。 |
| **API 端点** | - 管理类：`/api/v1/indices/rag/index/*`, `/api/v1/indices/rag/app/*`, `/api/v1/connector/dash/*`<br>- 运行时：`/api/v1/indices/knowledge/search`, `/api/v2/apps/knowledge/chat`<br>（全部基于 DashScope 网关，需 `{workspace_id}`） | **无独立端点**。其能力通过以下方式暴露：<br>- RAG API 的运行时端点（推荐生产使用）<br>- 底层单库检索：`/api/v1/indices/rag/index/retrieve`（不推荐，绕过 Agent 策略）<br>- 控制台 Playground、CLI、第三方 SDK 封装调用。 | **复用标准 OpenAI 兼容端点**：<br>- `/v1/chat/completions`（唯一入口）<br>- 通过请求体 `memory` 字段启用，**无需额外 endpoint**。 |
| **计费方式** | **按调用行为计费**：<br>- 知识库创建/更新/删除：免费<br>- 数据导入（OSS PUT）、切片管理：免费<br>- **运行时服务**（`/search`, `/chat`）：按 **RCU（Resource Capacity Unit）** 计费，1 RCU ≈ 50 QPS·秒；标准版含基础额度，旗舰版按用量计费。<br>- 监控类接口（`/monitor`）：单独计费，低频。 | **按资源规格与用量计费**：<br>- 知识库实例：标准版（固定 QPS）、旗舰版（按 RCU）<br>- 存储：按实际向量索引体积计费（GB·月）<br>- 调用：与 RAG API 运行时一致（RCU）<br>- **自 2026 年 1 月 4 日起正式计费**，含 720 小时免费额度。 | **按记忆条目与调用频次计费**：<br>- 写入：按成功写入的 `fact`/`profile` 条目数计费<br>- 查询：按每次 `memory.query` 的键数量计费<br>- TTL 管理（90 天默认）：包含在基础费用中<br>- **不消耗 RCU 或知识库存储资源**。 |
| **典型场景** | - 构建企业级 RAG 平台（多租户、多知识库、动态 Agent 编排）<br>- 需要细粒度控制切片、人工审核/注入内容<br>- 自动化知识库生命周期管理（CI/CD 集成）<br>- 定制化检索策略（混排、路由、过滤规则）开发 | - 快速上线文档问答机器人（HR 政策、产品手册）<br>- 多模态搜索（图片库检索、会议录像语音定位）<br>- 表格数据分析与自然语言查询<br>- 控制台快速验证、A/B 测试不同模型效果 | - 个性化客服：记住用户历史投诉、设备型号、偏好渠道<br>- 智能助手：持续追踪用户日程、待办事项、阅读兴趣<br>- 教育应用：记录学生知识点掌握情况、错题归因<br>- 游戏/NPC：维护角色关系、玩家行为轨迹 |

## 各方案的适用场景建议

- **优先选用 RAG API 当且仅当**：  
  ✅ 你需要**程序化管理多个知识库**（如 SaaS 多租户场景）；  
  ✅ 你要求**Agent 级别的策略编排能力**（如根据用户角色路由到不同知识库、动态启用/禁用切片）；  
  ✅ 你正在构建**自动化知识运维流水线**（如监听 OSS 新增文件 → 自动触发知识库更新 → 发布新 Agent）；  
  ❌ 不建议用于简单问答需求——过度复杂，增加开发与维护成本。

- **优先选用知识库（通过控制台或简化 API）当且仅当**：  
  ✅ 你的核心诉求是**快速部署一个高质量的知识问答服务**（如内部 Wiki 助手、销售话术库）；  
  ✅ 你需要**开箱即用的多模态支持**（上传 PDF+图片+Excel 即可检索）；  
  ✅ 你依赖**可视化调试能力**（Playground 实时查看召回质量、调整相似度阈值）；  
  ❌ 不适合需要跨用户共享记忆、或在对话中动态维护用户状态的场景。

- **必须选用[长期记忆](../concepts/memory.md)（LTM）当且仅当**：  
  ✅ 你的应用本质是**多轮、长周期、强个性化**的对话系统（如个人健康顾问、专属学习教练）；  
  ✅ 你需要**严格隔离用户数据**（`x-bailian-user-id` 是硬性隔离边界）；  
  ✅ 你希望**避免将用户隐私信息写入知识库**（LTM 是独立安全域，不参与向量化与公开检索）；  
  ❌ 不可用于存储公共知识、文档片段或需要语义检索的内容——它不支持向量搜索，仅支持键值精确匹配。

## 面向开发者的技术选型参考

| 你的需求 | 推荐方案 | 关键理由 |
|----------|----------|----------|
| “我要给销售团队做一个产品文档问答机器人，支持上传 PDF 和 PPT，一周内上线” | **知识库（控制台 + Playground）** | 最快路径：上传→配置→测试→发布，无需写一行 API 代码；多模态原生支持，切片与嵌入全自动。 |
| “我们是 SaaS 厂商，要为每个客户开通独立知识库，并允许客户管理员自助上传/下架文档” | **RAG API + 自研控制台** | RAG API 提供完整的 `index`/`app`/`connector` 管理能力，支持租户隔离（`workspace_id`）、批量文件注册、Agent 版本灰度发布。 |
| “我们的客服机器人需要记住每位用户的订单号、投诉历史、上次沟通时间，并在后续对话中主动提及” | **长期记忆（LTM） + RAG API（可选）** | LTM 专为用户级状态设计：`user_id` 隔离、`facts` 类型存订单号、`profiles` 存服务偏好；若还需查公共知识库，则组合调用 `/chat` 接口。 |
| “我们要做一款法律咨询 App，用户提问时既要查《民法典》原文（知识库），又要记住用户所在省份（用于地方条例适配）” | **知识库 + 长期记忆（组合使用）** | 公共法条存知识库（支持语义检索与引用溯源）；用户地域存 LTM（保证实时性与隔离性）；两者通过 `agent_id` 与 `user_id` 在业务层协同。 |
| “我们需要审计所有知识召回结果，确保敏感文档不被误召回” | **RAG API（底层 `/retrieve` + 日志分析）** | RAG API 提供最细粒度的召回结果（`nodes[]` 含完整 `metadata`），配合 SLS 日志中的 `pipeline_id` 和 `node_ids`，可实现全链路审计；知识库控制台仅展示摘要。 |

> **重要提醒**：三者并非互斥，而是**分层协作关系**：  
> **长期记忆（LTM）** 解决 *“用户是谁、记得什么”* —— 对话状态层；  
> **知识库** 解决 *“世界有什么、如何查找”* —— 领域知识层；  
> **RAG API** 解决 *“如何搭建、调度、监控整个系统”* —— 工程集成层。  
> 实际项目中，推荐以知识库为数据核心、LTM 为用户状态补充、RAG API 为自动化底座，构建稳健的 RAG 应用架构。
