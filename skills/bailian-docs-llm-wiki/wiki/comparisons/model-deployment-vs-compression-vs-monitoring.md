# 模型部署、压缩与监控三大生产化能力对比

为帮助开发者在模型落地生产过程中高效选型，本文系统对比百炼平台提供的**模型部署**、**模型压缩**与**模型监控**三大核心生产化能力。三者分别解决“如何稳定提供服务”、“如何降本增效运行服务”和“如何持续保障服务健康”的关键问题，覆盖从上线到运维的全生命周期。本文聚焦技术维度差异，不涉及底层基础设施细节，面向实际工程落地场景提供可操作的选型参考。

## 关键能力维度对比

| 维度 | 模型部署 | 模型压缩 | 模型监控 |
|------|----------|----------|----------|
| **核心目标** | 提供稳定、可伸缩、隔离的推理服务入口 | 降低模型体积与推理延迟，提升单位算力吞吐效率 | 实时观测服务状态，识别性能退化、异常调用与成本风险 |
| **输入格式** | 模型标识（`model_code`）、部署规格参数（如 `input_tpm`, `deploy_spec`）、计费策略 | 原始模型 ID（如 `qwen2-7b-instruct`） + 量化配置（`quantization`, `quantization_config`），或直接使用预置压缩模型 ID | 无显式输入；自动采集所有已调用模型的请求数据（含 `model_code`, `api_key`, `request_id` 等元信息） |
| **输出格式** | 部署成功后返回唯一 `deployment_id` 和可调用的 `model_code`（如 `my-qwen3.8-max-ptu-202408`），通过标准 API 接口返回推理结果 | 返回与原始模型协议完全兼容的推理响应（JSON 格式），仅内部执行量化推理；无额外字段注入 | 多维可视化图表（折线/柱状图）、结构化统计报表（CSV/Excel 导出）、告警通知（钉钉/邮件/Webhook）、SLS 日志（JSON 格式） |
| **支持模型** | • PTU：部分预置大模型 + 所有 LoRA 微调模型<br>• DTU/MU：基础模型 + LoRA + 全参微调模型<br>• [Token](../concepts/token.md) 按量：**仅 LoRA 微调模型** | • Qwen1.5/2/2.5、Llama2/3 系列<br>• 仅支持 4-bit / 8-bit 权重量化 + KV Cache 量化（fp8_e4m3）<br>• **不支持 LoRA 在线压缩**（需先合并） | • 所有可调用模型（含预置、LoRA、全参微调）均支持用量统计与基础指标<br>• 告警与推理日志：**语音/图像/视频/三方直连类模型不支持** |
| **API 端点** | • 创建部署：`POST /api/v1/deployments`<br>• 调用服务：`POST /v1/chat/completions`（使用部署生成的 `model_code`） | • 无独立端点；通过 `POST /v1/chat/completions` 的 `model` 字段指定压缩模型 ID，或在请求体中传入 `quantization` 参数 | • 用量查询：`GET /api/v1/usage/statistics`（需鉴权）<br>• 监控指标：`GET /api/v1/telemetry/metrics`（分钟级聚合）<br>• 告警管理：`POST /api/v1/alerts/rules`（配置接口） |
| **计费方式** | • PTU/DTU：按预购 TPM（每分钟 [Token](../concepts/token.md) 数）或 MU（模型单元）**预付费/后付费**<br>• [Token](../concepts/token.md) 按量：按实际输入/输出 Token 数**后付费**，**不使用不计费** | **不单独计费**；压缩本身免费，但调用压缩模型产生的 Token 消耗计入对应部署或按量计费账单 | **不计费**；监控能力为平台标配功能，数据存储与告警通知无额外费用（SLS 投递日志按 SLS 标准计费） |
| **典型场景** | • 高并发客服机器人（PTU）<br>• 金融风控强隔离推理（DTU/MU）<br>• A/B 测试快速验证（Token 按量） | • 边缘设备轻量部署（如车载终端）<br>• 高并发摘要服务（降低首 token 延迟）<br>• 成本敏感型长文本批量处理 | • SLA 异常归因（如首 token >2s 突增）<br>• 安全审计（Prompt/Response 留痕）<br>• 成本治理（识别低效 API-Key 或滥用模型） |

## 各方案适用场景建议

### ✅ 模型部署 —— 选型决策树
- **需要长期稳定服务 + 高并发 + 低延迟保障？** → 优先选择 **PTU 模式**（适合 `qwen3.8-max` 等大模型长文本场景）  
- **需资源硬隔离 + 支持全参微调 + 自定义推理模式（如 PD 分离）？** → 选择 **MU 模式**（DTU 适用于新模型快速上线，MU 更适合成熟模型精细化运营）  
- **仅做效果验证 / 小流量灰度 / 临时项目？** → 使用 **Token 按量部署**（零闲置成本，但仅限 LoRA 模型）  
- **希望自动匹配最优模型（效果/成本平衡）？** → 启用 **智能路由**（仅 [OpenAI 兼容接口](../concepts/openai-compatible-api.md)可用，需北京/新加坡地域）

### ✅ 模型压缩 —— 使用前提与收益判断
- **适用**：当模型推理延迟成为瓶颈（尤其首 token）、GPU 显存紧张、或需在边缘设备部署时；Qwen/Llama 系列 7B~14B 模型经 4-bit 量化后，显存下降约 60%，首 token 延迟降低 25%~40%。  
- **慎用**：对生成质量极度敏感的场景（如法律文书生成），建议先在测试集验证 PPL 与人工评估指标；**禁止与 LoRA 适配器同时启用**（会触发 400 错误）。  
- **推荐路径**：先用 `qwen2-7b-instruct-int4` 等预置压缩模型快速验证 → 再通过 `quantization_config` 微调分组粒度（如 `group_size=64` 进一步压延时）。

### ✅ 模型监控 —— 运维能力建设指南
- **必须开启**：所有生产环境部署（无论 PTU/DTU/Token 按量），用于建立基线、发现隐性故障（如失败率缓慢爬升至 0.9%）。  
- **重点配置**：  
  - 告警：为每个核心模型配置「失败率 >1% 持续 5 分钟」+「调用时长 P95 >3s 持续 10 分钟」双规则；  
  - 日志：**审计日志默认开启，推理日志需主动投递 SLS**（用于安全合规与 Prompt 工程分析）；  
- **避坑提示**：用量数据延迟约 1 小时，不可用于实时限流；若需毫秒级监控，请集成应用层埋点（如 SDK 自定义 metric 上报）。

## 面向开发者的选型参考原则

1. **分阶段推进**：  
   - 验证期 → Token 按量部署 + 基础用量统计（低成本试错）  
   - 上线期 → DTU/MU 部署 + 模型压缩（保障性能与成本）  
   - 运营期 → 全量开启监控告警 + 推理日志（构建可观测闭环）  

2. **组合使用是常态**：  
   - 一个生产服务通常同时涉及三者：例如 `MU 部署 qwen2-7b-instruct` + `启用 awq 4-bit 量化` + `配置失败率告警与 SLS 日志投递`。  
   - 注意依赖关系：**模型压缩不改变部署形态，监控不依赖部署模式**，但 Token 按量部署因无资源独占，其监控数据波动性更高（受平台共享资源影响）。  

3. **权限与配额先行**：  
   - 部署前确认业务空间已开通模型权限 & RPM/TPM 配额充足；  
   - 开启监控日志前完成 SLS 角色授权；  
   - 所有部署创建后计费方式不可变更，务必在创建前确认模式（PTU/DTU/MU/Token）。  

4. **文档与控制台一致性校验**：  
   - 模型支持列表以 [模型压缩](../../raw/model-user-guide/model-compression.md) 和 [模型列表](raw/model-user-guide/model-deployment-index/model-deployment-introduction.md) 中最新表格为准；  
   - 控制台界面功能（如某模型是否显示「告警配置」按钮）为最终权威，文档描述可能存在滞后。  

> 💡 **一句话总结**：部署是“建管道”，压缩是“缩管径提流速”，监控是“装压力表+报警器”。三者协同，方能构建高可靠、低成本、可演进的大模型生产体系。
