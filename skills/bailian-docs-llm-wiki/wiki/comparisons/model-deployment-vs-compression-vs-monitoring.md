# 模型部署、压缩与监控实践方案对比

为帮助开发者在百炼平台上高效构建、交付和运维大模型应用，本文系统对比三大核心实践方案：**模型部署**（含多种计费与调度模式）、**模型压缩**（后训练量化）与**模型监控**（可观测性体系）。对比聚焦于技术可行性、资源约束、适用阶段及协同关系，旨在支撑从验证到生产的全生命周期选型决策——尤其面向需要兼顾效果、成本与稳定性的工程化场景。

---

## 关键维度对比表

| 维度 | 模型部署（专属服务） | 模型压缩（PTQ 量化） | 模型监控（可观测性） |
|------|------------------------|--------------------------|--------------------------|
| **输入格式** | 模型 ID（如 `qwen3-8b-ft-xxx`）、部署参数（`plan`, `ptu_capacity`, `deploy_spec` 等） | 全精度微调模型（状态为「成功」）、量化模板、可选校准数据集 | 无显式输入；自动采集已部署/已调用模型的请求与响应元数据 |
| **输出格式** | 唯一 `model code`（如 `qwen3-8b-ft-abc123`），用于 API 调用；返回标准 OpenAI/DashScope 格式响应 | 新模型实例（命名规则：`<源模型名>-<后缀>`），可直接用于部署，**不可继续微调或二次压缩** | 图表化监控指标（失败率、TTFT、[Token](../concepts/token.md) 消耗等）、结构化日志（审计日志含 Request ID/[Token](../concepts/token.md) 用量；推理日志含 Prompt/Response 截断内容）、告警通知（邮件/钉钉/短信） |
| **支持模型** | • 基础模型：Qwen、DeepSeek、GLM、Kimi 等预置版本<br>• 微调模型：LoRA（全量支持）、全参微调（白名单）<br>• 导入模型：LoRA 支持，全参需审核 | • **仅限百炼平台内完成的微调模型**（如 `qwen3.5-flash-2026-02-23`）<br>• **仅华北2（北京）地域可用**<br>• 不支持基础模型、OSS 导入模型、API 注册模型 | • **用量统计**：覆盖所有可调用模型（含语音/图片/视频生成）<br>• **监控告警 & 推理日志**：**仅限文本类大语言模型**（不支持语音、图片、视频生成及三方直连模型） |
| **API 端点** | `/api/v1/deployments`（创建/查询/扩缩容）<br>调用端点：`https://dashscope.aliyuncs.com/api/v1/services/<model_code>/chat/completions`（DashScope）或 [OpenAI 兼容接口](../concepts/openai-compatible-api.md) | `/api/v1/model-compression-jobs`（创建/查询任务）<br>产出模型可直接通过标准部署 API 使用 | • 用量统计：`/api/v1/usage-statistics`（只读）<br>• 监控指标：控制台实时图表（无直接 API，数据投递至 Prometheus/SLS 可程序化获取）<br>• 日志：SLS 查询接口（需配置投递） |
| **计费方式** | • **PTU**：预付费，按预置 TPM 吞吐量（kTPM）月度计费<br>• **DTU/MU**：预付费，按独占算力单元（DTU 输入/输出 TPM 或 MU 规格×副本数）月度计费<br>• **[Token](../concepts/token.md) 按量**：后付费，按实际 Token 消耗计费（仅 LoRA） | • **压缩任务本身限时免费**（以控制台公告为准）<br>• **压缩后模型部署费用独立计费**（按 MU 规格，通常低于源模型） | • **监控能力本身不计费**（免费）<br>• 数据投递至 SLS/Prometheus 产生的云产品费用另计<br>• **监控数据不作为计费依据**，对账请以费用中心账单为准 |
| **典型场景** | • PTU：高并发客服机器人、实时搜索摘要<br>• DTU/MU：金融风控问答、医疗报告生成（需强 SLA）<br>• Token 按量：A/B 测试、效果验证、低频 PoC<br>• 智能路由：多模型灰度发布、成本敏感型泛化任务 | • 将 `MU1*8` 全参微调模型压缩为 `MU5` 部署规格，降低 40%+ 算力成本<br>• 在保持业务指标（如 QA 准确率下降 <2%）前提下，提升吞吐密度 | • 实时发现某模型失败率突增至 15%，定位为提示词注入攻击导致内容安全拦截<br>• 分析首 Token 延时（TTFT）持续升高，确认需扩容 PTU 或切换至 DTU 模式<br>• 审计日志追踪异常 Token 消耗来源（特定 API Key 或 Prompt 模板） |

## 各方案适用场景建议

### ✅ 模型部署 —— 选型核心：**明确业务 SLA 与成本模型**
- **选 PTU**：当业务有**确定性高并发需求**（如每日百万级用户咨询），且能接受“保底吞吐 + 溢出策略”，追求极致性价比。适合流量平稳、长上下文场景（支持前缀缓存折扣）。
- **选 DTU/MU**：当业务要求**严格资源隔离、可控延迟上限、或需自定义推理模式**（如启用 `enable_thinking`）。DTU 是新模型首选，MU 适用于存量模型迁移。适合金融、政务等强合规场景。
- **选 Token 按量**：**仅限 LoRA 微调模型**，用于快速验证效果、小流量上线、或预算受限的实验阶段。注意：月度闲置自动释放，不适合长期稳定服务。
- **选智能路由**：当存在多个备选模型（如 Qwen3 + GLM4），需根据请求语义、成本策略或故障状态**动态调度**，实现效果与成本的帕累托优化。注意：仅限北京/新加坡地域，且仅支持文本 Chat Completions。

### ✅ 模型压缩 —— 选型核心：**在精度可接受前提下最大化 ROI**
- **必须满足前置条件**：模型为百炼平台内完成的微调任务产出，且位于华北2（北京）地域。
- **推荐使用时机**：全参微调模型部署成本过高（如 `MU1*8`），但业务对精度容忍度 >98%（可通过离线评估验证）；或需在相同硬件规格下部署更多模型实例（提升集群利用率）。
- **慎用场景**：对生成质量极度敏感（如法律文书生成）、模型本身已为轻量级（如 Qwen2.5-1.5B）、或需后续继续微调——因压缩后模型**不可逆、不可再训练**。

### ✅ 模型监控 —— 选型核心：**生产环境稳定性与成本治理的基石**
- **必开场景**：所有**已上线的生产服务**，尤其是使用 PTU/DTU 的高价值模型。分钟级延迟的 TTFT/E2E 监控是 SLA 达标的核心证据。
- **强推荐配置**：  
  ▪️ **失败率告警**（阈值 1%~3%）：第一时间捕获模型崩溃或内容安全策略误伤；  
  ▪️ **TotalToken 消耗告警**：防止 [Prompt 工程](../concepts/prompt-engineering.md)缺陷（如循环生成）导致成本失控；  
  ▪️ **429 限流告警**：识别是否需扩容 PTU/DTU 或优化客户端重试逻辑；  
  ▪️ **开启推理日志（带 SLS 投递）**：用于根因分析、合规审计、Prompt 效果归因。
- **无需监控场景**：纯本地开发调试、非生产环境的临时测试（此时用量统计已足够）。

## 开发者技术选型参考指南

| 你的目标 | 推荐组合方案 | 关键操作建议 |
|----------|----------------|----------------|
| **快速验证一个 LoRA 微调效果** | Token 按量部署 + 用量统计 | 1. 控制台一键部署，填 `plan=lora`；2. 调用后立即查看「模型用量」页，关注 Token 消耗与成功率；3. 无需开启复杂监控，避免配置成本。 |
| **将全参微调模型投入生产，但成本超预算** | 全参微调 → 模型压缩 → DTU 部署 + 全量监控 | 1. 确认模型在北京地域且为百炼微调产出；2. 选择中等强度量化模板（如 MU5），用校准数据集验证精度；3. 压缩成功后，用新模型名部署 DTU 服务；4. **立即配置失败率、TTFT、429 告警**，并开启审计日志投递。 |
| **构建高可用多模型服务网关** | 智能路由（主） + PTU/DTU（备选模型） + 统一监控 | 1. 将 Qwen3、GLM4 等模型分别以 PTU/DTU 部署；2. 创建智能路由服务，配置「效果优先」策略与故障自动切换；3. **在路由服务层面统一配置监控告警**（而非单个备选模型），重点关注路由成功率与下游模型健康度。 |
| **排查线上模型响应变慢问题** | DTU/PTU 部署 + 模型监控（TTFT/E2E） + 推理日志 | 1. 进入「模型监控」→ 选择对应模型 → 查看「首 Token 延时」趋势图；2. 若 TTFT 升高而 E2E 稳定，检查 Prompt 长度/复杂度；3. 若两者同步升高，开启推理日志，结合 SLS 查询具体慢请求的 Prompt 和生成过程。 |
| **满足金融行业审计要求** | DTU 部署 + 全量审计日志（SLS 投递） + 自定义告警 | 1. 使用 DTU 保障资源独占与可追溯性；2. 在监控中开启审计日志投递至指定 SLS Project；3. 配置「内容安全拦截次数」告警（需人工判断是否为误拦）；4. 定期导出 SLS 日志用于第三方审计。 |

> **重要协同提醒**：  
> - **压缩是部署的前置优化步骤，不是替代方案**：压缩后模型仍需通过部署方案（PTU/DTU）对外提供服务；  
> - **监控是部署的必配能力，不是可选项**：无监控的生产部署等于“盲飞”，无法保障 SLA 与成本可控；  
> - **三者共用同一业务空间权限体系**：开通部署权限即默认具备用量查看权限，但监控告警需额外完成云监控角色授权。
