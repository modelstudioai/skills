# [长期记忆](../concepts/long-term-memory.md)与 RAG 方案对比：Long Term Memory vs RAG API

## 对比目的与背景

在百炼平台构建智能对话与知识增强型应用时，开发者常需在「个性化状态维持」与「外部知识融合」两类核心能力间进行技术选型。**[长期记忆](../concepts/long-term-memory.md)（Long Term Memory, LTM）** 聚焦于**用户专属、结构化、细粒度的事实与画像管理**，服务于多轮对话中的一致性与个性化；而 **RAG API** 则面向**通用或领域专属的外部知识库全生命周期管理与语义问答**，支撑基于文档、表格、图像等多源内容的深度检索与推理。

本对比旨在帮助开发者清晰区分二者的设计边界、能力范围与集成成本，避免常见误用（如用 RAG 存储用户手机号，或用 LTM 托管企业产品手册），从而做出符合业务目标、合规要求与工程可维护性的技术决策。

## 关键维度对比

| 维度 | [长期记忆](../concepts/long-term-memory.md)（LTM） | RAG API |
|------|----------------|---------|
| **核心定位** | 用户级结构化记忆管理（事实 + 画像） | 知识库级语义检索与问答服务（文档/数据驱动） |
| **输入格式** | 纯文本字符串（≤2048 字符），需显式指定 `memory_type`（`fact` 或 `profile`）、`user_id`、可选 `metadata` 和 `ttl_seconds` | 多样化原始内容：PDF/Word/Excel/TXT/图片/网页等文件；支持元数据标签（`doc_metadata`）、自定义切片策略、嵌入模型选择；需先上传再索引 |
| **输出格式** | 查询返回 JSON 数组，每项含 `id`、`content`、`score`、`metadata`、`created_at`；无生成式回答，仅记忆片段召回（top-5） | 检索接口返回带 `score` 的文档片段（chunk）列表；问答接口返回流式或非流式 JSON，含 `answer` 字段（模型生成结果）、`references`（引用片段）、`trace_id` 等运行时信息 |
| **支持模型** | 仅限 `qwen-max`、`qwen-plus`、`qwen-turbo` 三类模型调用其记忆能力；其他模型调用被静默忽略 | **不直接绑定模型**，但深度集成：<br>• 嵌入模型：`text-embedding-v4`、`qwen3-vl-embedding`<br>• 重排序模型：默认 `qwen3-rerank`，可配置<br>• 问答模型：由 Agent 的 `agent_model` 指定（如 `qwen3.7-plus`）<br>• 解析/路由模型：`qwen3-vl-plus`（按上下文语义区分使用） |
| **API 端点** | 统一前缀 `/v1/memory`：<br>• `POST /v1/memory/write`<br>• `POST /v1/memory/query`<br>• `DELETE /v1/memory/clear` | 多路径前缀，依赖 `workspace_id` 构建 Base URL：<br>• 知识库管理：`/api/v1/indices/rag/`<br>• 数据导入：`/api/v1/connector/dash/`<br>• Agent 管理：`/api/v1/indices/rag/app/`<br>• 运行时：`/api/v1/indices/knowledge/search`（检索）、`/api/v2/apps/knowledge/chat`（问答） |
| **计费方式** | 按**调用次数计费**：<br>• 写入（`/write`）与查询（`/query`）均计为 1 次 API 调用<br>• 清除（`/clear`）不计费<br>• 记忆存储本身**不额外收费**（受配额约束） | 按**资源维度分层计费**：<br>• 知识库创建/更新/删除：按次<br>• 文档解析与切片：按页数或字符数<br>• 嵌入向量化：按 token 数<br>• 检索与问答调用：按请求次数 + 生成 token 数（问答接口）<br>• 存储容量：按月按 GB 收费（知识库索引占用） |
| **数据隔离粒度** | `user_id` 级严格隔离；同一 `user_id` 下 `fact` 与 `profile` 类型独立存储与检索 | `workspace_id`（业务空间）级隔离；知识库（`indexId`）、Agent（`agent_id`）均为命名空间内唯一资源，支持跨用户共享知识库 |
| **典型场景** | • 记录用户地址、订单偏好、会议日程等动态事实<br>• 持久化用户语言习惯、兴趣标签、服务等级等画像特征<br>• 多轮客服中保持“上次说要退订会员”的上下文一致性 | • 企业内部知识库（制度/流程/FAQ）问答<br>• 客服坐席辅助系统（实时检索产品手册）<br>• 合同/财报/研报等专业文档分析<br>• 多模态场景（图文混合检索、视觉问答） |
| **数据生命周期控制** | 显式 TTL（秒级）：`fact` 默认 30 天，`profile` 默认 1 年；设为 `0` 表示永不过期（受总容量配额限制） | 无全局 TTL；通过手动删除知识库、文档或切片实现清理；软删除后数据不可恢复，需谨慎操作 |
| **合规与安全** | • 记忆内容**不参与训练**，不出现在任何日志/审计导出中<br>• 开发者须自行完成敏感信息脱敏<br>• 符合 GDPR/PIPL 对个人数据最小化与可控性的要求 | • 文件解析、向量化、检索过程均在平台可信环境执行<br>• 支持私有化部署知识库（需企业版许可）<br>• 元数据（`doc_metadata`）可用于权限过滤，但内容本身不自动脱敏 |

## 适用场景建议

### ✅ 推荐使用 **长期记忆（LTM）** 当：
- 你需要在**单用户会话中持续记住其个性化信息**（如“张三喜欢咖啡、住在西湖区、上月投诉过物流”）；
- 数据具有强**用户归属性、高变更频率、短中期时效性**（如订单状态、预约时间、偏好开关）；
- 要求**低延迟、高并发写入与查询**（单 `user_id` 下千级事实记忆仍可毫秒响应）；
- 需满足**严格的数据主权与隐私合规要求**，且不愿将用户 PII 数据存入通用知识库；
- 应用架构已解耦「状态管理」与「大模型推理」，希望用轻量 API 显式控制记忆生命周期。

### ✅ 推荐使用 **RAG API** 当：
- 你需要基于**大量静态或半静态外部文档**（如 500 页产品说明书、1000 条政策法规、历史工单库）提供精准问答；
- 场景涉及**复杂语义理解、跨文档推理、多跳检索或图文混合分析**；
- 知识需要**被多个用户/角色共享访问**（如客服团队共用知识库、销售与技术支持共用产品资料）；
- 要求**细粒度知识治理能力**：版本控制、权限分级（通过 `workspace_id` + IAM）、人工审核切片、A/B 测试不同嵌入/重排模型；
- 可接受**一定构建延迟**（文档上传 → 解析 → 切片 → 向量化 → 索引上线，通常需秒级至分钟级）。

### ⚠️ 明确不推荐混用的场景：
- ❌ **不要用 RAG 存储用户手机号、身份证号、家庭住址等 PII** —— 违反最小化原则，且 RAG 不提供用户级隔离与自动 TTL；
- ❌ **不要用 LTM 托管超过 1000 条事实或 100 条画像** —— 触发硬性配额限制，且缺乏全文检索、版本回溯、多人协作等知识库能力；
- ❌ **不要在 `/v1/chat/completions` 请求中尝试“伪造” LTM 字段** —— LTM 与推理完全解耦，该字段会被静默忽略；
- ❌ **不要期望 RAG 问答接口返回“用户上周订的咖啡机型号”** —— 若该信息未录入知识库文档，RAG 无法凭空生成；应由 LTM 提供，再由应用层拼接注入提示词。

## 技术选型参考（面向开发者）

| 选型考量 | LTM 更优 | RAG API 更优 |
|----------|-----------|----------------|
| **开发复杂度** | ⭐⭐⭐⭐☆（5 个核心接口，参数简洁，无状态管理负担） | ⭐⭐☆☆☆（需管理知识库生命周期、Agent 发布、文件解析状态、错误重试等，路径/参数命名不一致需特别注意） |
| **调试友好性** | ⭐⭐⭐⭐☆（查询返回原始记忆片段，便于验证写入是否成功、语义是否匹配） | ⭐⭐⭐☆☆（需结合 `trace_id` 查看完整链路日志；检索结果需比对 `references` 与原始文档；问答答案不可控性更高） |
| **扩展性** | ⭐⭐⭐☆☆（当前仅支持 3 款模型；未来可能扩展类型与 TTL 策略） | ⭐⭐⭐⭐☆（支持多嵌入/重排/问答模型热切换；知识库可横向扩容；支持私有化与 VPC 专有网络部署） |
| **运维可观测性** | ⭐⭐⭐☆☆（提供基础监控指标：调用量、成功率、P95 延迟） | ⭐⭐⭐⭐☆（提供知识库健康度、切片覆盖率、检索准确率（Beta）、Agent 调用链追踪等深度指标） |
| **合规就绪度** | ⭐⭐⭐⭐⭐（设计即面向隐私保护：无日志留存、无训练污染、用户级隔离明确） | ⭐⭐⭐☆☆（需开发者主动配置权限、审核文档内容、管理存储生命周期；企业版提供更强审计能力） |

> **一句话总结**：  
> **LTM 是“记人”的工具——轻量、专属、可控；RAG 是“记事”的工具——厚重、共享、智能。**  
> 真实业务中二者常协同使用：LTM 提供用户上下文（Who & What matters to them），RAG 提供领域知识支撑（What is true in the world），由应用层统一编排提示词与调用流程。
