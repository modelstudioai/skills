# 模型部署、微调与压缩对比

为帮助开发者在模型生产全链路中做出高效、经济、可落地的技术决策，本文系统对比百炼平台三大核心能力模块：**模型部署**（服务化上线）、**模型微调**（能力定制优化）与**模型压缩**（推理成本优化）。三者并非互斥替代关系，而是构成“训练→优化→上线”的协同闭环：微调产出专属模型，压缩降低其部署门槛，部署最终交付稳定服务。本对比聚焦各方案的工程属性、适用边界与选型关键因子，面向实际开发与运维场景提供可操作的决策依据。

## 关键维度对比

| 维度 | 模型部署 | 模型微调 | 模型压缩 |
|------|----------|----------|----------|
| **核心目标** | 将模型（基础/微调/自定义）转化为高可用、可计量的在线 API 服务 | 在领域数据上增量训练模型，提升任务准确性、安全性与行为可控性 | 对已微调模型进行后训练量化（PTQ），降低推理资源消耗与部署成本 |
| **输入格式** | - 模型标识（`model_code` 或 `auto-model-xxx`）<br>- 部署参数（如 `ptu_capacity`, `plan`, `deploy_spec`）<br>- （LoRA 模型需提前导入 OSS） | - 基础模型 ID（如 `qwen3-8b`）<br>- 训练数据集（JSONL/ZIP，格式严格校验）<br>- 超参配置（`n_epochs`, `lora_rank`, `learning_rate` 等） | - 源模型 ID（仅限状态为 `succeeded` 的百炼微调模型）<br>- 量化模板（如 `MU5`/`MU8`）<br>- （可选）校准数据集（≤5 个已发布数据集） |
| **输出格式** | - 可调用的 `model_code`（如 `qwen3.8-max-abc123`）<br>- 标准化 API 响应（OpenAI 兼容或 DashScope 协议）<br>- 实时监控指标（TPM/RPM/延迟/缓存命中率） | - 新模型 ID（如 `ft-qwen3-8b-20260915-xyz789`）<br>- 训练日志、损失曲线、验证指标报告<br>- 模型状态：`succeeded` / `failed` / `canceled` | - 新模型 ID（源模型名 + 后缀，如 `my-qwen35-flash-quant-mu8`）<br>- 量化配置快照与日志<br>- 模型状态：`succeeded`（不可逆） |
| **支持模型类型** | - PTU/DTU/MU：Qwen、DeepSeek、GLM、Qwen-VL 等主流基础及 LoRA 微调模型<br>- [Token](../concepts/token.md) 按量：**仅 LoRA 微调模型**<br>- 智能路由：预置 `qwen3.8-max`、`deepseek-v4-flash-0731` 等 9 款文本模型（仅 OpenAI 接口） | - 文本：Qwen3/Qwen2.5/Plus（SFT/CPT/DPO/RL）<br>- 多模态：Qwen-VL（SFT）<br>- 图像/视频：万相系列（LoRA）<br>- 语音：CosyVoice（SFT）<br>- 决策：`decision-model-preview-2026-09-24` | - **仅支持百炼平台完成且状态为 `succeeded` 的微调模型**<br>- 不支持基础模型、第三方模型、未发布模型或视觉/语音/决策类微调模型（当前限制） |
| **API 端点** | `POST /api/v1/deployments`（PTU/MU/LoRA 支持；DTU 暂不支持）<br>调用端点：`https://dashscope.aliyuncs.com/api/v1/services/aigc/text-generation/generation`（DashScope）或 `https://maas.aliyuncs.com/v1/chat/completions`（OpenAI 兼容） | `POST /api/v1/fine_tunes`（创建任务）<br>`GET /api/v1/fine_tunes/{fine_tune_id}`（查询状态）<br>数据上传：`POST /api/v1/files` | **暂无公开 API**；仅控制台操作（路径：左侧导航栏 → 模型压缩 → 创建压缩任务） |
| **计费方式** | - PTU：按预置吞吐额度（KTPM）月度订阅<br>- DTU：按输入/输出 TPM 基准值整数倍计费<br>- MU：按部署单元（MU1/MU5等）数量 × 副本数 × 时长<br>- [Token](../concepts/token.md) 按量：按实际输入/输出 [Token](../concepts/token.md) 用量实时计费<br>- 智能路由：按所选备选模型的实际调用消耗计费 | - MTU（Model Training Unit）：按训练时长与算力规格计费（全参/SFT/CPT/RL）<br>- Token 计费：仅 SFT/CPT/LoRA 场景支持（按训练数据 Token 总量）<br>- OPD/RL 必须使用 MTU 计费 | - **压缩任务本身限时免费**（以控制台公告为准）<br>- **压缩后模型的部署费用按 MU 规格实时计费**（如 `MU5` 比 `MU1` 成本更低） |
| **典型场景** | - 高并发客服对话（PTU）<br>- 金融风控低延迟推理（DTU）<br>- A/B 测试新模型（Token 按量）<br>- 多模型效果兜底（智能路由） | - 客服话术对齐（SFT）<br>- 注入行业知识库（CPT）<br>- 拒绝有害请求（DPO）<br>- IP 形象定制（万相 LoRA）<br>- 工单自动分类（决策模型） | - 微调模型上线前成本压测<br>- 边缘/轻量级服务部署（如 `MU5` 替代 `MU16`）<br>- 大规模灰度发布时的资源弹性扩容 |

## 各方案适用场景建议

### ✅ 模型部署 —— 何时选择哪种模式？
- **选 PTU**：当业务流量稳定、可预测，且对 P99 延迟（<500ms）和吞吐一致性（如 ≥50K TPM）有强要求；适合核心生产服务（如电商搜索问答、企业知识库）。
- **选 DTU**：当需物理资源隔离保障 SLA（如金融交易辅助），或存在突发流量但拒绝降级（如大促期间营销文案生成）；注意基准 TPM 需整数倍购买。
- **选 MU**：当需灵活扩缩容（如副本数动态调整）、启用高级推理参数（`enable_thinking`, `max_context_length`），或部署视觉语言模型（Qwen-VL）；平衡成本与可控性。
- **选 Token 按量**：仅用于 LoRA 模型的效果验证、POC 或低频内部工具；**严禁用于生产环境**（无扩缩容能力、无 SLA 保障）。
- **选智能路由**：当业务可接受模型切换（如“效果优先”策略下自动切至 `qwen3.8-max`，“成本优先”切至 `glm-5.2`），且仅调用文本 Chat Completions；**必须使用 [OpenAI 兼容接口](../concepts/openai-compatible-interface.md)，且仅限北京/新加坡地域**。

### ✅ 模型微调 —— 何时必须微调？
- **必须微调**：基座模型在业务数据上表现差（准确率 <70%）、存在严重幻觉/拒答/格式错误；或需注入私有知识（法律条文、产品手册）、强化安全护栏（拒绝越权请求）。
- **推荐 LoRA 微调**：数据量 < 5,000 条、预算有限、需快速迭代（训练耗时短、显存占用低）；适用于客服、代码补全、营销文案等任务。
- **考虑全参/CPT 微调**：数据量 > 50,000 条、需深度知识融合（如医疗诊断术语体系）、或基座模型能力不足（如长文档摘要）；需更高算力与更长周期。
- **慎用 DPO/RL**：仅当已有高质量偏好数据（正负样本对）或可构建可靠 Reward 模型；否则易引入偏差，增加调试成本。

### ✅ 模型压缩 —— 何时值得压缩？
- **强烈建议压缩**：微调模型部署后 MU 成本过高（如 `MU16` 月成本超 ¥20,000），且业务对精度容忍度 >2%（如客服响应 F1 分数下降 ≤2% 可接受）。
- **必须前置验证**：同一源模型至少尝试 `MU5`/`MU8` 两个模板，并用**真实业务测试集**评估精度、延迟与首 token 时间；避免仅依赖控制台“压缩成功率”。
- **禁止压缩场景**：模型用于金融风控、医疗诊断等高敏感场景；或微调后已接近基座模型精度上限（压缩可能引发不可逆性能塌陷）；或模型为视觉/语音/决策类（当前不支持）。

## 技术选型参考（面向开发者）

| 决策问题 | 推荐动作 | 关键检查项 |
|----------|----------|------------|
| **我的模型是否该上线？** | 先微调，再压缩，最后部署 | ▢ 是否已用业务数据验证基座模型效果？<br>▢ 若效果不达标 → 进入微调流程；若达标 → 直接部署（跳过微调/压缩） |
| **微调后该用什么部署模式？** | LoRA 模型 → 优先 PTU/MU；全参模型 → 优先 MU/DTU | ▢ LoRA 模型：确认 `rank` 为 8/16/32/64，且 `chat_template` 与基座一致<br>▢ 全参模型：联系客户经理白名单开通，再选 MU/DTU |
| **如何降低成本？** | 微调 → 压缩 → 降 MU 规格 → 切换部署模式 | ▢ 压缩后是否在业务测试集上通过精度验收？<br>▢ `MU5` 部署是否满足 P99 延迟？若否 → 尝试 `MU8` 或回退至 `MU16` + PTU |
| **能否混合使用？** | ✅ 支持完整链路：微调 → 压缩 → PTU 部署；或微调 → Token 按量（验证）→ MU 部署（生产） | ▢ 所有环节地域需一致（压缩仅北京，部署需匹配）<br>▢ 智能路由不可与压缩模型混用（路由仅支持预置模型） |
| **紧急上线但预算紧张？** | 选择 Token 按量（LoRA）→ 快速验证 → 再迁移至 PTU/MU | ▢ 确认模型为 LoRA 类型且已导入<br>▢ 明确告知团队：此为临时方案，**不可用于用户直接访问的生产入口** |

> **重要提醒**：  
> - **所有部署创建后，计费方式不可变更**（如 PTU 不能转为 Token 按量），切换需先下线再重建；  
> - **模型压缩不可逆**，请务必在压缩前备份源微调模型；  
> - 智能路由与 PTU 的缓存机制不兼容（路由不保障缓存命中），高缓存依赖场景请勿选用；  
> - 实际可选模型、地域支持与价格以[百炼控制台](https://bailian.console.aliyun.com)实时信息为准，文档描述可能存在滞后。
