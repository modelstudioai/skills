# 知识检索与记忆能力方案对比

为帮助开发者在百炼平台上高效构建具备上下文感知能力的智能应用，本文对三种核心语义检索与长期状态管理能力——**知识库（Knowledge Base）**、**记忆库（Memory Library）** 和 **向量与排序服务（Vector & Rerank）** 进行系统性对比。三者虽均基于向量技术，但在设计目标、数据生命周期、调用范式及适用边界上存在本质差异。本对比旨在厘清能力定位，避免功能误用（如用记忆库替代知识库做文档问答），并为 RAG 架构设计、对话状态管理、自定义检索链路等典型场景提供可落地的技术选型依据。

## 关键维度对比

| 维度 | 知识库（Knowledge Base） | 记忆库（Memory Library） | 向量与排序服务（Vector & Rerank） |
|------|--------------------------|---------------------------|-----------------------------------|
| **核心定位** | 面向**静态私有文档**的 RAG 检索增强，强调**领域知识精准召回与生成式问答** | 面向**动态用户/会话上下文**的长期[记忆管理](../concepts/memory.md)，强调**多轮对话状态持久化与个性化检索** | 面向**通用语义计算**的原子能力，提供**文本嵌入生成**与**候选结果重排序**两类独立服务 |
| **输入格式** | 支持 PDF/Word/TXT/Markdown 等文件上传；或通过 API 接入 OSS/NAS/数据库等结构化/非结构化数据源 | JSON 对象：`content`（≤8192 字符纯文本） + 可选 `metadata`（键值对标签，≤10 对） + 可选 `memory_id` | 向量服务：单字符串或字符串数组；排序服务：`{ "query": string, "documents": string[] }` 对象 |
| **输出格式** | 结构化响应含 `answer`（LLM 生成答案）、`citations`（引用来源元数据）、`retrieved_chunks`（可选） | 写入响应返回 `memory_id`；检索响应返回匹配的记忆条目列表（含 `content`, `metadata`, `score`, `memory_id`） | 向量服务：`embedding`（浮点数组或 base64 编码）+ `usage`；排序服务：`results`（按 score 降序的索引数组），**不返回原文** |
| **支持模型** | 生成模型：仅 `qwen-max` / `qwen-plus` / `qwen-turbo`；向量模型：固定 `text-embedding-v1`（不可替换） | 生成模型：仅 `qwen-max` / `qwen-plus` / `qwen-turbo`；向量模型：实际强制使用 `text-embedding-v3`（`embedding_model` 参数已废弃） | 向量模型：`text-embedding-v1`、`multimodal-embedding-v1` 等；排序模型：`rerank-v1`；**完全独立于 LLM 生成模型** |
| **API 端点** | `POST /v1/knowledge_base/query`（RAG 查询）<br>`POST /v1/knowledge_bases`（管理） | `POST /v1/memories`（写入）<br>`POST /v1/memories/search`（检索） | `POST /api/v1/services/embeddings`（向量）<br>`POST /api/v1/services/rerank`（排序） |
| **计费方式** | **三维度叠加计费**：向量维度消耗（按 embedding 调用量）、查询次数（按 `/query` 调用）、存储容量（按知识库占用空间） | **按条计费**：以写入成功的记忆条目数为计费单元；检索调用免费 | **按次计费**：向量服务按 `input` 中文本数量计费；排序服务按单次请求中 `documents` 数量计费 |
| **数据生命周期** | 长期静态存储（文档级），支持定时同步与增量更新；首次构建耗时较长（分钟至小时级） | 动态短期存储（条目级），写入后约 2–5 秒可检索（最终一致性）；无自动过期机制，需业务侧主动清理 | 无状态、瞬时计算：输入即处理，无数据持久化，不存储任何原始内容或向量结果 |
| **典型场景** | 客服知识问答（FAQ 文档）、技术文档助手（API 手册）、企业内部制度查询、合规政策解读 | 多轮客服对话中记住用户偏好（如“上次说过敏”）、销售助手记录客户历史需求、个性化推荐上下文沉淀 | 自建 RAG 流程中的向量化阶段、对搜索引擎/数据库初筛结果进行语义重排、多模态图文检索预处理 |

## 各方案的适用场景建议

- **选择知识库（Knowledge Base）当且仅当**：  
  ✅ 你的数据是**批量、静态、结构清晰的文档集合**（如产品手册、合同模板、培训材料）；  
  ✅ 你需要**开箱即用的端到端 RAG 流程**（自动分块→向量化→检索→LLM 生成→溯源）；  
  ✅ 你追求**高精度、可审计的答案**，且接受其与 Qwen 系列模型强绑定；  
  ❌ 不适用于实时聊天记录、用户画像标签、频繁变更的会话状态等动态小片段数据。

- **选择记忆库（Memory Library）当且仅当**：  
  ✅ 你的数据是**离散、动态、带业务标签的短文本片段**（如用户反馈、会话摘要、配置偏好）；  
  ✅ 你需要**跨会话、跨用户维度的灵活过滤检索**（例如 `metadata: {user_id: "u123", type: "complaint"}`）；  
  ✅ 你已在应用层实现对话管理逻辑，仅需一个**低延迟、带结构化元数据的持久化检索后端**；  
  ❌ 不适用于长文档解析、需要生成式回答、或要求严格事务一致性的金融/医疗场景。

- **选择向量与排序服务（Vector & Rerank）当且仅当**：  
  ✅ 你需要**完全自主控制 RAG 流程各环节**（如自定义分块策略、混合检索逻辑、外部向量库集成）；  
  ✅ 你已有成熟的数据管道，仅需**原子级语义计算能力**（如将自有数据库字段向量化、对 Elasticsearch 结果重排）；  
  ✅ 你需要**多模态能力**（图文联合嵌入）或对**排序结果做深度后处理**（如融合规则分数）；  
  ❌ 不适用于快速上线问答机器人、缺乏工程资源搭建完整检索链路的中小团队。

## 技术选型参考（面向开发者）

| 你的需求 | 推荐方案 | 关键理由 | 注意事项 |
|----------|----------|----------|----------|
| **零代码/低代码快速上线客服问答机器人** | 知识库 | 控制台一键上传文档，API 直接获取带溯源的答案，无需处理向量、分块、重排等细节 | 必须使用 Qwen 系列模型；文档格式与大小受限；效果优化依赖参数组合实测 |
| **构建带用户记忆的智能导购助手（如记住上次浏览商品）** | 记忆库 | 原生支持 `metadata` 过滤，SDK 封装简洁（`memory.upsert()`/`search()`），写入延迟低 | 单条内容长度限制 8192 字符；不支持批量删除；需自行设计清理策略 |
| **在现有搜索系统（如 OpenSearch）之上叠加语义重排能力** | 向量与排序服务 | `rerank-v1` 可直接对接任意初筛结果，返回索引便于客户端映射；计费透明按次 | 排序结果不返回原文，需业务层维护 `documents` 映射表；需自行处理错误重试与限流 |
| **自建向量数据库（如 Milvus/Pinecone）并注入百炼模型能力** | 向量与排序服务 | 获取标准 `text-embedding-v1` 向量，无缝写入自有库；后续仍可调用百炼 `rerank-v1` 提升精度 | 向量维度固定（1536），不可定制；多模态输入需额外处理图像 URL/base64 |
| **需要同时满足文档问答 + 用户对话记忆** | **知识库 + 记忆库 组合使用** | 知识库处理“公司制度”等静态知识，记忆库处理“张三的订单偏好”等动态状态，职责分离清晰 | 二者 workspace 隔离，需分别管理权限与配额；答案生成需在应用层协调调用时机 |

> **重要提醒**：  
> - **禁止混用场景**：勿将用户聊天记录直接塞入知识库（违反文档静态性假设，导致分块失真、成本激增）；勿用记忆库存储 10MB PDF（超出单条长度限制）。  
> - **性能兜底建议**：高并发场景下，知识库检索建议启用 `retrieval_strategy=hybrid` + `rerank=true`；记忆库检索务必利用 `metadata` 过滤缩小范围；自建流程中，排序服务 `top_k` 建议 ≤ 50 以保障延迟。  
> - **演进兼容性**：所有方案均遵循百炼统一认证（Bearer [Token](../concepts/token.md)）与错误码规范；未来模型升级（如 `text-embedding-v3` 全面替代 v1）将通过 API 版本控制平滑过渡，旧参数（如 `embedding_model`）已明确标记 deprecated，请及时迁移。
