# 模型评估与应用评估对比

百炼平台提供两套独立的评测体系：**模型评测**面向大语言模型本身的能力验证，**应用评测**面向智能体和工作流应用的端到端输出质量评估。两者在评测对象、数据准备、评分机制和结果分析上存在显著差异。本文从关键维度对比两者的能力边界，帮助开发者根据实际需求选择合适的评测方案。

## 关键维度对比

| 维度 | 模型评测 | 应用评测 |
| --- | --- | --- |
| 评测对象 | 大语言模型（千问系列、第三方文本生成模型及其调优版本） | 智能体应用、工作流应用 |
| 评测模式 | 自定义评测、基线评测 | 自动评测（单应用 / 多应用横向）、手动评测、新版评测任务 |
| 数据来源 | 自备 Excel 数据集（评测数据集 / 推理结果集）或系统预置标准数据集（基线评测） | 知识库自动生成、人工构建上传、应用观测导入 |
| 数据格式 | Excel（Prompt / Completion / Output 列） | Excel（`.xls`/`.xlsx`）、JSONL（`.jsonl`）、新版按应用出入参定义 |
| 评分机制 | 评测维度：大模型评估-数值型/分类型、规则评估-文本相似度/字符串匹配、人工评估 | 评估器：LLM 评估器、Code 评估器、基于历史标注；标签：分类/布尔值/数字/文本 |
| 评分组件上限 | 可自由组合多个评测维度（无明确上限） | 单个评测任务最多 10 个评估器 |
| 归因分析 | 不支持 | 支持 RAG 归因（模型理解有误、重排不佳、检索无效、切片不完整、未获取知识） |
| 支持模型范围 | 自定义评测：千问 QwQ/Max/Plus/Turbo/Coder/Math 等及第三方；基线评测：仅调优后模型 | 自动评测仅支持 qwen-max 和 qwen-plus |
| 计费构成 | 裁判模型 Token 费用 + 被评测模型推理费用（分别归属） | 评测 Tokens × 模型调用单价 |
| 前提条件 | 自定义评测需创建评测维度和数据集；基线评测需完成模型调优部署 | 应用已发布、已配置知识库、已开通应用观测 |
| 多模型/多应用对比 | 可对多个候选模型横向对比，支持排行榜 | 多应用横向评测最多同时对比 8 个应用 |
| 行业基准 | 基线评测支持 C-Eval / MMLU / ARC / GSM8K / HellaSwag / BBH 等公开榜单 | 不支持行业标准基准 |

## 评测模式详细对比

| 对比项 | 模型评测 - 自定义评测 | 模型评测 - 基线评测 | 应用评测 - 自动评测 | 应用评测 - 手动评测 |
| --- | --- | --- | --- | --- |
| 灵活性 | 高，自定义评分标准 | 低，使用预置规则 | 中，可选评估器组合 | 高，人工自由判断 |
| 人力投入 | 需准备数据集和评测维度 | 仅选模型即可 | 自动生成评测集和报告 | 需人工标注打分 |
| 是否需要知识库 | 否 | 否 | 是 | 否（但需手动构建评测集） |
| 输出结果 | 综合得分、通过率、数据明细 | 分学科得分、能力雷达图 | 评分报告、归因分析、调优建议 | 评测报告 |

## 适用场景建议

**选择模型评测的场景：**

- 需要在多个候选大模型之间做选型决策，用相同测试集横向对比。
- 对调优（Fine-tuning）后的模型进行效果验证，量化调优前后的得分变化。
- 需要用公开基准（如 C-Eval、MMLU）量化模型通用能力并向团队汇报。
- 建立定期评测机制，持续监控模型在固定数据集上的表现趋势。

**选择应用评测的场景：**

- 评估智能体或工作流应用的端到端输出质量，而非单独评估底层模型能力。
- 应用依赖 RAG（知识库[检索增强生成](../concepts/rag.md)），需要定位回答质量问题出现在哪个环节（检索、重排、模型理解等）。
- 知识库更新、Prompt 调整或模型更换后，需要回归验证应用整体效果。
- 希望对比同一应用的不同版本或多个应用方案，进行选型或迭代验证。

**两者结合使用：**

在完整的开发链路中，建议先用模型评测完成底层模型选型和调优验证，再用应用评测验证整个应用（含知识库、Prompt、检索策略）的端到端效果。模型评测关注"模型能力够不够"，应用评测关注"应用效果好不好"，两者分别覆盖不同层次的质量保障需求。
