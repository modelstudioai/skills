# 向量检索与数据连接能力对比

在构建 RAG（[检索增强生成](../concepts/rag.md)）、智能 Agent 或企业级 AI 应用时，开发者常需在**语义级相似匹配**与**结构化数据精准查询**两类能力间做出技术选型。向量检索（通过 `vector and sort` API 实现）侧重于文本/图文的语义理解与排序，适用于非结构化内容的模糊匹配；而数据连接（Data Connection）则聚焦于安全、可控地对接外部结构化数据源，实现确定性 SQL 查询与动态上下文注入。本页旨在从工程落地视角，系统对比二者的核心能力边界、使用约束与适用场景，帮助开发者快速判断：何时该用向量检索？何时必须依赖数据连接？抑或二者协同使用？

## 关键维度对比

| 维度 | 向量检索（`vector and sort`） | 数据连接（Data Connection） |
|------|------------------------------|-----------------------------|
| **核心定位** | 语义嵌入与相关性重排：将文本/图文映射到向量空间，计算相似度或对候选文档打分排序 | 结构化数据动态接入：在模型推理过程中安全执行 SQL 查询或调用外部 API，获取精确、可验证的业务数据 |
| **输入格式** | • 文本向量：`string` 或 `string[]`（纯文本）<br>• [多模态](../concepts/multi-modal.md)向量：`{ "text": "...", "image": "base64..." }` 或 `{ "text": "...", "image_url": "https://..." }`（单图单文本配对）<br>• Rerank：`{ "query": "...", "documents": ["...", "..."] }`（纯文本） | • `type` + `connection_uri`（JDBC URI / OSS URL / base64 内容 / OpenAPI Schema URL）<br>• 查询逻辑由模型在运行时自动生成（RAG/Agent 场景），或由用户预定义 SQL/API 调用模板（工具调用场景） |
| **输出格式** | • 文本/[多模态](../concepts/multi-modal.md)向量：`{ "embeddings": [...] }`（float 或 base64 编码向量数组）<br>• Rerank：`{ "results": [{ "index": 0, "relevance_score": 0.92 }] }`（按相关性降序排列的文档索引与分数） | • 结构化结果：`{ "rows": [...], "columns": [...], "row_count": 12 }`（JSON 格式二维表数据）<br>• 支持自动类型推断（如数字、布尔、日期），不返回原始二进制或 BLOB 字段 |
| **支持模型** | • 文本嵌入：`text-embedding-v1` 等<br>• [多模态](../concepts/multi-modal.md)嵌入：`multimodal-embedding-v1`（单图+单文本）<br>• 重排序：`rerank-v1` 等<br>→ **所有模型均独立调用，不绑定特定 LLM** | • 仅限 `qwen-max`、`qwen-plus`、`qwen-turbo`、`qwen2.5-*` 系列大语言模型<br>→ **必须作为模型推理链路的一部分启用**（如 RAG 检索器、Agent 工具），不可单独调用 |
| **API 端点** | • 向量：`POST https://dashscope.aliyuncs.com/api/v1/services/embeddings`<br>• Rerank：`POST https://dashscope.aliyuncs.com/api/v1/services/rerank`<br>→ 统一 `/services/` 命名空间，按能力分路径 | • 连接管理：`POST /v1/data_connections`（创建）、`GET /v1/data_connections/{id}`（查询）<br>• 运行时触发：**无独立 API**，由模型服务在 RAG/Agent 执行阶段内部调用<br>→ 依赖 `/v1/chat/completions` 等主推理接口的上下文配置 |
| **计费方式** | • 按**向量条数**或**rerank 文档对数量**计费<br>• 示例：`text-embedding-v1` 100 条输入 = 100 次计费单元；`rerank-v1` 输入含 20 个 documents = 20 次计费单元<br>• 多模态向量按“文本+图像”作为一个输入单元计费 | • 按**数据连接实例数** + **查询执行次数**计费<br>• 创建/更新连接本身不计费；每次模型运行中触发一次 SQL/API 查询即计费 1 次<br>• 查询超时、失败仍计费（因已消耗连接资源） |
| **典型场景** | • 对知识库文档做语义召回（如：用户问“如何重置密码”，召回“忘记密码”“账号安全”等语义相近文档）<br>• 图文混合搜索（如：上传产品图 + “找类似设计的竞品”）<br>• 对 BM25 初筛结果做精排（提升 Top-K 结果质量） | • 查询实时数据库（如：用户问“张三上月销售额”，模型自动查 MySQL 订单表）<br>• 动态读取 Excel 报表（如：分析最新销售周报 CSV）<br>• 调用内部业务系统 API（如：通过 OpenAPI 获取库存状态） |
| **数据安全性** | • 输入文本/图像不落盘；向量结果为数学表示，不包含原始敏感信息<br>• 但需注意：若输入含 PII（如身份证号），其向量可能隐含可逆风险（建议预脱敏） | • 原始数据**永不进入百炼服务端内存或存储**；仅查询结果经沙箱解析后注入模型上下文<br>• 连接凭证加密存储，控制台不显示明文；SQL 默认只读，杜绝写操作风险 |
| **扩展性与限制** | • 单请求上限：文本向量 ≤100 条，rerank ≤50 个 documents<br>• 不支持流式响应；多模态向量不支持 `encoding_format=base64` 输出<br>• 无内置缓存机制，高频重复请求需自行实现客户端缓存 | • 单连接最大关联 10 个应用；单账号最多 50 个连接<br>• SQL 查询默认超时 10s（可配至 60s），结果默认截断至 1000 行（可配至 5000）<br>• CSV/Excel 限 50MB 且必须 UTF-8 无 BOM；不支持 MongoDB（文档过时） |

## 各方案的适用场景建议

### ✅ 优先选择 **向量检索**
- 你的数据是**非结构化文本或图文**（如 PDF 解析文本、网页快照、产品描述、客服对话日志），且需要支持“模糊语义匹配”；
- 你已具备向量数据库（如 Milvus、Pinecone、阿里云 OpenSearch 向量版），仅需百炼提供高质量嵌入/重排能力；
- 你需要对召回结果进行**二次精排**（例如：先用 BM25 快速初筛 100 篇，再用 `rerank-v1` 排出 Top 10）；
- 你追求低延迟、高并发的**纯向量化流水线**，无需访问实时业务数据库。

### ✅ 优先选择 **数据连接**
- 你的关键信息存在于**关系型数据库、CSV/Excel 表格或内部 REST API** 中，且要求**强一致性、实时性与精确字段匹配**（如“订单号=ORD2024001”的查询）；
- 你需要让模型**直接理解并操作结构化 schema**（如自动识别 `sales.amount` 是数值、`orders.status` 是枚举）；
- 你正在构建 Agent，需赋予模型**调用真实业务系统的能力**（如“创建工单”“查询物流轨迹”），而非仅回答静态知识；
- 你无法将敏感业务数据导入向量库（合规要求），必须保持数据驻留在自有环境。

### ✅ 推荐 **协同使用**
- **RAG 增强架构**：用向量检索从非结构化知识库（如产品文档）中召回候选片段；同时用数据连接实时查询结构化数据库（如客户 CRM 表）补充用户专属信息，两者结果拼接后送入 LLM；
- **混合检索策略**：对用户问题并行触发向量检索（语义召回）和 SQL 查询（关键词精确匹配），再由 LLM 融合两种结果生成最终回答；
- **Agent 工具路由**：当用户提问涉及“查数据”时，由 LLM 判定应调用数据连接工具；当提问涉及“解释概念”或“总结文档”时，则调用向量检索获取背景材料。

## 面向开发者的选型参考

| 你的需求 | 推荐方案 | 关键原因 | 注意事项 |
|----------|----------|----------|----------|
| “我要把 10 万份 PDF 文档变成可搜索的知识库” | 向量检索 + 自建向量库 | 百炼提供工业级嵌入模型，精度远超通用 Sentence-BERT；支持多模态扩展 | 需自行搭建/运维向量数据库；PDF 解析需前置处理 |
| “用户问‘我的订单发货了吗？’，我需要查 Oracle 订单表” | 数据连接 | 直接对接生产库，毫秒级返回真实状态；SQL 只读保障绝对安全 | 需配置 JDBC URI 和网络白名单；避免在提示词中暴露表结构 |
| “召回结果太多太杂，想让模型更懂哪个最相关” | `rerank-v1` | 专为 query-document 打分优化，显著优于向量余弦相似度排序 | 输入 documents 数量 ≤50；不支持图像/表格等富媒体 |
| “既要查数据库，又要搜文档，还要识图” | **组合方案**：数据连接 + `text-embedding-v1` + `multimodal-embedding-v1` | 各司其职：数据连接保准确，向量检索保语义，多模态拓展图文场景 | 注意 [Token](../concepts/token.md) 开销与端到端延迟；建议用异步任务编排查询流程 |
| “我们有严格的数据不出域要求，连向量也不能传出去” | **暂不适用任一方案** | 向量检索需上传原文/图片；数据连接虽不传数据但需开放数据库访问权限 | 可考虑百炼私有化部署版，或使用本地化嵌入模型（如 ONNX 运行时） |

> **最后提醒**：技术选型不是非此即彼。在复杂 AI 应用中，**向量检索解决“找什么”（What to retrieve）**，**数据连接解决“找哪里”（Where to fetch）**——二者本质互补。建议从最小可行场景切入：先用向量检索跑通 RAG 基础链路，再逐步集成数据连接以接入核心业务数据，最终形成语义+结构的双重增强能力。
