# 流程型 Agent 与托管型 Agent 对比

为帮助开发者在百炼平台中高效选型，本文系统对比两类核心 Agent 架构方案：**流程型 Agent（Flow Agent）** 与 **托管型 Agent（Managed Agent）**。二者定位不同——前者面向「已发布、可复用的业务级智能应用」，强调低代码集成与工作流编排；后者面向「需深度定制、全生命周期可控的运行时智能体」，强调细粒度控制与扩展能力。本对比基于当前平台（2024年Q3）稳定发布的 API 能力，聚焦实际开发决策所需的关键技术维度，不涉及内部实现细节或未公开的预览功能。

## 关键维度对比

| 维度 | 流程型 Agent（Flow Agent） | 托管型 Agent（Managed Agent） |
|------|-----------------------------|--------------------------------|
| **核心定位** | 调用已发布的工作流/智能体应用（App），或管理底层组件（如[长期记忆](../concepts/long-term-memory.md)）；以“服务调用”和“配置管理”为主 | 构建、部署、运行和扩展可编程的 Agent 实例；以“运行时控制”和“会话生命周期管理”为核心 |
| **输入格式** | - 应用调用接口：`{"input": {...}}`，结构由应用定义（如 `{"query": "xxx", "user_id": "123"}`）<br>- 组件接口（如[长期记忆](../concepts/long-term-memory.md)）：JSON body 含 `content`, `description` 等字段，严格按 Schema 定义 | 标准化结构：`{"input": {"text": "..."}}` 或 `{"input": {"files": ["file_id1"]}}`；支持文本+文件混合输入；`stream` 参数控制响应模式 |
| **输出格式** | - 应用调用接口：返回 `output` 字段（含 `text`, `files`, `actions` 等），结构与所调用 App 的输出契约一致<br>- 组件接口：返回资源 ID（如 `memoryId`）、列表分页数据（含 `nextToken`）等管理元信息 | 同步调用：返回完整 `{"output": {"text": "...", "files": [...]}}`；流式调用（`stream=true`）：SSE 格式事件流（`data: {"delta": {"text": "..."}}`） |
| **支持模型** | 不直接暴露模型选择；底层模型由工作流/智能体应用在控制台配置决定（如 Qwen-Max、GLM-4），API 层不可覆盖 | 显式支持指定模型：创建 Environment 或 Agent 时通过 `model_id` 参数声明（如 `"qwen-max"`、`"qwen-plus"`）；当前仅支持百炼托管模型，不支持 BYOM（Bring Your Own Model） |
| **API 端点与认证** | **双端点体系，认证方式分离**：<br>- 应用调用：`https://{workspaceId}.cn-beijing.maas.aliyuncs.com/v1/apps/{app_id}/chat`，使用 **Bearer API Key**<br>- 组件管理（如[长期记忆](../concepts/long-term-memory.md)）：`https://bailian.{region}.aliyuncs.com/v1/{workspaceId}/memories`，使用 **AccessKey 签名（ACS3-HMAC-SHA256）** | **统一端点与认证**：<br>- 全部接口位于 `https://dashscope.aliyuncs.com/api/v1/...`（或区域化域名）<br>- 统一使用 **Bearer Access [Token](../concepts/token.md)**（通过 OAuth2 流程获取），无需 AccessKey 签名 |
| **计费方式** | 按调用量计费：<br>- 应用调用：按每次请求计费（含 token 消耗）<br>- 组件接口（长期记忆）：**免费**（当前阶段，不计入账单） | 按 Agent 实例 + 调用行为综合计费：<br>- Agent 创建/环境配置：免基础费<br>- 每次 Session 调用：按输入/输出 token 及调用次数计费<br>- File API、Memory Store 等扩展能力按用量单独计费 |
| **典型场景** | - 快速集成已上线的客服问答、审批助手、报告生成等标准化应用<br>- 在自有系统中嵌入一个“黑盒智能模块”，关注输入输出契约而非内部逻辑<br>- 需要轻量级长期记忆（如用户偏好快照）且接受手动维护 | - 构建多轮对话机器人（如销售顾问、技术支持），需精确控制会话状态与上下文生命周期<br>- 需动态加载技能（Skills）、安全注入凭证（Vault）、解析上传文档（File API）的复杂 Agent<br>- 要求流式响应、事件驱动（Event）、自定义 Memory Store TTL 或检索策略的高阶场景 |
| **内存能力** | 仅提供“长期记忆（旧）”：结构化 KV 存储，需显式传入 `memoryId`；**不支持向量化、语义检索、自动摘要；不支持用户画像**；已标记为遗留方案 | 提供“Memory Store”：支持对话级记忆持久化（TTL 默认 7 天），与 Session 强绑定；支持后续扩展向量存储与检索插件（平台演进方向） |
| **扩展性与定制** | 低代码导向：扩展依赖控制台配置工作流节点；API 层不开放 Skill 注册、工具调用链路控制 | 高代码导向：支持注册自定义 Skill（HTTP/Webhook 函数）、配置 Credential Vault、挂载外部文件、编写 Event Handler；具备完整 Agent 运行时控制平面 |
| **运维与可观测性** | 依赖 DashScope 应用网关日志；组件操作（如删记忆）无审计日志；错误码分散（应用侧 vs OpenAPI 侧） | 提供统一 Session 日志、Skill 调用追踪、Event 流监控；所有操作符合阿里云 OpenAPI 审计规范，支持 request_id 全链路排查 |

## 适用场景建议

### ✅ 推荐选用 **流程型 Agent（Flow Agent）** 当：
- 你已有在百炼控制台发布完成的成熟工作流或智能体应用，只需在业务系统中“调用它”；
- 项目周期紧，团队无专职 AI 工程师，希望最小化接入成本；
- 仅需简单状态保持（如记住用户上次选择的城市），且能接受手动管理记忆体生命周期；
- 安全合规要求允许使用 API Key（而非更严格的 OAuth [Token](../concepts/token.md)）进行服务间调用。

### ✅ 推荐选用 **托管型 Agent（Managed Agent）** 当：
- 你需要构建具备多轮对话、上下文感知、工具调用、文件理解等复合能力的专属 Agent；
- 业务逻辑强依赖异步事件（如用户提交表单后触发审批流、文件解析完成推送通知）；
- 必须对敏感操作（如调用支付 API）实施凭证隔离（Vault），或需对上传文档做预处理与引用；
- 团队具备 RESTful API 集成经验，愿意承担稍高的开发与调试成本，以换取长期可维护性与扩展弹性。

> ⚠️ 注意：若项目涉及用户画像管理（如标签体系、行为轨迹聚合），两类方案均**不直接支持**——必须通过百炼控制台的「用户画像」模块配置，再以 ID 方式在 Agent 中引用，API 层暂无画像 CRUD 接口。

## 技术选型参考（致开发者）

| 你的需求 | 推荐方案 | 理由简述 |
|----------|-----------|-----------|
| “我只想调用一个已上线的‘合同审核助手’，给它传一段文本，拿回审核意见” | **流程型 Agent** | 直接调用 `/apps/{id}/chat`，5 分钟完成集成；无需管理会话、内存或模型版本。 |
| “我要做一个银行理财顾问 Bot，需记住用户风险测评结果、实时查询产品库、支持上传资产证明 PDF，并在每轮对话中动态生成个性化建议” | **托管型 Agent** | 需 `Session` 管理多轮状态、`File API` 解析 PDF、`Skills` 调用风控引擎、`Memory Store` 缓存测评结果——仅托管型提供完整能力栈。 |
| “我需要为 10 个不同业务线部署相似但参数不同的审批流，每个流需独立记忆审批人偏好” | **流程型 Agent + 长期记忆（旧）** | 为每条流创建独立 `memoryId`，调用时传入即可；避免重复开发 10 套 Agent，复用工作流模板更高效。 |
| “我正在设计 SaaS 平台的 AI 插件市场，需允许第三方开发者注册自己的工具函数并安全接入我的 Agent” | **托管型 Agent** | `Skills API` 和 `Vault API` 是唯一支持第三方扩展与凭证沙箱的机制；流程型无开放工具注册能力。 |
| “我对延迟极度敏感，要求首字响应 <800ms，且需 SSE [流式输出](../concepts/streaming-output.md)” | **托管型 Agent** | 原生支持 `stream=true` SSE；流程型应用调用接口目前仅同步响应，流式能力需应用自身实现。 |

**最后建议**：  
- 新项目优先评估 **托管型 Agent** ——其设计更符合现代 Agent 工程范式，平台演进重心明确，长期记忆（新）、RAG 集成、可视化调试等高级能力将首先在此架构落地；  
- 现有流程型应用可继续使用，但**避免在新项目中依赖“长期记忆（旧）”**，该能力已标注为遗留方案，未来将逐步迁移至托管型 Memory Store 或统一向量数据库；  
- 混合架构可行：用托管型 Agent 作为主控体，通过 `Skills` 调用流程型已发布的工作流应用，兼顾复用性与可控性。
