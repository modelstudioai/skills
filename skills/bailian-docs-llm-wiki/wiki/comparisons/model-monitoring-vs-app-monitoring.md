# 模型监控 vs 应用监控

在阿里云百炼平台使用大模型构建 AI 应用时，**模型监控**与**应用观测**是两类不同层级的可观测能力。前者聚焦于底层模型调用本身的成本、性能与安全指标，后者关注上层应用（智能体、工作流、高代码应用）内部完整的调用链路与节点行为。两者结合使用，才能构建从模型服务到业务应用的全栈可观测体系。本文从多个关键维度对比两者的差异，帮助开发者在技术选型时明确各自的定位与适用场景。

## 关键维度对比

| 维度 | 模型监控 | 应用观测 |
|------|----------|----------|
| **监控对象** | 主账号下所有[业务空间](../concepts/workspace.md)的模型调用 | 智能体应用、工作流应用、高代码应用 |
| **观测层级** | 模型服务层（单次 API 调用粒度） | 应用调用链层（端到端调用链路） |
| **核心指标** | 调用次数、Token 消耗、首 Token 延时、调用时长、RPM/TPM、失败率、内容安全错误 | 调用链路追踪、Span 节点树、Token 总量、首 Token 耗时、调用时长、失败率 |
| **数据延迟** | 普通监控小时级，高级监控分钟级 | 分钟级 |
| **数据协议 / 底层服务** | 私有 Prometheus 实例，支持 Prometheus HTTP API | 可观测链路 OpenTelemetry 服务 |
| **API 接入** | 支持（Prometheus `query_range`，Basic Auth 鉴权） | 暂无 API 接口，仅控制台使用 |
| **第三方集成** | 支持接入 Grafana 及自建监控系统 | 无直接第三方集成，依赖 OpenTelemetry 存储 |
| **告警能力** | 支持，按紧急/错误/警告/普通等级通过短信、邮件、电话、钉钉/企微机器人、Webhook 通知 | 不支持独立告警配置 |
| **日志能力** | 支持审计日志和推理日志（仅北京/新加坡地域部分模型） | 通过 Span 数据查看输入/输出，支持导出 JSONL/EXCEL |
| **调用链路追踪** | 不支持，仅按模型/[业务空间](../concepts/workspace.md)/API Key 等维度聚合 | 支持，按 CHAIN → AGENT/LLM/RETRIEVER/TOOL 等节点展开完整调用树 |
| **节点类型覆盖** | 不涉及节点概念 | CHAIN、AGENT、LLM、RETRIEVER、EMBEDDING、RERANKER、REWRITER、TOOL、GUARDRAIL、工作流专属节点等 |
| **Span 筛选与过滤** | 不支持 | 支持 Root Span / All Span / Model Span 模式，可按状态、关键词、延时、Token 量、标签等多维过滤 |
| **数据标注与评测** | 不支持 | 支持对 Span 添加自定义标签，并可批量添加到评测集 |
| **免费额度管理** | 支持「免费额度用完即停」开关，避免超额付费 | 不涉及模型免费额度 |
| **用量统计** | 按模型类型（Token/张/秒等）统计，支持近 30 天查询及历史账单导出 | 按应用维度统计 Token 总量与调用次数，最长 30 天 |
| **计费** | 随模型调用计费（Token/张/秒），高级监控与告警不额外收费 | 功能本身免费，需支付 OpenTelemetry 服务的存储费用 |
| **地域支持** | 普通监控全地域；高级监控北京/新加坡/弗吉尼亚；告警北京/新加坡；日志仅北京/新加坡部分模型 | 依赖 OpenTelemetry 服务开通地域 |
| **覆盖模型范围** | 所有模型（含调优后的自定义模型） | 仅应用内部调用的模型链路（通过 LLM 节点体现） |

## 适用场景建议

### 选择模型监控的场景

- **成本管控**：需要按[业务空间](../concepts/workspace.md)、模型维度精细化追踪 Token 消耗，设置免费额度用完即停，或通过账单分析优化用量。
- **性能基线与告警**：需要对模型服务的延时、RPM、TPM、失败率等设置阈值告警，出现异常时第一时间通过电话/短信/钉钉群通知到值班人员。
- **外部系统集成**：已有基于 Prometheus + Grafana 的可观测体系，希望将模型调用指标接入统一大盘，通过 HTTP API 拉取 `model_call_count`、`model_call_duration`、`model_first_token_duration` 等指标。
- **内容安全审计**：需要记录模型推理日志，对输入输出进行合规审计与故障排查。
- **纯 API 调用场景**：应用以直接调用模型 API 为主（非百炼应用编排），不涉及智能体或工作流节点链路。

### 选择应用观测的场景

- **应用链路调试**：智能体或工作流运行结果不符合预期，需要查看从根节点到 LLM、检索、插件、重排等每个节点的输入输出与耗时，定位瓶颈节点。
- **RAG 效果优化**：需要分别观测 RETRIEVER（BM25 / 向量检索）、RERANKER、REWRITER、EMBEDDING 等检索链路节点的表现，针对性优化召回与排序策略。
- **评测闭环**：希望将线上观测数据（Span）标注后直接回流到评测集，构建"观测 → 标注 → 评测 → 优化"的迭代闭环。
- **多模态节点分析**：应用包含插件调用（TOOL）、内容安全检测（GUARDRAIL）、分类（CLASSIFIER）等多种节点，需要按节点类型分别统计耗时与成功率。
- **应用级统计**：关注整体应用的调用次数、失败率、Token 总量等业务层指标，而非单个模型调用的底层性能指标。

## 技术选型参考

对于生产环境的百炼应用，推荐两者**协同使用**而非二选一：

1. **基础层（模型监控）**：无论应用形态如何，都应开启模型监控以获取成本、性能、安全三类核心指标，并配置告警规则。对于已有 Prometheus 体系的团队，通过高级监控接入 Grafana 是自然的选择。
2. **应用层（应用观测）**：对于基于百炼智能体、工作流或高代码框架构建的应用，应开启应用观测以获得调用链路追踪、节点级分析、数据标注与评测回流能力。
3. **分工边界**：模型监控回答"模型服务是否健康、花了多少钱"；应用观测回答"这次请求在应用里走了哪些节点、哪一步慢了、结果是否正确"。两者通过 Request ID / Trace ID 可相互关联。
4. **成本考量**：模型监控的高级监控与告警不额外收费，只需关注模型调用本身的用量成本；应用观测需承担 OpenTelemetry 的存储费用，在高调用量场景下应关注存储成本增长。
5. **限制注意**：应用观测暂无 API，无法嵌入自动化流水线；Assistant API 创建的智能体不支持应用观测。模型监控的日志功能目前仅覆盖北京/新加坡地域的部分模型，选型时需确认所在地域与模型是否在支持范围内。
