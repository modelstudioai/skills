# 知识库、记忆库与[长期记忆](../concepts/long-term-memory.md)功能对比

为帮助开发者在百炼平台上准确选型，本文对三种核心状态与知识管理能力——**知识库（Knowledge Base）**、**记忆库（Memory Library）** 和 **[长期记忆](../concepts/long-term-memory.md)（新）（Long Term Memory New）** 进行系统性对比。三者均面向“将外部信息注入大模型上下文”这一目标，但在设计定位、数据形态、生命周期、集成方式及适用边界上存在本质差异。本对比基于当前平台（v20240701 及 SDK v2.3.0+）的正式能力，聚焦技术可行性、API 可控性与生产落地约束，不涉及概念性或未来规划功能。

| 维度 | 知识库（Knowledge Base） | 记忆库（Memory Library） | [长期记忆](../concepts/long-term-memory.md)（新）（Long Term Memory New） |
|------|--------------------------|---------------------------|----------------------------------------|
| **核心定位** | 面向**静态、结构化、组织级知识资产**的 RAG 增强组件；强调权威性、可溯源、批量治理 | 面向**动态、细粒度、用户/会话级结构化记忆**的通用向量存储服务；强调灵活性、元数据驱动、跨模型兼容 | 面向**对话级上下文延续**的轻量状态管理能力；强调与 Qwen 模型深度协同、开箱即用、低代码集成 |
| **输入格式** | 支持上传完整文档（PDF/Word/Excel/TXT/Markdown），自动解析→分块→向量化；内容为原始文件文本 | 仅支持 `content`（string，≤8192 字符） + `metadata`（flat object，≤10 键，单值≤1024 字符）；需应用层预处理为语义单元 | 仅支持 `content`（string，≤8192 字符） + `metadata`（object，总大小≤4KB，字段名不可以 `_` 开头）；无文档解析能力 |
| **输出格式** | 返回 `query` 的问答结果（含生成答案） + 溯源片段列表（含原文、位置、相似度）；支持多轮上下文感知 | 仅返回检索结果列表：每条含 `id`、`content`、`metadata`、`score`（余弦相似度）；**不生成答案，需应用调用 LLM 二次处理** | 仅返回检索结果列表：每条含 `id`、`content`、`metadata`、`score`；**不生成答案，需应用自行拼接 [prompt](../guides/prompt.md) 调用模型** |
| **支持模型** | 仅限 `qwen-max`、`qwen-plus`、`qwen-turbo`；其他模型无法启用知识库增强 | **全模型兼容**（Qwen/GLM/第三方等），但嵌入固定使用 `text-embedding-v1`；检索结果供任意模型消费 | 仅限 `qwen-max`、`qwen-plus`、`qwen-turbo`；其他模型调用时 `memory_id` 参数被忽略，退化为无状态调用 |
| **API 端点** | `/v1/knowledge_bases/{kb_id}/query`（查询接口）<br>`/v1/knowledge_bases`（管理接口） | `/v1/memory/collections/{collection_name}/upsert`（写入）<br>`/v1/memory/collections/{collection_name}/search`（检索） | `/v1/memory/write`（写入）<br>`/v1/memory/retrieve`（检索）<br>`/v1/memory/clear`（清空） |
| **计费方式** | 按**知识库实例 + 文档存储量 + 查询次数**计费：<br>• 存储：GB/月<br>• 查询：次（按 `query` 调用计）<br>• 不含嵌入计算费用（已内嵌） | 按**写入条数 + 检索次数 + 存储容量**计费：<br>• 写入：条<br>• 检索：次<br>• 存储：GB/月（按 collection 统计） | 按**写入条数 + 检索次数 + 存储容量**计费：<br>• 写入：条<br>• 检索：次<br>• 存储：GB/月（按 `memory_id` 统计） |
| **数据生命周期** | 静态为主：文档上传后长期有效；支持定时同步更新源文件；无自动过期机制 | 动态可控：由业务显式写入/检索；单 collection 最多 100 万条；**无 TTL，需自行清理** | 对话级隔离：以 `memory_id` 为单位；单 `memory_id` 最多 10,000 条；**当前版本无 TTL，永久保留直至 `clear`** |
| **关键能力特性** | • 自动文档解析与智能分块<br>• 关键词+向量混合检索（`enable_hybrid_search`）<br>• 多轮问答上下文感知<br>• 完整溯源（原文高亮、页码/段落） | • 元数据过滤（`filter` 支持 `==`/`!=`/`in`）<br>• Collection 级隔离与命名控制<br>• 批量 upsert（≤100 条/次）<br>• 向量索引延迟约 30 秒 | • `memory_id` 作为一级隔离标识（建议 UID/SessionID 哈希）<br>• `filter` 支持 `eq`/`in`/`contains`<br>• 写入延迟 <300ms（高并发需重试）<br>• 不支持单条删除，仅支持 `clear` 全量清空 |
| **典型场景** | • 客服知识库问答（产品手册、FAQ）<br>• 内部政策/合规文档助手<br>• 技术文档智能检索与摘要 | • 用户偏好记忆（如“用户喜欢无糖咖啡”）<br>• 多会话间个性化推荐上下文复用<br>• 工单系统中跨任务的实体关系追踪 | • 客服对话中持续记住用户姓名、订单号、投诉历史<br>• 多步骤表单填写中暂存中间状态<br>• 推荐引擎中实时更新用户本次会话兴趣标签 |

## 各方案的适用场景建议

- **选择知识库，当你的需求是：**  
  ✅ 需要直接对 PDF/Word 等原始文档进行问答，且要求答案可溯源、可验证；  
  ✅ 数据来源稳定、更新频率低（如季度更新的产品手册）；  
  ✅ 场景强依赖“权威答案”，而非个性化表达；  
  ❌ 不适合高频写入、细粒度用户状态管理，也不适合非 Qwen 模型。

- **选择记忆库，当你的需求是：**  
  ✅ 需要跨模型（包括 GLM、第三方 API）统一管理用户/会话记忆；  
  ✅ 数据高度结构化、需复杂元数据过滤（如 `user_id == "u123" AND category IN ["diet","allergy"]`）；  
  ✅ 业务已具备成熟的文本预处理流水线，能将事件转化为短文本记忆单元；  
  ❌ 不适合直接喂入长文档，也不提供问答生成能力，需自行构建 LLM 调用链。

- **选择长期记忆（新），当你的需求是：**  
  ✅ 主力模型为 `qwen-max`/`qwen-plus`/`qwen-turbo`，追求最小开发成本实现对话状态延续；  
  ✅ 场景以“单用户单会话”为主，记忆规模可控（<10k 条/用户），且接受全量清空策略；  
  ✅ 需要快速验证对话记忆效果，无需自建向量数据库或设计复杂元数据 schema；  
  ❌ 不适合多模型混用架构，也不适合需要精确控制单条记忆生命周期（如按时间过期）的场景。

## 面向开发者的技术选型参考

1. **先确认模型栈**：若已锁定 Qwen 系列且追求端到端 RAG 效果 → 优先评估**知识库**；若需兼容 GLM 或自托管模型 → 排除知识库和长期记忆（新），仅剩**记忆库**可选。

2. **再判断数据形态**：  
   - 输入是**原始文件**？→ 必选**知识库**（唯一支持文档解析）。  
   - 输入是**结构化事件流**（如用户点击、表单提交、API 日志）？→ 在**记忆库**与**长期记忆（新）** 中二选一。  
     - 若需 `collection` 级多租户隔离、复杂过滤、百万级存储 → 选**记忆库**；  
     - 若只需 `user_id` 级轻量状态、快速上线、且模型栈固定 → 选**长期记忆（新）**。

3. **最后审视运维诉求**：  
   - 需要自动文档同步、权限隔离、企业级审计日志？→ **知识库**提供最完备管控面。  
   - 需要跨 collection 联合检索、TTL 过期、嵌套 metadata？→ 当前三者均不支持，需自研或等待平台演进。  
   - 对写入延迟敏感（<100ms）？→ **长期记忆（新）** 延迟最低（<300ms），但需处理 503；**记忆库**有 30 秒索引延迟；**知识库**无实时写入概念（离线构建）。

> **重要提醒**：三者**不互斥**，可组合使用。典型模式为：  
> **知识库**承载企业知识底座（静态权威） + **长期记忆（新）** 承载当前会话状态（动态上下文） → 构成“静态知识 + 动态记忆”的双层 RAG 架构，兼顾准确性与个性化。  
> 开发者应基于首个 MVP 场景的最小可行路径启动，再根据数据规模、模型扩展性、安全合规要求逐步演进。
