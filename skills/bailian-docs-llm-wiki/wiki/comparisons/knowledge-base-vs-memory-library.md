# 知识库与记忆库（[长期记忆](../concepts/long-term-memory.md)）功能对比

本文旨在帮助开发者清晰区分百炼平台中**知识库（Knowledge Base）** 与**记忆库（Memory Library，即[长期记忆](../concepts/long-term-memory.md)）** 两大核心能力的定位、技术实现与适用边界。二者虽均基于向量检索与大模型协同，但设计目标截然不同：知识库面向**静态、共享、领域化文档数据**的 RAG 增强；记忆库则聚焦**动态、私有、用户级会话状态**的跨轮次持续理解。准确选型可避免架构冗余、成本浪费与效果偏差，是构建高可用智能应用的关键前提。

## 关键维度对比

| 维度 | 知识库（Knowledge Base） | 记忆库（[长期记忆](../concepts/long-term-memory.md)，Memory Library） |
|------|--------------------------|-------------------------------------|
| **核心目标** | 提升模型在**特定领域知识**上的事实准确性与专业性（“我知道什么”） | 维持模型对**特定用户/会话**的上下文连续性与个性化理解（“我记得你什么”） |
| **数据性质** | 静态、批量注入、多用户共享（如公司制度、产品手册、FAQ） | 动态、流式生成、严格按 `user_id` 隔离（如用户偏好、历史承诺、待办事项） |
| **输入格式** | 支持 PDF/Word/Excel/TXT/Markdown 等**完整文档文件**（单文件 ≤100 MB）；自动切片、向量化 | 支持 `messages`（最多 50 条 role-content 对）或 `custom_content`（≤512 字符纯文本）；**不接受原始文件上传** |
| **输出格式** | 检索返回结构化文档片段（含 `content`, `source`, `score`）；问答生成结果含引用溯源标记（如 `[1]`） | 返回记忆片段列表（`memory_nodes`），含 `id`, `content`, `timestamp`, `metadata`；用户画像返回结构化 JSON（字段名由 schema 定义） |
| **支持模型** | 默认对接 `qwen-max`/`qwen-plus`/`qwen-turbo`；开源模型需显式指定 `model_id` | **不绑定生成模型**；记忆写入（Add）与检索（Search）为独立服务，结果可注入任意下游模型（如 `qwen-max`、`qwen2.5-72b` 或自定义 LLM） |
| **API 端点** | - 检索：`POST /v1/knowledge_bases/{kb_id}/retrieve`<br>- RAG 问答：`POST /v1/chat/completions`（需传 `knowledge_base` 参数） | - 写入：`POST /api/v2/apps/memory/add`<br>- 检索：`POST /api/v2/apps/memory/search`<br>- 管理：`GET /api/v2/apps/memory/list` 等（统一 `/api/v2/apps/memory/` 基路径） |
| **计费方式** | 按实际调用量计费：<br>• 检索次数（每次 `/retrieve` 或 `/chat/completions` 中启用知识库）<br>• 生成 token 数（RAG 问答中的 output tokens） | **商业化起始时间：2026 年 8 月 20 日 10:00（北京时间）**<br>• `AddMemory` 与 `SearchMemory` 分别计费<br>• 按 `pro`/`lite` 策略版本分档定价（`pro` 成本更高，精度与召回率更优） |
| **典型场景** | • 客服机器人回答产品参数/售后政策<br>• 内部员工查询制度文档/项目报告<br>• 技术支持助手解析 API 文档与错误日志 | • 个人助理记住用户每日饮水提醒、会议偏好、饮食禁忌<br>• 销售助手持续追踪客户关注点与历史承诺<br>• 教育应用记录学生薄弱知识点与学习风格 |
| **数据隔离粒度** | 按 `knowledge_base_id` 隔离；同一知识库内所有用户共享内容 | 严格按 `user_id` 隔离；同一 `user_id` 下可跨多个 `memory_library_id` 或 `project_id` 存储不同类型记忆 |
| **更新机制** | 支持增量同步（上传新文件/修改原文后重建索引）；**不支持细粒度段落编辑** | 支持 `UpdateMemory`（PATCH）与 `DeleteMemory`（DELETE）；用户画像支持多轮增量更新字段值 |
| **时效性控制** | 无内置过期机制；文档更新需手动触发同步 | 支持 `expired_in_days` 参数（写入时可选）；未设置则按 MemoryProject 默认规则（通常 180 天），**仅影响检索可见性，数据物理保留** |

## 适用场景建议

### ✅ 选择知识库（Knowledge Base）当：
- 你的数据是**组织级、静态、需多人协作使用**的文档集合（如企业知识库、法规汇编、技术白皮书）；
- 核心诉求是让模型**准确回答事实性问题**，且答案必须可追溯至原始文档；
- 数据体量大（万级文档）、格式多样（PDF/表格/长文），需自动化切片与混合检索（BM25 + 向量）；
- 业务逻辑要求**强一致性**——所有用户看到的知识源完全相同，无需个性化过滤。

### ✅ 选择记忆库（长期记忆）当：
- 你需要模型**跨会话记住单个用户的行为、偏好、承诺或状态**（如“上次说要推荐科幻小说”、“已确认下周三开会”）；
- 数据来源于**实时对话流**，需从自然语言中自动提取关键事件（记忆片段）或结构化属性（用户画像）；
- 要求**严格的隐私隔离**，确保 A 用户的记忆绝不会被 B 用户或系统其他模块访问；
- 业务需要灵活的**记忆生命周期管理**（如手动删除敏感信息、按规则自动归档、多策略检索平衡速度与精度）。

### ⚠️ 避免混淆的典型误区：
- **❌ 用知识库存储用户个人信息**：违反数据隔离原则，存在隐私泄露风险，且无法按 `user_id` 精准召回。  
- **❌ 用记忆库托管产品说明书**：成本高昂（按调用频次计费）、缺乏文档级元数据管理（如来源页码）、不支持 PDF 表格解析等专业能力。  
- **❌ 在同一场景强行混用二者替代对方**：例如用记忆库存 FAQ 以图“个性化”，会导致维护成本剧增且检索效率低下；或用知识库存储用户聊天记录以图“长期记忆”，将造成严重的数据污染与权限失控。

## 技术选型参考（面向开发者）

| 选型决策点 | 推荐动作 | 说明 |
|------------|----------|------|
| **数据源头是文件还是对话？** | 文件 → 知识库；对话消息 → 记忆库 | 这是最根本的判据。知识库 API 不接受 `messages` 输入；记忆库 API 不接受文件上传。 |
| **是否需要多用户共享同一份知识？** | 是 → 知识库；否 → 记忆库 | 知识库天然共享；记忆库强制 `user_id` 隔离，共享需业务层聚合（不推荐）。 |
| **是否要求答案带原文引用？** | 是 → 知识库；否 → 记忆库 | 知识库 RAG 问答默认返回 `[1][2]` 引用；记忆库返回纯文本片段，引用需自行实现。 |
| **是否需结构化抽取固定字段（如“年龄”“职业”）？** | 是 → 记忆库（配合 `profile_schema`）；否 → 知识库 | 知识库仅做语义匹配，不提供 Schema 驱动的结构化抽取。 |
| **延迟敏感度如何？** | 检索延迟 <300ms → 优先记忆库（`SearchMemory` 平均 200–500ms）；容忍 >1s → 知识库（索引构建+RAG生成链路更长） | 知识库端到端延迟受文档体积、`top_k`、重排序等影响更大。 |
| **当前预算与未来扩展性** | 免费试用期 → 可先用记忆库验证；需长期稳定 → 知识库计费模式更透明可控 | 记忆库商业化时间明确（2026年8月），知识库已全面计费；大规模知识库部署需预估 token 消耗。 |

> **最佳实践提示**：复杂应用常需**协同使用**二者。例如：客服机器人 = **知识库**（回答产品功能） + **记忆库**（记住该用户的历史投诉与特殊需求）。此时，知识库结果用于生成通用答案，记忆库结果作为个性化前缀注入提示词（如“用户张三曾反馈屏幕亮度问题，本次回答请优先提及护眼模式”），实现精准增强。
